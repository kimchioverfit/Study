    Tailscale

    Tailscale — 포트포워딩 없이 집 PC에 외부에서 접속하는 원리

    집 PC(Windows 11)를 카페 와이파이·폰 LTE 어디서든 원격 데스크톱(RDP)·SSH로 조작할 수 있게 만든 과정과, 그게 왜 되는지를 네트워크 관점에서 정리. 공유기 설정은 하나도 건드리지 않았음.

    결론부터 아주 쉽게: 공유기 뒤에 숨은 PC는 밖에서 찾아 들어갈 방법이 없음. Tailscale은 반대로 PC가 스스로 밖으로 나가서 다른 기기와 중간에서 만나게 하고, 그 사이에 WireGuard 암호화 터널을 깔아 마치 같은 LAN에 있는 것처럼 보이게 함. RDP·SSH는 그 터널 위에서 평소처럼 동작할 뿐임.

    관련: OSI 7계층 · 실제 설정 스크립트는 별도 저장소 remote_computer에 있음

    🔷 2. 문제의식 — 왜 집 PC는 밖에서 안 보이는가

    2.1 사설 IP와 NAT

    집 PC의 주소를 확인하면 192.168.55.100. 이건 사설 IP(RFC 1918)라 인터넷에서는 의미가 없음 — 전 세계 수억 대의 공유기가 똑같은 192.168.x.x를 쓰고 있음.

    인터넷에서 보이는 건 공유기의 공인 IP 하나뿐(예: 211.x.x.x). 집 안 기기들이 밖으로 나갈 때 공유기가 출발지 주소를 자기 공인 IP로 바꿔 쓰는데, 이게 NAT(Network Address Translation)임.

    PC → 공유기 : src 192.168.55.100:51000 → dst 8.8.8.8:53
공유기 → 밖 : src 211.x.x.x:56926     → dst 8.8.8.8:53   ← 공유기가 바꿔 씀
                                                          (NAT 테이블에 "56926 ↔ 192.168.55.100:51000" 기록)
답장 → 공유기: dst 211.x.x.x:56926 → NAT 테이블 조회 → PC로 전달

    핵심은 마지막 줄. 공유기는 “안에서 먼저 나간 연결"의 답장만 안으로 넘김. 테이블에 없는 패킷이 밖에서 오면 누구한테 줄지 모르니 버림.

    2.2 그래서 밖에서 두드리면

    카페 노트북 → 211.x.x.x:3389 (RDP)
공유기: "3389? NAT 테이블에 없음. 집 안 기기 중 누구 거야?" → 버림

    이게 집 PC가 “보이지 않는” 이유임. 방화벽 때문이 아니라 NAT 구조상 목적지를 알 수 없기 때문임(방화벽은 그 위에 한 겹 더).

    2.3 전통적 해법과 그 문제

    방법원리문제
    포트포워딩공유기에 “3389 오면 192.168.55.100으로” 규칙 추가전 세계에 3389가 열림. 봇이 24시간 비밀번호 대입함. 공인 IP가 바뀌면 DDNS도 필요
    직접 VPN 서버(OpenVPN, WireGuard)집에 VPN 서버를 세우고 그 포트만 포워딩포워딩은 여전히 필요. 키 배포·IP 변경·NAT 종류 대응을 직접 해야 함
    TeamViewer/AnyDesk 류회사 서버가 항상 중계화면 공유 전용. 트래픽이 회사 서버를 지나고 임의 프로토콜(SSH 등)엔 못 씀

    Tailscale은 두 번째(WireGuard)를 쓰되, 그 귀찮은 부분 — 키 배포, 주소 찾기, NAT 뚫기 — 를 자동화한 것임.

    🔷 3. Tailscale이란

    WireGuard 기반 메시(mesh) VPN 서비스. 같은 계정으로 로그인한 기기들이 서로 직접 연결되어 하나의 사설망(tailnet)을 이룸.

    구성요소역할
    tailscaled (각 기기의 데몬)WireGuard 터널 관리, NAT 통과, 가상 네트워크 어댑터 운영
    조정 서버 (control plane, login.tailscale.com)로그인 처리, 기기 목록·공개키·엔드포인트 배포, ACL 정책. 트래픽은 안 지나감
    DERP 서버STUN 서버 + 직접 연결 실패 시 릴레이. 전 세계 분산(도쿄, 홍콩, …)
    관리 콘솔기기 관리, 키 만료, ACL, 공유

    몇 가지 특징:

    • 주소: 기기마다 100.64.0.0/10 대역(RFC 6598, CGNAT 대역 — 일반 사설망과 충돌 안 나게 고른 것)에서 하나씩. 예: 100.101.1.1. 기기가 어디로 이동해도 이 주소는 고정임.
    • MagicDNS: 기기이름.tailnet이름.ts.net 형태 이름이 자동으로 붙음. IP 안 외워도 됨.
    • 인증: Tailscale이 비밀번호를 직접 갖지 않고 Google/Microsoft/GitHub 같은 기존 IdP에 위임함.
    • 기본 정책: 같은 tailnet 안 기기끼리는 전부 통신 허용. ACL로 좁힐 수 있음.
    • 오픈소스: 클라이언트는 공개(BSD). 조정 서버는 비공개지만 호환 구현 Headscale이 있음. 무료 플랜(Personal)은 사용자 6명·기기 무제한이라 개인 용도엔 충분함.

    🔷 4. 사용법

    4.1 서버 쪽 (접속당할 PC, Windows)

    # 1. 설치 (관리자)
winget install --id Tailscale.Tailscale -e

# 2. 로그인 — 브라우저가 열리고 Google 계정 등으로 로그인
tailscale up

# 3. 확인
tailscale status          # 내 IP, 같은 tailnet의 다른 기기 목록
tailscale ip -4           # 내 Tailscale IPv4
tailscale netcheck        # NAT 종류, 가장 가까운 DERP, 지연시간

    접속당할 서비스는 따로 켜야 함. Tailscale은 길만 놓아 줌:

    # 원격 데스크톱 (RDP, 3389) — 설정 > 시스템 > 원격 데스크톱 켜기와 동일
Set-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Terminal Server' -Name fDenyTSConnections -Value 0
Set-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp' -Name UserAuthentication -Value 1  # NLA 강제

# SSH 서버 (OpenSSH, 22)
Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Set-Service sshd -StartupType Automatic; Start-Service sshd

    Tailscale SSH(Tailscale이 SSH 서버 역할까지 하는 기능)는 Linux/macOS 전용이라 Windows에서는 OpenSSH를 따로 켜야 함.

    4.2 클라이언트 쪽 (접속하는 노트북/폰)

    1. Tailscale 설치 후 같은 계정으로 로그인 → 자동으로 같은 tailnet에 들어옴
    2. tailscale status에 집 PC가 보이면 끝
    3. 접속:
    ssh user@100.101.1.1                      # 또는 ssh user@my-desktop.tailxxxx.ts.net
mstsc /v:100.101.1.1                      # Windows 원격 데스크톱
tailscale ping 100.101.1.1                # 직접 연결인지 릴레이인지 확인

    tailscale ping 출력 예:

    pong from my-desktop (100.101.1.1) via DERP(tok) in 52ms     ← 아직 릴레이
pong from my-desktop (100.101.1.1) via 211.x.x.x:56926 in 8ms  ← 홀펀칭 성공, 직접 연결로 전환

    첫 패킷은 DERP로 보내고, 뒤에서 홀펀칭을 시도해 성공하면 직접 연결로 갈아탐. 그래서 접속은 항상 즉시 되고, 몇 초 뒤 빨라짐.

    4.3 계정이 두 개인 점 주의

    무엇어디에 씀
    Tailscale 로그인 계정 (Google 등)기기를 tailnet에 넣을 때. 한 번만
    Windows 사용자 계정 + 비밀번호RDP/SSH 로그인할 때 매번. Microsoft 계정이면 PIN이 아니라 MS 계정 비밀번호

    Tailscale은 “누구 PC인지"만 보증하고, 그 PC에 로그인하는 건 여전히 OS 몫임.

    4.4 자주 쓰는 명령

    명령뜻
    tailscale up / down연결 / 끊기 (설정은 유지)
    tailscale status기기 목록, 각 기기와의 연결 방식(direct/relay)
    tailscale netcheck내 NAT 환경 진단
    tailscale ping <ip>경로 확인
    tailscale logout이 기기를 tailnet에서 제거

    🔷 5. 원리 1 — WireGuard: 터널의 정체

    Tailscale이 실제로 패킷을 나르는 건 WireGuard임. Linux 커널에 포함된 VPN 프로토콜로, 설계가 극단적으로 단순함(코어 약 4,000줄. OpenVPN은 10만 줄대).

    5.1 키쌍이 곧 신원

    WireGuard에는 사용자 이름·비밀번호·인증서가 없음. 기기마다 Curve25519 키쌍 하나가 전부임.

    • 비밀키: 기기 밖으로 절대 안 나감
    • 공개키: 상대에게 알려 줌 = “나한테 보낼 땐 이 키로 암호화해”

    SSH 공개키 인증과 같은 발상임. Tailscale은 이 공개키를 조정 서버를 통해 같은 tailnet 기기끼리 자동 배포함 — 사람이 wg0.conf에 손으로 붙여 넣던 일을 대신하는 것임.

    5.2 Cryptokey Routing

    WireGuard의 핵심 아이디어. “공개키 ↔ 허용 IP” 표 하나로 라우팅과 인증을 동시에 해결함.

    peer 공개키AllowedIPs
    노트북 공개키100.101.1.2/32
    폰 공개키100.101.1.3/32
    • 보낼 때: 목적지 IP가 100.101.1.2면 → 표에서 그 IP를 가진 peer의 공개키로 암호화해서 보냄
    • 받을 때: 복호화가 노트북 공개키로 성공했고, 안에 든 패킷의 출발지가 100.101.1.2면 통과. 아니면 버림

    즉 “100.101.1.2에서 왔다"는 주장과 “노트북 비밀키를 가졌다"는 증명이 같은 것이 됨. IP 스푸핑이 원천적으로 불가능함.

    5.3 가상 네트워크 어댑터

    OS 입장에서 Tailscale은 네트워크 카드 하나로 보임(Windows: “Tailscale Tunnel”, Linux: tailscale0). 라우팅 테이블에 “100.64.0.0/10은 이 어댑터로"가 등록되어 있음.

    앱: connect(100.101.1.1:3389)
 → OS 라우팅: 100.x → Tailscale 어댑터
 → tailscaled: Cryptokey routing → 상대 공개키로 암호화(ChaCha20-Poly1305)
 → UDP 패킷으로 감싸서 실제 이더넷 어댑터로 송신
 → 상대 tailscaled: 복호화 → 상대 OS의 Tailscale 어댑터에서 "패킷 도착"
 → 상대 앱(RDP 서버, 3389)

    앱은 자기가 VPN 위에 있다는 걸 모름. 그래서 RDP, SSH, 파일 공유, 게임 뭐든 그냥 됨.

    5.4 왜 UDP인가

    WireGuard는 UDP만 씀. 이유 두 가지:

    1. 안에 든 게 TCP면 TCP-over-TCP 문제(바깥 TCP와 안쪽 TCP가 서로 재전송해서 성능 붕괴)를 피해야 함
    2. UDP는 연결 상태가 없어서 뒤에 나오는 홀펀칭이 훨씬 쉬움

    5.5 로밍

    WireGuard peer는 상대의 “현재 주소"를 마지막으로 유효한 패킷이 온 곳으로 갱신함. 노트북이 와이파이에서 LTE로 바뀌어 공인 IP가 달라져도, 다음 패킷이 새 주소에서 오면 그냥 그리로 답함. 연결이 안 끊기는 이유임.

    🔷 6. 원리 2 — 조정 서버: 전화번호부

    WireGuard를 손으로 쓸 때 제일 귀찮은 게 “상대 공개키와 현재 IP:포트를 어떻게 아는가"임. 조정 서버가 그걸 대신함.

    sequenceDiagram
    participant PC as 집 PC
    participant CS as 조정 서버
    participant LT as 노트북
    PC->>CS: 로그인(Google OAuth), 내 WireGuard 공개키, 내 엔드포인트 후보들
    LT->>CS: 로그인(같은 계정), 내 공개키, 내 엔드포인트 후보들
    CS-->>PC: netmap: {노트북: 공개키, 100.101.1.2, 엔드포인트 후보, DERP 홈}
    CS-->>LT: netmap: {집 PC: 공개키, 100.101.1.1, 엔드포인트 후보, DERP 홈}
    Note over PC,LT: 이제 서로 알고 있음 → 직접 WireGuard 핸드셰이크
    • 조정 서버가 아는 것: 계정, 기기 목록, 공개키, 각 기기가 “나 밖에서 보면 211.x.x.x:56926이야"라고 보고한 주소들
    • 조정 서버가 모르는 것: 비밀키, 트래픽 내용. 조정 서버가 뚫려도 기존 터널은 못 엿봄(새 기기를 몰래 끼워 넣는 건 가능하므로 Tailscale은 이걸 막는 tailnet lock 기능을 따로 둠)
    • 조정 서버 연결이 잠깐 끊겨도 이미 받은 netmap으로 P2P는 계속 동작함

    🔷 7. 원리 3 — NAT 통과: 어떻게 양쪽 공유기를 뚫는가

    여기가 핵심. 2절에서 “공유기는 안에서 먼저 나간 연결의 답장만 넣어 줌"이라고 했음. 그러면 양쪽 다 먼저 나간 것처럼 만들면 됨.

    7.1 STUN — 내가 밖에서 어떻게 보이는지 알아내기

    PC는 자기 공인 주소를 모름(자기 눈엔 192.168.55.100). STUN(RFC 5389) 서버에 UDP 패킷을 하나 보내면, 서버가 “네가 온 주소는 211.x.x.x:56926이야"라고 답해 줌. Tailscale은 DERP 서버들이 STUN 역할도 겸함.

    tailscale netcheck 결과가 바로 이것임:

    * UDP: true
* IPv4: yes, 211.x.x.x:56926          ← STUN이 알려준 내 공인 주소:포트
* MappingVariesByDestIP: false        ← 목적지가 달라도 같은 포트로 매핑됨 = "쉬운 NAT"
* Nearest DERP: Tokyo (49.5ms)

    7.2 홀펀칭 — 동시에 서로에게 쏘기

    양쪽이 조정 서버를 통해 서로의 공인 주소:포트를 알게 됐음. 이제 동시에 상대 주소로 UDP를 보냄.

    sequenceDiagram
    participant PC as 집 PC<br/>192.168.55.100
    participant A as 공유기 A<br/>211.x.x.x
    participant B as 공유기 B<br/>58.x.x.x
    participant LT as 노트북<br/>10.0.0.7
    PC->>A: UDP → 58.x.x.x:40001
    Note over A: NAT 테이블 기록:<br/>56926 ↔ PC, 상대 58.x.x.x:40001<br/>"이제 거기서 오는 건 PC 거"
    A--xB: 첫 패킷은 B가 버림 (B 테이블에 아직 없음)
    LT->>B: UDP → 211.x.x.x:56926
    Note over B: NAT 테이블 기록:<br/>40001 ↔ LT, 상대 211.x.x.x:56926
    B->>A: 도착
    Note over A: 테이블에 있음 → PC로 전달 ✅
    A->>PC: 
    PC->>A: 재전송
    A->>B: 이번엔 B 테이블에도 있음 → LT로 전달 ✅
    B->>LT: 
    Note over PC,LT: 양쪽 구멍 뚫림 → WireGuard 핸드셰이크 → P2P 완성

    각 공유기는 자기 쪽 기기가 “먼저 나갔다"고 믿음. 실제로는 양쪽이 동시에 나간 것임. 이후 패킷은 조정 서버도 릴레이도 안 거치고 두 공유기 사이를 직접 오감.

    7.3 NAT의 종류 — 왜 가끔 안 뚫리는가

    공유기가 NAT 테이블을 어떻게 만드느냐에 따라 난이도가 갈림(RFC 4787 용어).

    NAT 유형동작홀펀칭
    Endpoint-Independent Mapping (“쉬운 NAT”, 대부분 가정용 공유기)내부 PC:51000은 목적지가 누구든 항상 56926으로 나감✅ STUN이 알려준 포트를 그대로 쓰면 됨
    Endpoint-Dependent Mapping (“어려운 NAT”, 대칭형 NAT. 일부 기업망·통신사 CGNAT)목적지마다 다른 포트를 배정. STUN 서버에게 보인 포트 ≠ 노트북에게 보일 포트⚠️ 포트를 추측해야 함

    MappingVariesByDestIP: false가 쉬운 NAT라는 뜻임. 어려운 NAT를 만나면 Tailscale은:

    1. 한쪽만 어려우면: 쉬운 쪽이 여러 포트를 열어 두고, 어려운 쪽이 그중 하나를 맞히기를 기다림
    2. 양쪽 다 어려우면: 이른바 생일 공격 — 양쪽이 수백 개의 랜덤 포트를 동시에 쏴서 하나라도 겹치길 노림(생일 역설 덕에 256개 정도면 확률이 꽤 높음)
    3. UPnP / NAT-PMP / PCP로 공유기에 “포트 하나만 열어 줘"라고 정식 요청(공유기가 지원할 때)
    4. 그래도 안 되면 DERP

    7.4 DERP — 최후의 릴레이

    Designated Encrypted Relay for Packets. Tailscale이 전 세계에 둔 중계 서버. 각 기기는 가장 가까운 DERP(한국이면 도쿄)에 HTTPS(443) 아웃바운드로 항상 붙어 있음.

    • 443 아웃바운드는 어떤 방화벽도 막지 않으므로 항상 됨
    • 릴레이는 WireGuard 패킷을 그대로 넘길 뿐, 키가 없어 내용을 못 봄
    • 왕복이 도쿄를 거치니 느림(위 예: 직접 8ms vs DERP 52ms). 그래서 DERP로 먼저 연결해 두고 뒤에서 홀펀칭을 계속 시도함

    즉 사용자 입장에선 “접속은 무조건 되고, 대부분은 빠름"이 됨.

    🔷 8. 패킷 한 개의 여행 — RDP 클릭 한 번이 지나는 길

    카페 노트북에서 원격 데스크톱 창을 클릭했을 때, 그 마우스 이벤트가 집 PC까지 가는 경로를 OSI 계층 으로 보면 터널이 어디에 끼는지 보임.

    단계계층내용
    1L7RDP 프로토콜: “좌표 (412, 300) 클릭”
    2L4TCP, 목적지 포트 3389
    3L3IP: 100.101.1.2 → 100.101.1.1 — Tailscale 가상 어댑터로 라우팅
    4—tailscaled: 집 PC 공개키로 암호화(ChaCha20-Poly1305) → WireGuard 패킷
    5L4이걸 다시 UDP에 담음. 목적지 211.x.x.x:56926 (홀펀칭으로 뚫어 둔 구멍)
    6L3IP: 10.0.0.7 → 211.x.x.x. 카페 공유기가 NAT → 58.x.x.x:40001 → 211.x.x.x
    7L2/L1와이파이 → 카페 공유기 → 인터넷 → 집 공유기
    8L3집 공유기: NAT 테이블 조회 → 192.168.55.100으로 전달
    9—집 PC tailscaled: 복호화 → 원래 IP 패킷(3단계) 복원 → Tailscale 어댑터에 투입
    10L4/L7Windows: 3389 포트 → 원격 데스크톱 서비스 → 마우스 클릭 발생

    IP 패킷 안에 IP 패킷이 들어 있는 구조(3단계가 5~6단계 안에 캡슐화됨). 안쪽 주소는 tailnet 주소, 바깥 주소는 실제 인터넷 주소. 이게 “터널"이라는 말의 정확한 의미임.

    🔷 9. 보안 — 무엇이 열리고 무엇이 안 열리는가

    항목상태
    공인 IP로 직접 접속❌ 불가. 포트포워딩 없음. 인터넷에서 포트 스캔해도 아무것도 안 보임
    tailnet 밖 기기에서 100.101.1.1 접속❌ 불가. 그 주소는 tailnet 안에서만 존재
    tailnet 안 기기✅ 기본 ACL은 전부 허용. 필요하면 관리 콘솔에서 “노트북만 PC의 3389·22 허용"으로 좁힘
    전송 암호화WireGuard (Curve25519 키 교환, ChaCha20-Poly1305, BLAKE2s). 릴레이 포함 전 구간
    Tailscale 계정 탈취 시공격자가 자기 기기를 tailnet에 추가할 수 있음 → IdP 계정 2단계 인증 필수. tailnet lock을 켜면 기존 기기의 서명 없이는 새 기기가 못 들어옴
    키 만료기기 키는 기본 180일 후 재로그인 요구. 서버용 PC는 콘솔에서 만료 해제 가능
    Windows 방화벽 프로필Tailscale 어댑터는 Private, 이더넷은 Public으로 잡히므로 “Private 전용” 방화벽 규칙(OpenSSH 기본값)은 자연히 Tailscale 경유로만 열림
    RDP 자체NLA(네트워크 수준 인증) 켜서 로그인 전 화면 노출 차단. 그래도 OS 계정 비밀번호가 최종 관문

    정리하면 공격면이 “인터넷 전체"에서 “내 Tailscale 계정에 로그인한 기기"로 줄어듦. 그 계정을 지키는 게 곧 PC를 지키는 것임.

    🔷 10. Q&A

    Q. VPN이라는데 인터넷 트래픽이 전부 Tailscale을 지나는 건가? 아님. 기본은 100.64.0.0/10 대역만 터널로 감(split tunnel). 유튜브는 평소처럼 감. 원하면 한 기기를 exit node로 지정해 전체 트래픽을 그리로 보낼 수 있음(해외에서 한국 IP 쓰기 등).

    Q. 집 공유기가 이중 NAT(통신사 CGNAT + 내 공유기)면? 그래도 됨. NAT가 몇 겹이든 “안에서 밖으로"는 되니 STUN·홀펀칭·DERP 모두 동작함. 통신사 CGNAT가 대칭형이면 직접 연결 확률이 낮아져 DERP 비중이 늘 뿐임.

    Q. 조정 서버(Tailscale 회사)가 죽으면? 이미 연결된 기기끼리는 계속 통신함(netmap 캐시). 새 기기 추가·키 교체만 안 됨. 회사 자체를 못 믿겠으면 Headscale로 조정 서버를 직접 운영할 수 있음.

    Q. WireGuard를 그냥 직접 쓰면 안 되나? 됨. 다만 (1) 집 공유기에 UDP 포트 하나 포워딩, (2) DDNS, (3) 기기마다 키를 손으로 교환, (4) 폰이 LTE↔와이파이 오갈 때 엔드포인트 갱신 — 을 직접 해야 함. Tailscale은 이 네 가지를 없앤 것임.

    Q. 폰 데이터로도 되나? 됨. 폰이 어떤 NAT 뒤에 있든 상관없음. 홀펀칭이 실패하면 DERP로 감.

    Q. PC가 꺼져 있으면? 안 됨. Tailscale은 네트워크만 담당. 전원 연결 시 절전을 끄거나, 다른 기기가 Wake-on-LAN 매직 패킷을 같은 LAN에서 쏴 줘야 함.

    Q. 100.x.x.x가 왜 사설 IP 대역(10., 172.16., 192.168.)이 아닌가? 그 대역은 집·회사 LAN이 이미 쓰고 있어 충돌 위험이 큼. 100.64.0.0/10은 통신사 내부용(CGNAT, RFC 6598)이라 개인 LAN에서 쓸 일이 거의 없어 골랐음.

    🔷 11. 한 줄 요약

    밖에서 안으로 못 들어오니, 양쪽이 동시에 밖으로 나가 중간에서 만나고(홀펀칭), 그 위에 키쌍 기반 암호화 터널(WireGuard)을 깔아 같은 LAN처럼 쓰는 것. 실패하면 릴레이(DERP). 주소록 관리는 조정 서버가.
