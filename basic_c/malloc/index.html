malloc

malloc

C의 동적 메모리 할당 함수. 결론부터: heap에서 크기만큼 빌리고, void*를 돌려주니 형변환해서 쓰고, 다 쓰면 반드시 free()로 직접 반납해야 하는 함수다. 반납을 잊거나, 두 번 반납하거나, 반납 후에도 계속 쓰면 이 문서 3장의 버그들이 그대로 터진다.

heap 영역 자체의 특성(스택과의 속도/크기 차이, 단편화)은 Memory_Layout , Fragmentation 참고. C++의 new와의 비교는 New_malloc 참고.

1. 기본 사용

malloc(size)은 heap 영역에서 size 바이트만큼 메모리를 할당하고, 그 블록의 첫 번째 바이트 주소를 반환한다.

#include <stdlib.h>

int *p = (int *)malloc(sizeof(int));    // int 1개 크기만큼 heap에서 할당
*p = 42;
free(p);
  • 반환 타입은 void* — 아무 타입도 아닌 포인터이므로 원하는 타입으로 형변환해서 받는다
    • C는 void* → 다른 포인터로의 암시적 변환을 허용해서 캐스팅 없이도 대입 가능(int *p = malloc(...)), 하지만 C++에서는 금지되어 있어 명시적 캐스팅이 필수다
  • 실패 시 NULL을 반환한다 (예외를 던지지 않음). 실전 코드는 반드시 체크한다:
int *p = (int *)malloc(sizeof(int) * n);
if (p == NULL) {
    // 할당 실패 처리 — 메모리 부족 등
}
  • 배열 할당은 sizeof(T) * count로 크기를 직접 계산해서 넘긴다:
int *arr = (int *)malloc(sizeof(int) * 5);
for (int i = 0; i < 5; i++)
    arr[i] = i + 1;             // arr[i] == *(arr + i)
free(arr);

1-1. int a = ... vs int *a = ... — *를 빠뜨리는 실수

int a = (int *)malloc(sizeof(int));    // ❌ 타입 불일치
int *a = (int *)malloc(sizeof(int));   // ✅ 올바른 선언
  • malloc은 항상 주소값(포인터)을 반환한다. 그 주소를 담을 변수는 반드시 포인터 타입(int *)이어야 한다
  • 첫 번째 줄은 a를 포인터가 아닌 평범한 int 로 선언해놓고 주소값을 대입하는 코드다. 결과는 아키텍처의 데이터 모델에 따라 다르다:
    • 64bit(LP64/LLP64): 포인터는 8바이트, int는 4바이트 → 대입 시 상위 32비트가 잘려나가 원래 주소와 다른 값이 된다. 이후 그 값을 다시 포인터로 캐스팅해서 역참조하면 엉뚱한 주소를 건드려 크래시하거나 데이터를 오염시킨다
    • 32bit(ILP32): 포인터도 int도 둘 다 4바이트라 숫자값 자체는 잘리지 않고 보존된다. (int *)(long)a처럼 다시 포인터로 되돌리면 원래 주소와 같은 값이 나온다는 뜻 — 그래서 32bit 환경에서 짠 이런 코드가 “우연히 동작"하는 것처럼 보인다
    • 하지만 32bit이라 값이 안 잘린다는 사실이 이 코드를 안전하게 만들어주진 않는다: 여전히 타입이 틀렸다는 사실 자체가 버그이고(컴파일러 경고, 정적 분석 실패, 코드 리뷰에서 지적됨), 무엇보다 64bit로 옮기는 순간 조용히 깨지는 이식성 문제로 남는다
    • C에서는 이 대입에 대해 컴파일러가 assignment makes integer from pointer without a cast 경고를 낸다 (32bit/64bit 무관하게 — 타입 불일치 자체를 지적하는 것이지 크기가 맞고 안 맞고의 문제가 아니다)
    • C++에서는 애초에 포인터 → int 암시적 변환이 없어 컴파일 에러
    • 포인터를 정수로 정말 담아야 하는 상황(포인터 산술, 디버그 출력 등)이라면 크기가 항상 딱 맞는 intptr_t/uintptr_t(<stdint.h>)를 쓰는 것이 아키텍처 독립적인 정석이다
  • 두 번째 줄에서 int *a의 *는 “a는 int를 가리키는 포인터"라는 뜻이다. int a와 int *a는 완전히 다른 타입(값 vs 주소)이므로, malloc의 반환값을 받는 변수는 항상 *가 붙어야 한다는 점을 기계적으로 기억해두는 게 안전하다
  • 만약 a가 진짜 int여야 했다면(가리키는 값을 바로 쓰고 싶었다면) int a = *(int *)malloc(sizeof(int));처럼 역참조까지 해야 값이 나온다 — 다만 이 경우 할당받은 주소를 어디에도 저장하지 않으므로 free() 할 방법이 사라져 즉시 메모리 누수가 된다 (3-1장 참고)

1-2. malloc 반환값 캐스팅 — C의 암묵적 변환 허용 vs C++의 금지

void *p = malloc(sizeof(int));
int  *q = malloc(sizeof(int));         // C: 캐스팅 없이 OK — C 관용 스타일에서는 이쪽을 권장
int  *r = (int *)malloc(sizeof(int));  // C에서도 문법적으로는 되지만, 캐스팅이 불필요

int *q = malloc(sizeof(int));          // ❌ C++: 컴파일 에러
int *r = (int *)malloc(sizeof(int));   // ✅ C++: 캐스팅 필수

C — void*는 어떤 객체 포인터 타입으로도 암묵적 변환된다.

  • C 표준은 void* ↔ 다른 포인터 타입 간 암묵적 변환을 허용한다. 따라서 int *q = malloc(...)는 그 자체로 완전히 합법이며, 정보 손실도 없다 (포인터 타입끼리의 변환이지 크기가 다른 타입 간 변환이 아니다)
  • K&R, comp.lang.c FAQ 등 전통적인 C 스타일 가이드는 오히려 “캐스팅하지 말라"고 권장한다. 이유는 캐스팅 자체의 위험보다는, 캐스팅이 진짜 버그를 가려버리기 때문이다:
// #include <stdlib.h> 를 깜빡 빠뜨렸다고 가정
int *p = (int *)malloc(sizeof(int) * n);   // 캐스팅 있음 — 경고 없이 조용히 통과할 수 있음
int *q = malloc(sizeof(int) * n);          // 캐스팅 없음 — "incompatible pointer" 류의 경고 발생
  • 오래된 C(C89) 컴파일러는 선언되지 않은 함수를 만나면 반환 타입을 int로 암묵적으로 가정한다. stdlib.h를 빠뜨리면 malloc이 int를 반환하는 것으로 취급된다
  • 이때 캐스팅이 없으면 int → int* 대입이 타입 불일치로 감지되어 컴파일러가 경고를 낸다 — 빠진 include를 즉시 알아챌 수 있다
  • 반대로 캐스팅이 있으면 (int *)라는 명시적 지시 때문에 컴파일러가 “일부러 변환하는구나” 판단하고 경고를 억제해버린다. 결과적으로 malloc이 실제로는 int(4바이트)로 취급되어 반환값이 잘리는데도 아무 경고 없이 통과한다 — 1-1장에서 다룬 “64bit에서 포인터가 잘리는 문제"가 캐스팅 때문에 소리 없이 발생하는 셈이다
  • 즉 C에서 malloc 캐스팅을 생략하는 것은 “혹시 모를 실수를 컴파일러 경고로 잡아내겠다"는 방어적 스타일이다. 최신 C(C99 이후 암묵적 int 반환 금지, 그리고 -Wall/-Werror 빌드)에서는 이 문제의 실효성이 예전만큼 크지 않지만, 관용적으로 여전히 통용된다

C++ — void*의 암묵적 변환 자체가 없다.

  • C++의 타입 시스템은 C보다 엄격하며, void* → T*의 암묵적 변환을 아예 허용하지 않는다. 캐스팅 여부로 실수를 가려낼 여지 자체가 없으므로, 캐스팅은 선택이 아니라 필수다
  • 대신 C++은 애초에 이 논쟁이 무의미해지는 방향으로 설계되어 있다 — new는 타입이 있는 포인터를 바로 반환하므로 캐스팅도, 암묵적 변환 논쟁도 필요 없다 (New_malloc 참고). 실전 C++ 코드가 malloc 대신 new/스마트 포인터를 쓰는 이유 중 하나이기도 하다
CC++
void* → T* 암묵적 변환허용금지
malloc 캐스팅불필요 (전통적으로 생략 권장)필수
캐스팅 생략 시 이점빠진 include, 타입 불일치를 경고로 감지해당 없음 — 애초에 컴파일 안 됨

2. calloc / realloc — malloc의 두 형제

함수시그니처차이점
malloc(size)크기만 지정내용을 초기화하지 않는다 — 쓰레기 값이 들어있음
calloc(n, size)개수 × 원소 크기0으로 초기화해서 반환. n * size 오버플로도 내부적으로 체크
realloc(ptr, new_size)기존 포인터 + 새 크기기존 내용을 보존하며 크기 조절 (필요하면 새 위치로 이동)
int *a = calloc(5, sizeof(int));    // {0, 0, 0, 0, 0} — malloc(5*sizeof(int))과 달리 미초기화 쓰레기 없음

int *b = malloc(5 * sizeof(int));
b = realloc(b, 10 * sizeof(int));   // 앞 5개 값 유지, 뒤 5개는 미초기화

realloc의 함정 — 반환값을 원래 포인터에 바로 덮어쓰지 말 것:

int *p = malloc(100);
p = realloc(p, 200);        // ❌ realloc이 NULL을 반환하면 원래 p 주소를 잃어버려 leak

int *tmp = realloc(p, 200); // ✅ 임시 변수로 받아 성공 여부 확인 후 교체
if (tmp) p = tmp;
  • realloc이 실패하면 원래 블록은 그대로 유효한 채 NULL만 반환한다. 반환값을 바로 p에 덮으면 실패 시 원래 주소를 잃어 그 블록을 영영 해제할 수 없게 된다(누수 확정)

3. 흔한 버그 3종

3-1. 메모리 누수 (Memory Leak)

free()를 안 하면 그 블록은 프로세스가 끝날 때까지 회수되지 않는다.

void handler(void) {
    char *buf = malloc(4096);
    return;        // free 없이 리턴 — buf를 아는 유일한 변수가 사라짐 → 누수 확정
}

포인터를 잃어버리는 순간(덮어쓰기, 스코프 탈출) 그 블록을 해제할 방법 자체가 사라진다 — heap 메모리는 이름이 없고 포인터가 유일한 접근 수단이기 때문.

3-2. Double Free

같은 포인터를 두 번 free()하면 undefined behavior. 할당자 내부 메타데이터(free list)가 깨져서 이후 malloc/free가 알 수 없는 방식으로 오작동하거나 크래시한다.

free(p);
free(p);   // ❌ UB — 최신 glibc는 대부분 감지해서 abort 시키지만, 항상 그런 건 아님

3-3. Dangling Pointer — free 후 계속 접근

int *p = malloc(sizeof(int));
*p = 42;
free(p);
printf("%d\n", *p);   // ❌ 이미 반납한 메모리를 읽음

이게 왜 위험한지, segfault를 넘어 보안 취약점까지 이어지는 경로는 Error_Pointer 문서에 자세히 정리되어 있다 (NULL pointer, wild pointer와의 구분 포함).

공통 대책:

  • free(p) 직후 p = NULL; — dangling 상태를 즉시 무효화 (NULL 역참조는 즉시 크래시라 오류를 조기에 드러낸다는 것이 핵심)
  • 하나의 블록을 여러 포인터가 가리킨다면, 마지막 소유자가 누구인지 명확히 관리 (C++이라면 Smart Pointer 로 이 문제 자체를 구조적으로 없앤다)

4. 내부적으로 무슨 일이 일어나나

  • malloc이 요청 크기를 그대로 주는 게 아니라 정해진 size class 단위로 반올림해서 지급한다 — 이 반올림 낭비가 내부 단편화다. glibc malloc(ptmalloc)의 청크 구조와 bin 분류, 이로 인한 단편화 패턴은 Fragmentation 2~3장 참고
  • 멀티스레드 환경에서 malloc은 내부적으로 lock을 잡는다. 이 lock은 fork() 직후 자식 프로세스에서 데드락을 유발할 수 있는 대표적 원인이다 — 자세한 사고 재현은 Fork 참고
