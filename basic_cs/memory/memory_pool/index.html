Memory Pool

Memory Pool (메모리 풀)

큰 메모리 블록을 미리 확보해두고, 고정 크기 슬롯으로 잘라서 빌려주고 돌려받는 커스텀 할당자. 단편화 의 실전 해법이자, 실시간/임베디드 시스템에서 malloc을 대체하는 정석 패턴이다.

1. 왜 필요한가 — malloc의 3가지 약점

일반 할당자(malloc/new)는 범용이라는 대가로 다음을 포기한다 (Memory_Layout 3-2 참고):

malloc의 약점결과
free list 탐색 — 실행 시간이 그때그때 다름실시간 시스템에서 WCET(최악 실행 시간) 보장 불가
할당/해제 반복 시 외부 단편화 누적장기 실행 기기에서 어느 날 갑자기 할당 실패
내부 lock — 멀티스레드 경합우선순위 역전, 지연 스파이크 (fork/lock 문제 의 그 lock)

메모리 풀은 이 셋을 전부 뒤집는다: O(1) 결정적 할당, 단편화 0, (스레드별 풀이면) lock 0.

2. 동작 원리 — 고정 슬롯 + free list

핵심 아이디어: 모든 슬롯이 같은 크기이므로 “맞는 블록 찾기"라는 문제 자체가 사라진다.

초기화: 큰 블록을 슬롯 N개로 자르고, 빈 슬롯끼리 리스트로 엮음

 free_head → [슬롯0] → [슬롯1] → [슬롯2] → [슬롯3] → NULL
              (빈 슬롯 자체의 앞부분을 next 포인터로 재활용 — 별도 메타데이터 0)

할당: free_head에서 하나 뽑기        해제: 리스트 앞에 도로 끼우기
 free_head → [슬롯1] → ...           free_head → [슬롯0] → [슬롯1] → ...
 (반환: 슬롯0)                        (포인터 조작 2회 — O(1))
  • 할당 = 리스트 head 뽑기, 해제 = head에 끼우기 — 둘 다 포인터 몇 번 조작으로 끝 (O(1), 탐색 없음)
  • 빈 슬롯의 메모리 앞부분을 next 포인터로 쓰므로 관리 오버헤드도 사실상 0
  • 같은 크기만 오가므로 외부 단편화 가 원리적으로 발생 불가

최소 구현 예제

typedef struct Pool {
    void  *free_head;
    size_t slot_size;          // 최소 sizeof(void*) 이상
} Pool;

void pool_init(Pool *p, void *buf, size_t slot_size, size_t nslots) {
    p->slot_size = slot_size;
    p->free_head = buf;
    char *c = buf;                             // 슬롯들을 리스트로 엮기
    for (size_t i = 0; i < nslots - 1; i++)
        *(void **)(c + i * slot_size) = c + (i + 1) * slot_size;
    *(void **)(c + (nslots - 1) * slot_size) = NULL;
}

void *pool_alloc(Pool *p) {
    void *slot = p->free_head;
    if (slot) p->free_head = *(void **)slot;   // head 하나 뽑기
    return slot;                               // 고갈 시 NULL
}

void pool_free(Pool *p, void *slot) {
    *(void **)slot = p->free_head;             // head 앞에 끼우기
    p->free_head = slot;
}
// 사용: 정적 버퍼 위에 풀 구성 — heap을 아예 안 거침 (.bss에 잡힘)
static char buf[64 * 256];                     // 64B 슬롯 × 256개
static Pool pkt_pool;
pool_init(&pkt_pool, buf, 64, 256);

void *pkt = pool_alloc(&pkt_pool);
/* ... */
pool_free(&pkt_pool, pkt);

3. 대가 — 무엇을 포기하는가

제약설명 / 대응
고정 크기슬롯보다 작은 요청은 내부 단편화 (슬롯 안 낭비), 큰 요청은 불가 → 크기별 풀 여러 개 운용 (64B/256B/1KB 풀 등 — glibc의 size class, 커널 slab과 같은 발상)
용량 고정풀 고갈 시 정책을 설계 시점에 정해야 함: ① 실패 반환(호출자가 처리) ② 빈 슬롯 날 때까지 대기 ③ malloc으로 fallback ④ 풀 확장. 하드 RT는 보통 ① + 충분한 사전 산정
범용성 없음어떤 크기가 얼마나 필요한지 미리 알아야 설계 가능 — 반대로 말하면, 그걸 아는 시스템(임베디드)에서는 단점이 아님

5. 실전 사례

  • RTOS: FreeRTOS의 고정 블록 힙(heap_4의 병합 힙과 별개로, 큐/태스크용 정적 할당 xQueueCreateStatic 등), 메시지 큐 버퍼 — 실시간성 보장의 기본기
  • 네트워크 스택: 패킷 버퍼 풀 (리눅스 커널 sk_buff도 slab 캐시로 관리) — 초당 수십만 번 할당/해제되는 고정 크기 객체의 전형
  • 커널 slab allocator: “같은 크기 객체 전용 캐시"라는 점에서 메모리 풀과 같은 아이디어의 커널 버전 (Linux Memory 4장의 SLUB)
  • 게임 엔진: 프레임마다 쓰고 버리는 임시 데이터를 arena(선형) 할당자로 — 프레임 끝에 포인터 하나 리셋으로 전체 해제
  • 안전 규격 코딩(항공 DO-178C, 차량 MISRA): 런타임 동적 할당 금지 → 시작 시 풀 구성만 허용

6. C++ 표준 도구 — std::pmr (C++17)

직접 구현하지 않아도 표준 라이브러리에 풀/아레나 할당자가 있다. std::pmr 컨테이너는 할당자를 런타임에 꽂을 수 있는 버전이다.

#include <memory_resource>

// 1. 아레나(선형) — 버퍼에서 순서대로 잘라주기만 하고, 소멸 시 통째로 해제
char buf[64 * 1024];
std::pmr::monotonic_buffer_resource arena(buf, sizeof(buf));
std::pmr::vector<int> v(&arena);           // v의 모든 할당이 buf 안에서 해결됨

// 2. 풀 — 크기별 풀들을 자동 운용
std::pmr::unsynchronized_pool_resource pool;   // 단일 스레드용 (lock 없음)
std::pmr::list<Packet> packets(&pool);         // 노드 할당이 풀에서 나옴
  • monotonic_buffer_resource: 해제가 아예 없는 대신 가장 빠름 — “한 프레임/한 요청 처리하고 통째로 버리는” 패턴에 최적
  • (un)synchronized_pool_resource: 크기별 풀 자동 관리. unsynchronized는 lock이 없어 빠른 대신 단일 스레드 전용
  • list/map처럼 노드 단위 할당이 잦은 컨테이너에서 효과가 크다

7. 요약

  • 메모리 풀 = 고정 크기 슬롯 + free list → 할당/해제 O(1), 결정적 시간, 외부 단편화 0
  • malloc의 비결정성·단편화·lock이 허용되지 않는 곳(실시간, 장기 실행 임베디드, 고빈도 할당 경로)의 표준 해법
  • 대가는 유연성 — 크기·용량을 미리 알고 설계해야 하며, 고갈 정책도 설계의 일부
  • C++이면 직접 짜기 전에 std::pmr 먼저 검토
