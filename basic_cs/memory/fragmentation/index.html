Memory Fragmentation (메모리 단편화)

할당과 해제를 반복하다 보면 메모리가 조각나서, 총 여유 공간은 충분한데 정작 원하는 할당은 실패하는 상태가 된다. Memory_Layout 의 heap 대가 중 하나이며, 장기 실행하는 임베디드/서버 시스템에서 특히 치명적이다.

1. 외부 단편화 (External Fragmentation)

할당된 블록들 “사이"에 생기는 자잘한 구멍 때문에, 여유 총량은 충분해도 연속된 큰 블록이 없는 상태.

초기:     [________________ 여유 100KB ________________]

할당:     [ A 20K ][ B 20K ][ C 20K ][ D 20K ][ 여유 20K ]

B, D 해제: [ A 20K ][빈 20K ][ C 20K ][빈 20K ][ 여유 20K ]

malloc(50K) → 실패!  (여유 총합 60KB지만 연속 공간은 최대 20KB)
  • 원인: 해제 순서가 할당 순서와 다르기 때문. 수명이 제각각인 블록들이 섞이면 필연적으로 발생한다
  • 오래 돌수록 악화된다 — “일주일 돌리면 malloc이 실패하기 시작하는 장비"의 전형적 원인

2. 내부 단편화 (Internal Fragmentation)

할당된 블록 “안"에서 실제 쓰는 크기보다 크게 받아서 낭비되는 부분.

malloc(5) 요청 →  실제로는 16B 블록 지급
[ 5B 사용 |    11B 낭비 (블록 내부)    ]
  • 원인: 할당자는 관리 효율을 위해 정해진 크기 단위(size class)로 반올림해서 준다 (glibc malloc은 최소 청크 + 16B 정렬, 커널 buddy는 2^n 페이지 단위)
  • 구조체 멤버 정렬(padding)로 인한 낭비도 같은 부류다 — Structure_Optimize 참고
  • 외부 단편화와의 구분: 외부는 블록 사이의 낭비(합치면 쓸 수 있는데 흩어져 있음), 내부는 블록 안의 낭비(이미 지급되어 누구도 못 씀)
구분위치원인완화책
외부 단편화블록들 사이할당/해제 순서 뒤섞임병합, 압축, 페이징, 풀 할당
내부 단편화블록 내부고정 단위 반올림, 정렬size class 세분화, 구조체 패킹

3. 할당자(allocator)는 어떻게 싸우는가

3-1. Free list와 배치 전략

할당자는 해제된 블록들을 free list로 관리하고, 요청이 오면 배치 전략으로 고른다.

전략방식특성
First fit처음 만나는 충분한 블록빠름. 앞쪽에 자잘한 조각 누적
Best fit가장 딱 맞는 블록낭비 최소 같지만, 쓸모없이 작은 자투리를 양산
Next fit지난 위치부터 탐색조각을 전체에 고르게 퍼뜨림

어느 전략도 외부 단편화를 없애지는 못한다 — 완화 수단일 뿐이다.

3-2. 병합 (Coalescing)

해제 시 인접 블록이 이미 free면 하나로 합친다.

[ A ][빈 20K][ B 해제됨 20K ][ C ]
              ↓ 병합
[ A ][      빈 40K          ][ C ]

glibc malloc(ptmalloc)은 경계 태그(boundary tag)로 앞뒤 블록 상태를 확인해 즉시 병합하고, 크기별 bin(fastbin/smallbin/largebin)으로 free 블록을 분류해 탐색을 줄인다.

3-3. Buddy System — 커널의 방식

리눅스 커널은 페이지 프레임을 2^n 단위 “버디” 쌍으로 관리한다 (Linux Memory 4장).

  • 큰 블록을 반씩 쪼개서 할당하고, 해제 시 자기 버디(쌍둥이 블록)가 free면 재귀적으로 병합 — 병합 대상 탐색이 O(1)
  • 대신 2^n 반올림으로 인한 내부 단편화를 감수한다 (33KB 요청 → 64KB 지급)
  • 그 낭비를 줄이려고 커널은 자주 쓰는 작은 객체들을 slab allocator로 따로 관리한다 — 같은 크기 객체 전용 캐시라서 내부/외부 단편화가 모두 최소화됨

3-4. 페이징 — 외부 단편화의 구조적 해결

가상 메모리 페이징은 “물리 메모리가 연속일 필요 자체를 없애서” 물리 단계의 외부 단편화를 해결한다 — 가상으로 연속인 100MB가 물리적으로는 흩어진 4KB 페이지들이어도 된다.

단, 이것으로 끝이 아니다:

  • 프로세스 heap 안의(가상 주소 공간 내부의) 외부 단편화는 그대로 남는다 — malloc이 조각내는 것은 가상 주소 공간이기 때문
  • 페이지 단위(4KB) 반올림이라는 내부 단편화가 새로 생긴다
  • 커널이 물리적으로 연속인 큰 메모리를 요구하는 경우(DMA 버퍼, huge page)에는 물리 단편화가 여전히 문제다 — kmalloc vs vmalloc 구분(Linux Memory )이 존재하는 이유

4. 임베디드/장기 실행 시스템에서의 실전 대응

단편화는 “고치는” 것이 아니라 설계로 회피하는 것이다. C/C++ heap은 GC 언어와 달리 압축(compaction, 살아있는 블록을 옮겨 붙이기)이 불가능하다 — 포인터가 주소를 직접 들고 있어서 블록을 옮길 수 없기 때문이다.

전략방법
메모리 풀 (pool allocator)부팅 시 큰 블록을 미리 확보하고, 고정 크기 슬롯으로 잘라 재사용. 같은 크기만 오가므로 외부 단편화가 원리적으로 0 — 임베디드의 정석. 동작 원리와 구현은 Memory_Pool 별도 정리
초기 일괄 할당필요한 메모리를 시작 시점에 전부 할당하고 런타임 중 malloc/free 금지 (항공/차량 등 안전 규격 코딩 표준의 단골 규칙)
수명별 분리수명이 같은 객체끼리 같은 arena에서 할당 → 한꺼번에 해제 (arena/region allocator)
realloc 반복 지양조금씩 키우는 realloc 루프는 조각 양산 — 2배 성장 전략이나 사전 reserve 사용
관측glibc malloc_stats()/malloc_info(), /proc/[pid]/smaps로 단편화 정도 확인

C++에서는 std::pmr::monotonic_buffer_resource / std::pmr::unsynchronized_pool_resource(C++17)가 풀/아레나 전략의 표준 구현이다 — 사용법은 Memory_Pool 6장 참고.

5. 요약

  • 외부 단편화 = 블록 사이 구멍 (총량은 되는데 연속 공간이 없음), 내부 단편화 = 지급된 블록 안의 낭비 (반올림/정렬)
  • 유저 공간 할당자는 free list + 병합 + size class로, 커널은 buddy + slab으로 완화한다
  • 페이징은 물리 외부 단편화를 구조적으로 없애지만, heap 내부의 단편화와 페이지 반올림 낭비는 남는다
  • C/C++은 압축이 불가능하므로, 장기 실행 시스템은 메모리 풀/사전 할당으로 단편화가 생길 여지 자체를 설계에서 제거하는 것이 정답이다
