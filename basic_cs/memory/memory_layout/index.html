Memory Layout

프로세스 메모리 구조 — Code / Data / Heap / Stack

프로그램이 실행되면 OS는 프로세스에게 가상 주소 공간을 주고, 그 안을 용도별 영역으로 나눈다. 이 구조는 OS 무관 개념이다 — 리눅스 ELF든 Windows PE든 같은 구도로 나뉜다. (리눅스 관점의 확인 도구는 Linux Memory 참고)

높은 주소 
┌──────────────────┐
│  커널 공간        │  유저 코드 접근 불가
├──────────────────┤
│  Stack     ↓     │  아래로 자람 (함수 호출마다)
│  ─ ─ ─ ─ ─ ─ ─   │
│  (빈 공간)        │  ← 둘이 마주보며 자라는 이유:
│  ─ ─ ─ ─ ─ ─ ─   │     같은 빈 공간을 양쪽에서 나눠 쓰기 위해
│  Heap      ↑     │  위로 자람 (malloc/new 마다)
├──────────────────┤
│  .bss            │  초기화 안 된 전역/정적 변수
│  .data           │  초기화된 전역/정적 변수
│  .rodata         │  상수 (문자열 리터럴 등)
│  .text (Code)    │  실행 코드
└──────────────────┘
낮은 주소
영역담는 것크기 결정 시점수명
Code (.text)기계어 코드컴파일 타임프로세스 전체
Data (.data/.bss)전역/정적 변수컴파일 타임프로세스 전체
Heap동적 할당 (malloc/new)런타임free/delete 할 때까지
Stack지역 변수, 함수 호출 프레임런타임 (자동)함수 리턴까지

1. Code 영역 (.text)

  • 컴파일된 기계어 명령이 놓이는 곳. CPU가 여기서 명령을 읽어 실행한다
  • 읽기 전용 + 실행 가능으로 매핑된다 — 코드를 덮어쓰는 공격/버그를 막기 위해 쓰기가 금지되고, 반대로 데이터 영역은 실행이 금지된다 (NX bit, W^X 원칙)
  • 읽기 전용이므로 같은 프로그램을 여러 개 띄우면 물리 메모리에서 한 부를 공유한다 — 공유 라이브러리(.so/.dll)가 메모리를 절약하는 원리이기도 하다

2. Data 영역 (.data / .bss / .rodata)

전역 변수와 static 변수가 놓이는 곳. 프로그램 시작 전에 준비되고 종료까지 산다.

int g_init = 42;          // .data   — 초기화된 전역
int g_zero;               // .bss    — 초기화 안 된 전역 (0으로 자동 초기화)
static int s_cnt;         // .bss
const char *msg = "hi";   // 포인터 msg는 .data, 문자열 "hi"는 .rodata

.data와 .bss를 왜 나눴는가 — 실행 파일 크기 때문이다.

  • .data는 초기값(42)을 실행 파일에 실제로 저장해야 한다
  • .bss는 “0으로 채울 크기"만 기록하면 되고, 로더가 실행 시 그만큼 0으로 채운 메모리를 준다
  • 그래서 int big[1000000]; 같은 대형 전역 배열은 실행 파일 크기를 거의 안 늘린다 (.bss행). int big[1000000] = {1};로 바꾸는 순간 4MB가 실행 파일에 들어간다

링커가 오브젝트 파일들의 섹션을 병합하는 과정은 Build , 전역 변수의 섹션 배치는 Compiler/process 참고.

3. Heap 영역 — 동적 할당

런타임에 크기를 정해서 빌리고, 다 쓰면 직접 반납하는 영역. malloc/free(C), new/delete(C++)로 다룬다. (기초 사용법: malloc , New_malloc )

3-1. 접근 방식 — 이름이 없고, 주소로만 접근한다

int *p = (int *)malloc(sizeof(int) * 100);
p[3] = 7;        // 오직 포인터(주소값)를 통해서만 접근
  • 지역/전역 변수와 달리 heap 메모리에는 변수 이름이 없다. malloc이 돌려준 주소값을 포인터에 들고 있는 것이 유일한 접근 수단이다
  • 그래서 그 포인터를 잃어버리면(덮어쓰면) 해제할 방법도 사라진다 — 이것이 곧 메모리 누수다

3-2. 왜 느린가 — stack과의 속도 차이

단계Stack 할당Heap 할당
할당스택 포인터(SP)를 빼는 명령 1개할당자(allocator)가 free list에서 맞는 블록 탐색 + 관리 메타데이터 갱신
부족 시(페이지 폴트로 자동 확장)brk/mmap 시스템 콜로 커널에 요청
멀티스레드스레드마다 자기 스택 (경합 없음)할당자 내부 lock 경합 가능 (fork/lock 문제 의 그 malloc lock)
캐시최근 프레임이 항상 캐시에 뜨거움블록들이 흩어져 있어 캐시 지역성 나쁨

즉 heap이 느린 이유는 ① 빈 블록 탐색 비용 ② 커널 개입 가능성 ③ lock ④ 지역성 저하가 겹치기 때문이다. 성능이 중요한 루프 안에서 malloc/new를 부르지 말라는 수칙이 여기서 나온다.

3-3. 크기 제한이 비교적 적다 — 런타임 크기 조절

  • Stack은 기본 수 MB(리눅스 보통 8MB)로 상한이 빡빡하지만, heap은 물리 메모리 + 스왑이 허용하는 한 커질 수 있다 — GB 단위 버퍼는 무조건 heap행
  • 크기를 런타임에 결정할 수 있고(malloc(n)의 n이 변수여도 됨), realloc으로 나중에 늘리거나 줄일 수도 있다
arr = realloc(arr, new_n * sizeof(int));   // 런타임에 크기 재조정
  • realloc은 제자리 확장이 안 되면 새 블록 할당 + 전체 복사 + 기존 해제를 하므로 주소가 바뀔 수 있다 — 이전 주소를 다른 곳에 들고 있었다면 전부 무효가 된다

3-4. 대가 1 — Memory Leak

수명을 프로그래머가 관리하므로, free를 빠뜨리면 그 블록은 프로세스가 죽을 때까지 반환되지 않는다.

void handler(void) {
    char *buf = malloc(4096);
    /* ... */
    return;        // free 없이 리턴 — buf 주소를 아는 자가 사라짐 → 누수 확정
}
  • 한 번의 누수는 사소하지만, 반복 호출되는 경로의 누수는 장기 실행 서버/임베디드 기기를 반드시 죽인다
  • 진단 도구는 Valgrind , C++에서의 구조적 예방은 Smart_Pointer 와 Rule of Zero (소유권을 타입에게 맡겨 free 누락 자체를 불가능하게)

3-5. 대가 2 — Fragmentation (단편화)

할당/해제를 반복하면 heap에 크고 작은 구멍이 생겨서, 총 여유 메모리는 충분한데 연속된 큰 블록이 없어 할당이 실패하는 상태가 온다. 내부/외부 단편화의 구분, 할당자의 대응(free list, 병합, buddy/slab), 임베디드에서의 메모리 풀 전략까지 → Fragmentation 문서에 별도 정리.

4. Stack 영역

함수 호출과 함께 자동으로 쌓이고 리턴과 함께 사라지는 영역.

4-1. 동작 — 함수 호출 프레임

main() 호출        f() 호출           f() 리턴
┌──────────┐      ┌──────────┐      ┌──────────┐
│main 프레임│      │main 프레임│      │main 프레임│
└──────────┘      ├──────────┤      └──────────┘
                  │f의 프레임 │       (f의 지역변수는
                  │(지역변수, │        모두 무효)
                  │ 리턴주소) │
                  └──────────┘
  • 지역 변수, 함수 인자, 리턴 주소가 프레임 단위로 쌓인다
  • 할당 = SP 이동 1명령, 해제 = 리턴 시 SP 복원 — 가장 빠른 메모리
  • 스레드마다 독립된 스택을 가진다 (pthread_attr 로 크기 조절)

4-2. 전형적 버그 2가지

① Stack Overflow — 상한(기본 ~8MB)을 넘으면 즉사(SIGSEGV):

void recurse(void) { recurse(); }          // 무한 재귀
void f(void) { char big[10*1024*1024]; }   // 대형 지역 배열 — heap으로 옮겨야 함

② 지역 변수 주소 반환 (dangling pointer):

int *f(void) {
    int x = 42;
    return &x;      // ❌ 리턴 즉시 x의 프레임이 무효 — 이후 접근은 UB
}
  • 잠깐 동작하는 것처럼 보일 수 있다(다음 함수 호출이 그 자리를 덮기 전까지) — 그래서 더 위험하다
  • heap 버전의 같은 버그(free 후 사용)와 함께 Error_Pointer 참고

5. Heap vs Stack 요약 비교

항목StackHeap
할당/해제자동 (함수 호출/리턴)수동 (malloc/free)
속도매우 빠름 (SP 이동)상대적으로 느림 (탐색+시스템콜+lock)
크기 결정컴파일 타임 (지역 배열 크기 고정)런타임 (변수 크기, realloc 가능)
크기 상한작음 (기본 ~8MB)큼 (물리 메모리+스왑 한도)
접근변수 이름으로포인터(주소값)로만
수명스코프 종료까지free 할 때까지 (프로그래머 책임)
대표 사고stack overflow, 지역 주소 반환memory leak, 단편화 , double free
