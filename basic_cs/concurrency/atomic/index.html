Atomic

std::atomic과 메모리 모델

C++ 표준(C++11~)과 CPU 하드웨어 레벨의 이야기로, OS와 무관하게 적용된다. C에도 동일한 개념의 <stdatomic.h>(_Atomic, atomic_int)가 있다.

1. 왜 필요한가 — “int는 원자적이지 않다”

int counter = 0;              // ❌ 두 스레드가 counter++ 하면
                              //    load → add → store 3단계가 인터리빙되어 값 유실

std::atomic<int> counter{0};  // ✅ counter++가 단일 원자 연산 (LOCK XADD 등)
counter.fetch_add(1);
  • counter++ 같은 read-modify-write는 CPU 입장에서 여러 단계라서, 뮤텍스나 atomic 없이는 데이터 레이스(미정의 동작)
  • volatile은 원자성과 무관하다 — 컴파일러 최적화 억제일 뿐, 동기화 도구가 아님 (시그널 핸들러의 sig_atomic_t(Signal 5장)와 스레드 동기화를 혼동하지 말 것)

2. 주요 연산

std::atomic<int> a{0};

a.store(1);                   // 쓰기
int v = a.load();             // 읽기
int old = a.exchange(5);      // 새 값 쓰고 이전 값 반환
a.fetch_add(1);  a.fetch_sub(1);  a.fetch_or(0x4);

// CAS (Compare-And-Swap) — lock-free 자료구조의 핵심 연산
int expected = 5;
bool ok = a.compare_exchange_strong(expected, 10);
// a == expected면: a = 10, true 반환
// 다르면:          expected에 현재 값이 담기고 false 반환

// 전형적 CAS 루프 (lock-free 갱신)
int cur = a.load();
while (!a.compare_exchange_weak(cur, cur * 2))
    ;   // 실패 시 cur에 최신 값이 들어오므로 그걸로 재시도
  • weak은 이유 없이 실패(spurious failure)할 수 있는 대신 일부 아키텍처(ARM의 LL/SC)에서 더 싸다 — 루프 안에서는 weak, 단발 호출은 strong
  • a.is_lock_free() — 해당 타입이 진짜 하드웨어 원자 명령으로 처리되는지 확인. 크기가 크면 내부적으로 lock을 쓸 수도 있다 (std::atomic<BigStruct>)

3. 메모리 순서 (memory_order)

atomic의 진짜 어려운 부분. CPU와 컴파일러는 성능을 위해 메모리 접근을 재배치하는데, atomic 연산에 순서 제약을 지정할 수 있다.

순서의미비용
seq_cst (기본값)전역 단일 순서 보장. 가장 직관적가장 비쌈 (특히 ARM)
acquire (load 측)이 load 이후의 접근들이 앞으로 재배치되지 않음중간
release (store 측)이 store 이전의 접근들이 뒤로 재배치되지 않음중간
relaxed원자성만 보장, 순서 보장 없음가장 쌈
// 생산자-소비자 핸드셰이크: release/acquire 짝
std::atomic<bool> ready{false};
int payload;

// [생산자]
payload = 42;                                  // ①
ready.store(true, std::memory_order_release);  // ② ①이 ②보다 먼저임을 보장

// [소비자]
while (!ready.load(std::memory_order_acquire)) // ③
    ;
use(payload);                                  // ④ ③이 참이면 ①의 결과가 보임
  • release store를 acquire load가 관측하면, store 이전에 쓴 모든 데이터(payload)가 load 쪽에 보이는 것이 보장된다 — 이것이 뮤텍스 unlock/lock이 내부적으로 하는 일이기도 하다
  • relaxed는 순서가 필요 없는 순수 카운터(통계 집계 등)에만
  • 확신이 없으면 기본값(seq_cst) 을 쓰는 것이 정답이다. 순서 완화는 프로파일링으로 병목이 확인된 뒤의 최적화

4. atomic vs mutex 선택 기준

상황선택
변수 하나의 카운터/플래그std::atomic
여러 변수를 한 덩어리로 일관되게 갱신mutex (atomic 여러 개로는 원자성이 안 묶임)
크리티컬 섹션에서 I/O, 긴 연산mutex (잠들 수 있음)
lock-free 큐/스택 구현atomic CAS — 단, ABA 문제 등 난도가 매우 높아 검증된 라이브러리 사용 권장

mutex 자체의 상세(타입, 우선순위 상속 등)는 Pthread API 2장, spinlock과의 비교는 동기화 심화 참고.

5. false sharing — atomic을 써도 느려지는 함정

서로 다른 atomic 변수라도 같은 캐시라인(64B)에 붙어 있으면, 코어들이 그 라인의 소유권을 서로 뺏고 빼앗기며(cache line ping-pong) 성능이 급락한다.

// ❌ 두 카운터가 같은 캐시라인에 인접 — 스레드 2개가 각자 자기 것만 증가시켜도 느림
std::atomic<long> c0, c1;

// ✅ 캐시라인 단위로 분리
struct alignas(64) PaddedCounter { std::atomic<long> v; };
PaddedCounter c[2];   // 스레드별로 c[t].v 사용, 마지막에 합산
  • C++17의 std::hardware_destructive_interference_size가 이 정렬 크기의 표준 표현
  • “스레드별 로컬 누적 → 마지막에 합산” 패턴이 공유 atomic 카운터보다 거의 항상 빠르다
