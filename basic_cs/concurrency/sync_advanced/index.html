동기화 심화 — 우선순위 역전과 Spinlock

우선순위 역전과 spinlock은 특정 OS에 국한되지 않는 동시성/실시간 이론이다 — Windows, RTOS(VxWorks, FreeRTOS), 베어메탈 어디서든 같은 구조로 발생한다. 예제 API는 리눅스 기준(Pthread API )으로 작성했다.

1. 우선순위 역전 (Priority Inversion)

1-1. 정의와 발생 구조

높은 우선순위 태스크가, 낮은 우선순위 태스크가 잡은 lock 때문에 — 그리고 그 사이에 끼어든 중간 우선순위 태스크 때문에 — 사실상 무한정 밀리는 현상.

등장 인물 3명으로 재현된다:

  • L (낮은 우선순위): 공유 자원의 lock을 잡고 작업 중
  • H (높은 우선순위): 같은 lock이 필요해서 대기
  • M (중간 우선순위): lock과 무관한 CPU 작업
시간 →
L: ──[lock 획득]──╳ (M에게 선점당함) ─ ─ ─ ─ ─ ─ ─ ─ [재개]──[unlock]
M:                 ██████████ CPU 독점 (lock 무관) ██████████
H:        [lock 대기 시작] ─ ─ ─ ─ 계속 블록 ─ ─ ─ ─ ─ ─ ─ ─ ─ [겨우 획득]
  1. L이 lock을 잡는다
  2. H가 깨어나 같은 lock을 요구 → L이 풀 때까지 블록
  3. 이때 M이 실행 가능해지면, 스케줄러는 M > L이므로 M을 실행한다
  4. L은 CPU를 못 받아 lock을 풀지 못하고, H는 계속 기다린다

결과적으로 H가 M보다 뒤로 밀리는 “우선순위 역전” 이 완성된다. H와 L만 있으면 대기 시간이 “L의 크리티컬 섹션 길이"로 유한하지만(bounded), M이 끼는 순간 M이 CPU를 쓰는 만큼 무한정 늘어난다(unbounded) — 이것이 진짜 문제다.

1-2. 실제 사고 — Mars Pathfinder (1997)

화성에 착륙한 탐사선이 며칠 간격으로 계속 리셋되는 장애가 발생했다. OS는 리눅스가 아니라 상용 RTOS인 VxWorks였다 — 이 문제가 OS를 가리지 않는다는 증거이기도 하다.

  • L: 기상 데이터 수집 태스크 — 정보 버스의 뮤텍스를 잡고 작업
  • H: 버스 관리 태스크 (높은 우선순위) — 같은 뮤텍스 대기
  • M: 통신 태스크 (중간 우선순위, 실행 시간 김) — L을 선점
  • H가 제때 실행되지 못하자, 워치독이 “시스템 멈춤"으로 판단하고 전체 리셋

JPL은 지구에서 원격으로 해당 뮤텍스의 우선순위 상속(priority inheritance) 옵션을 켜서 해결했다 (VxWorks의 뮤텍스 생성 플래그였고, 꺼진 상태로 배포됐던 것). 우선순위 역전이 교과서 밖 실물 사고임을 보여주는 대표 사례다.

1-3. 해결책 1 — 우선순위 상속 (Priority Inheritance)

“lock을 잡은 스레드는, 그 lock을 기다리는 스레드 중 가장 높은 우선순위를 임시로 물려받는다.”

H가 lock 대기 시작하는 순간:
L의 유효 우선순위가 H 수준으로 부스트 → M이 L을 선점 못 함
→ L이 빠르게 크리티컬 섹션을 끝내고 unlock
→ L은 원래 우선순위로 복귀, H가 lock 획득

M이 끼어들 틈이 사라지므로, H의 대기 시간이 “L의 크리티컬 섹션 길이"로 다시 유한해진다.

pthread에서의 설정:

pthread_mutexattr_t ma;
pthread_mutexattr_init(&ma);
pthread_mutexattr_setprotocol(&ma, PTHREAD_PRIO_INHERIT);
pthread_mutex_init(&m, &ma);
  • 리눅스 커널은 이를 PI-futex로 지원한다 — 커널이 lock 소유자를 추적해야 상속이 가능하므로, 일반 futex보다 약간 비싸다
  • 상속은 연쇄(chain) 된다: H → (lock A 소유) L1 → (lock B 대기) → (lock B 소유) L2까지 부스트가 전파된다
  • RT 리눅스(PREEMPT_RT 패치)는 커널 내부 spinlock 상당수를 PI 뮤텍스로 바꿔서 커널 수준의 역전까지 다룬다
  • 다른 환경에도 같은 개념이 있다: FreeRTOS 뮤텍스는 우선순위 상속이 기본 내장, Windows는 Autoboost라는 자체 부스팅 메커니즘을 갖고 있다

1-4. 해결책 2 — 우선순위 상한 (Priority Ceiling)

“lock을 잡는 순간, 그 lock을 쓸 수 있는 태스크 중 최고 우선순위(ceiling)로 즉시 올린다.”

pthread_mutexattr_setprotocol(&ma, PTHREAD_PRIO_PROTECT);
pthread_mutexattr_setprioceiling(&ma, 90);   // 이 뮤텍스의 상한 우선순위
비교상속 (PRIO_INHERIT)상한 (PRIO_PROTECT)
부스트 시점높은 태스크가 실제로 대기할 때 (사후 대응)lock을 잡는 즉시 (사전 예방)
사전 정보불필요이 lock을 쓰는 태스크들의 우선순위를 미리 알아야 함
데드락 예방❌ (역전만 해결)✅ 단일 프로세서에서는 상호 대기 자체가 예방됨 (OCPP/ICPP 이론)
비용대기 발생 시에만 지불lock 잡을 때마다 우선순위 변경 2회
실무범용. 리눅스 RT의 기본 선택정적으로 설계가 고정된 하드 RT 시스템

1-5. 한계와 실무 수칙

  • 우선순위 상속은 증상 완화지 만능이 아니다: 크리티컬 섹션이 길면 (부스트돼도) 그 길이만큼은 H가 기다린다 → 크리티컬 섹션을 짧게가 항상 1순위
  • 상속 연쇄가 길어지면 최악 지연 계산이 어려워진다 → RT 설계에서는 lock 중첩을 얕게
  • SCHED_FIFO 태스크와 일반 태스크가 뮤텍스를 공유하는 순간 역전 후보가 생긴다 → RT 스레드가 만지는 뮤텍스는 습관적으로 PRIO_INHERIT를 켠다
  • 조건 변수 대기, 세마포어에는 소유자 개념이 없어 우선순위 상속이 적용될 수 없다 (누구를 부스트할지 모름) — RT 경로에서는 뮤텍스 기반 설계가 유리한 이유

2. Spinlock

2-1. 개념 — 잠들지 않고 돈다

// 개념적 구현 (test-and-set)
while (__atomic_test_and_set(&flag, __ATOMIC_ACQUIRE))
    ;   // lock이 풀릴 때까지 CPU를 태우며 반복 검사 (busy-wait)

뮤텍스는 못 잡으면 잠들고(컨텍스트 스위치, 커널 개입), spinlock은 못 잡으면 CPU를 소모하며 반복 검사한다. pthread API:

pthread_spinlock_t sl;
pthread_spin_init(&sl, PTHREAD_PROCESS_PRIVATE);
pthread_spin_lock(&sl);
/* 아주 짧은 크리티컬 섹션 */
pthread_spin_unlock(&sl);
pthread_spin_destroy(&sl);

2-2. mutex vs spinlock — 트레이드오프의 본질

비교 대상은 “잠들었다 깨는 비용” vs “스핀하며 태우는 CPU” 다.

  • 뮤텍스 대기 = 컨텍스트 스위치 2회(잠들기+깨어나기) ≈ 수 µs + 캐시 오염
  • 스핀 대기 = lock이 풀릴 때까지의 시간 × CPU 100%
조건유리한 쪽
크리티컬 섹션이 수십~수백 ns (변수 몇 개 갱신)spinlock — 잠드는 비용이 아깝다
크리티컬 섹션에서 I/O, malloc, 긴 연산mutex — 스핀 낭비가 크고, 애초에 잠들 수 있는 코드는 spinlock 금지
코어가 남아돌고 지연시간이 극도로 민감spinlock
경합이 심함 (대기자 다수)mutex — 대기자 전원이 스핀하면 CPU 낭비 폭발

단, Pthread API 2-1에서 본 것처럼 리눅스 뮤텍스는 futex 기반이라 비경합 시에는 spinlock과 비용 차이가 거의 없다. spinlock의 이득은 “경합이 있되 아주 짧게 끝나는” 좁은 구간에서만 나온다.

2-3. 단일 코어에서 spinlock이 순수 낭비인 이유

스핀하는 동안 lock은 다른 코어의 스레드가 풀어줘야 한다. 코어가 하나뿐이면:

코어 1개: [A가 lock 잡음] → [B가 스핀 시작] → B가 스핀하는 동안
          A는 실행 자체를 못 함 (코어를 B가 쓰고 있으므로)
          → B는 자기 타임슬라이스가 끝날 때까지 무의미하게 스핀
          → 스케줄러가 A로 바꿔줘야 비로소 unlock 가능

즉 스핀한 시간 전부가 낭비고, 결국 컨텍스트 스위치도 일어난다 — 뮤텍스보다 항상 나쁘다. 단일 코어 임베디드에서 유저 공간 spinlock을 쓰면 안 되는 이유다.

2-4. 유저 공간 spinlock의 함정 — 선점과 우선순위 역전의 결합

유저 공간 spinlock이 커널 spinlock과 결정적으로 다른 점: lock을 쥔 스레드가 언제든 스케줄러에게 선점당할 수 있다.

  • holder가 lock을 쥔 채 스케줄 아웃되면, 다른 코어의 대기자들은 holder가 다시 스케줄될 때까지 통째로 스핀 — 수 ms급 낭비
  • 최악 조합은 SCHED_FIFO + 유저 spinlock: 높은 우선순위 스레드가 스핀하는 동안, lock을 쥔 낮은 우선순위 스레드는 (같은 코어라면) 영원히 CPU를 못 받는다. FIFO는 타임슬라이스가 없으므로 시스템이 그대로 멈춘다 — 우선순위 역전의 spinlock 버전이며, 여기에는 우선순위 상속 같은 구제 장치도 없다 (spinlock에는 커널이 아는 소유자 개념이 없음)
  • 그래서 실무 원칙: RT 우선순위 스레드에서 유저 spinlock 금지. 짧은 경합은 PRIO_INHERIT 뮤텍스로

2-5. 커널 spinlock은 왜 안전한가

커널 코드의 spin_lock()은 다른 규칙 위에서 동작한다.

  • spin_lock()은 해당 CPU의 선점(preemption)을 비활성화하고 잡는다 — “쥔 채로 스케줄 아웃"이 원천 차단됨
  • 인터럽트 핸들러 등 잠들 수 없는(atomic) 컨텍스트에서는 뮤텍스를 쓸 수 없으므로 spinlock이 유일한 선택지다
  • 대신 커널 spinlock 크리티컬 섹션 안에서는 잠드는 함수(kmalloc(GFP_KERNEL) 포함) 호출 금지가 철칙
  • PREEMPT_RT 패치는 지연시간 단축을 위해 이 spinlock들 대부분을 잠들 수 있는 PI 뮤텍스(rt_mutex)로 치환한다 — 1장의 우선순위 상속이 커널 안까지 들어간 것

2-6. 성능 디테일 — 스핀도 잘 돌아야 한다

TTAS (Test-and-Test-and-Set):

// 순진한 TAS 스핀: 매 반복이 원자 쓰기 → 캐시라인 소유권을 계속 뺏어옴
while (atomic_exchange(&flag, 1)) ;

// TTAS: 평소엔 로컬 캐시에서 읽기만 하다가, 풀린 걸 본 순간에만 원자 연산 시도
while (atomic_exchange(&flag, 1)) {
    while (atomic_load(&flag))       // 읽기 전용 스핀 (캐시 히트)
        __builtin_ia32_pause();      // x86 PAUSE — 파이프라인/전력 낭비 완화, ARM은 YIELD
}

원자 쓰기는 해당 캐시라인을 배타 상태로 가져와야 하므로, 대기자 전원이 TAS로 스핀하면 캐시라인 핑퐁(std::atomic 5장의 false sharing과 같은 메커니즘)으로 버스가 마비된다. 읽기 스핀 + pause가 기본 교양이고, 여기에 지수 백오프(실패할수록 대기 증가)를 얹기도 한다.

Adaptive mutex — 절충안:

pthread_mutexattr_settype(&ma, PTHREAD_MUTEX_ADAPTIVE_NP);  // glibc 확장

“잠깐 스핀해보고, 그래도 안 풀리면 잠든다.” 짧은 경합은 spinlock처럼, 긴 경합은 뮤텍스처럼 동작하는 하이브리드로, 크리티컬 섹션 길이가 들쭉날쭉할 때 무난한 선택이다.
