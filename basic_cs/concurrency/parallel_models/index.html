Parallel Models

병렬 프로그래밍 모델 — 태스크 병렬 vs 스레드 병렬

“루프를 병렬로 돌린다"는 같은 목표를 두고 Windows(PPL), 리눅스(pthread/OpenMP/TBB), C++ 표준이 각자 어떤 추상화를 제공하는지 비교. 개념 자체는 OS 무관이다.

1. 추상화 레벨의 차이

Windows PPL(Parallel Patterns Library)의 concurrency::parallel_for는 pthread와 추상화 레벨 자체가 다르다.

// Windows PPL — "무엇을 병렬로 할지"만 선언
#include <ppl.h>
concurrency::parallel_for(0, N, [&](int i) {
    results[i] = heavy_compute(data[i]);
});
// pthread — 스레드 수 결정, 범위 분할, 생성, join까지 전부 수동
for (int t = 0; t < NTHREAD; t++) {
    range[t] = (range_t){ .start = t * N / NTHREAD, .end = (t + 1) * N / NTHREAD };
    pthread_create(&tid[t], NULL, worker, &range[t]);
}
for (int t = 0; t < NTHREAD; t++)
    pthread_join(tid[t], NULL);
항목concurrency::parallel_for (PPL)pthread
추상화 레벨태스크 병렬 — 작업을 선언하면 런타임이 알아서 분배스레드 병렬 — 실행 흐름을 직접 관리
스레드 관리내장 스레드 풀 + 워크 스틸링 스케줄러가 자동 처리생성/분할/join 전부 수동
부하 불균형워크 스틸링으로 자동 완화 (i마다 작업량이 달라도 OK)정적 분할이면 가장 느린 스레드가 전체를 지배
세밀 제어 (affinity, RT 우선순위, 스택)❌ 런타임에 위임✅ 전부 가능
이식성Windows 전용 (MSVC)POSIX 전 플랫폼

워크 스틸링(work stealing): 스레드 풀의 각 워커가 자기 작업 큐를 갖고, 자기 큐가 비면 다른 워커의 큐에서 작업을 훔쳐온다. 작업량이 불균등해도 놀고 있는 코어가 저절로 일을 가져가므로 부하가 균형 잡힌다 — PPL, TBB, Go 런타임, Java ForkJoinPool이 모두 이 방식이다.

2. 리눅스/표준 쪽의 대응물

pthread로 직접 짜는 것 외에, PPL과 같은 레벨의 선택지들:

// 1. OpenMP — 컴파일러 지시자 방식 (HPC/임베디드에서 광범위)
#pragma omp parallel for
for (int i = 0; i < N; i++) results[i] = heavy_compute(data[i]);

// 2. C++17 병렬 알고리즘 — 표준, 이식성 최고
std::for_each(std::execution::par, v.begin(), v.end(), heavy_compute);

// 3. Intel TBB — PPL과 가장 유사 (PPL 자체가 TBB의 영향을 받아 API가 닮음)
tbb::parallel_for(0, N, [&](int i) { results[i] = heavy_compute(data[i]); });
선택지성격비고
OpenMP지시자(pragma) 방식컴파일러 지원 필요 (-fopenmp). C/C++/Fortran, 임베디드~HPC까지 가장 널리 퍼짐
C++17 std::execution::par언어 표준이식성 최고. 단 세부 튜닝 수단이 거의 없음 (GCC/libstdc++는 내부적으로 TBB 사용)
Intel TBB (oneTBB)라이브러리PPL의 원형에 가까움. 파이프라인, 동시 컨테이너 등 도구 풍부
pthread 직접저수준아래 “언제 내려가는가” 참고

3. 관계 정리 — 언제 어느 레벨을 쓰는가

PPL/TBB/OpenMP는 pthread(Windows에서는 Win32 스레드) 위에 얹힌 상위 레이어다.

  • 데이터 병렬 루프가 목적이면: 상위 레이어(태스크 병렬)가 생산성과 부하 분산에서 거의 항상 유리하다
  • 하드웨어에 붙는 제어가 필요하면: RT 우선순위, CPU affinity, NUMA 배치, 스택 크기 같은 것은 상위 레이어가 숨겨버리므로 pthread 레벨로 내려와야 한다 — Pthread API 의 attr/affinity 장, Multi_Thread_Diff 의 std::thread vs pthread 표와 같은 구도
  • 장시간 사는 워커(이벤트 루프, RT 주기 태스크)는 태스크 병렬 모델과 맞지 않는다 — 스레드를 직접 만들고 수명을 관리하는 것이 맞다
