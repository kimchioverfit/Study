Daemon

Process Group, Session, Daemon

프로세스 그룹과 세션은 셸의 잡 컨트롤(Ctrl+C가 파이프라인 전체를 죽이는 원리)과 데몬화(daemonize)를 이해하는 데 필요한 개념이다.

1. 프로세스 그룹과 세션의 계층 구조

Session (세션)  ── 제어 터미널(controlling terminal) 최대 1개와 연결
 ├── Process Group A (foreground)   ← 터미널 입력/시그널을 받음
 │    ├── ls
 │    └── grep      (ls | grep 파이프라인 = 한 그룹)
 └── Process Group B (background)
      └── long_task &
개념ID설명
프로세스 그룹PGID시그널을 한꺼번에 받는 단위. 셸은 파이프라인 하나를 한 그룹으로 묶는다
세션SID그룹들의 모음. 하나의 제어 터미널을 가질 수 있다
세션 리더SID == PID세션을 만든 프로세스 (보통 로그인 셸)
  • Ctrl+C를 누르면 터미널 드라이버가 foreground 프로세스 그룹 전체에 SIGINT를 보낸다 — ls | grep이 한꺼번에 죽는 이유
  • kill -TERM -PGID (음수 PID)로 그룹 전체에 시그널을 보낼 수 있다 (Signal 2장)

2. 관련 함수

#include <unistd.h>

pid_t getpgrp(void);            // 내 프로세스 그룹 ID
int   setpgid(pid_t pid, pid_t pgid);  // 프로세스 그룹 변경/생성
pid_t getsid(pid_t pid);        // 세션 ID 조회
pid_t setsid(void);             // 새 세션 생성 (데몬화의 핵심)

setpgid() — 셸이 잡 컨트롤을 구현하는 방법

// 셸이 파이프라인 실행 시: 첫 자식의 PID를 그룹 ID로 삼아 묶는다
setpgid(child_pid, pipeline_leader_pid);

setsid() — 새 세션 만들기

호출한 프로세스가 새 세션의 리더 + 새 그룹의 리더가 되고, 제어 터미널과의 연결이 완전히 끊긴다.

  • 제약: 이미 프로세스 그룹 리더인 프로세스는 호출할 수 없다 (EPERM) — 그래서 데몬화할 때 fork를 먼저 해서 “리더가 아닌 자식"을 만든 뒤 자식이 setsid를 호출한다

3. 데몬(Daemon) 만들기 — double fork 패턴

데몬은 터미널 없이 백그라운드에서 도는 서비스 프로세스다. 전통적인 데몬화 절차:

#include <unistd.h>
#include <sys/stat.h>
#include <fcntl.h>

void daemonize(void) {
    // 1차 fork: 부모 종료 → 자식은 "그룹 리더가 아닌" 상태가 됨
    if (fork() > 0) _exit(0);

    // 새 세션 생성 → 제어 터미널과 완전 분리
    setsid();

    // 2차 fork: 세션 리더도 아니게 만듦
    //           → 이후 터미널 디바이스를 열어도 제어 터미널로 붙잡는 일이 없음
    if (fork() > 0) _exit(0);

    // 환경 정리
    umask(0);                     // 상속받은 umask 초기화
    chdir("/");                   // 마운트 해제를 막지 않도록 루트로 이동

    // 표준 입출력을 /dev/null로 교체 (터미널 fd를 끊음)
    int fd = open("/dev/null", O_RDWR);
    dup2(fd, STDIN_FILENO);
    dup2(fd, STDOUT_FILENO);
    dup2(fd, STDERR_FILENO);
    if (fd > 2) close(fd);
}

각 단계가 필요한 이유

단계이유
1차 fork + 부모 종료① 셸에게는 명령이 끝난 것처럼 보임 ② 자식은 그룹 리더가 아니게 되어 setsid() 호출 자격이 생김 ③ 부모가 죽었으므로 고아가 되어 init(systemd)의 자식으로 편입
setsid()제어 터미널과 분리 — 터미널이 닫혀도 SIGHUP을 받지 않음
2차 fork세션 리더 자격까지 버림 — 세션 리더는 터미널 디바이스를 열면 그것이 제어 터미널로 붙어버릴 수 있는데(System V 계열), 그 가능성을 원천 차단
chdir("/")데몬이 어떤 디렉토리를 cwd로 물고 있으면 그 파일시스템을 umount 할 수 없게 됨
표준 fd 교체끊어진 터미널에 쓰다가 SIGPIPE/에러가 나는 것을 방지. 로그는 파일이나 syslog()로
  • glibc에는 이를 대충 해주는 daemon(nochdir, noclose) 함수도 있지만, double fork를 생략하는 등 완전하지 않아 직접 구현하는 경우가 많다

4. 현대의 관점 — systemd 시대의 데몬

systemd 환경에서는 위 전통 방식이 오히려 권장되지 않는다.

전통 데몬 (SysV 스타일)systemd 방식 (new-style)
스스로 double fork로 데몬화데몬화하지 않고 포그라운드로 실행 — systemd가 프로세스 관리
PID 파일로 중복 실행 방지systemd가 프로세스를 직접 추적 (PID 파일 불필요)
syslog()로 로그stdout/stderr에 그냥 출력 → journald가 수집
SIGHUP으로 설정 리로드ExecReload= 지시자로 정의
# /etc/systemd/system/myapp.service
[Service]
Type=simple            # 포그라운드 실행을 전제
ExecStart=/usr/bin/myapp
Restart=on-failure     # 죽으면 자동 재시작

즉 새로 작성하는 서비스라면 데몬화 코드를 넣지 말고 포그라운드 프로그램으로 만들어 서비스 매니저(systemd, 임베디드라면 BusyBox init + start-stop-daemon 등)에게 맡기는 것이 현대적 설계다. double fork 패턴은 “왜 그렇게 했는지"를 이해하는 것이 중요한 고전 기법으로 남아 있다.
