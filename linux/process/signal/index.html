Signal

Linux Signal

시그널은 커널 또는 다른 프로세스가 특정 프로세스에게 보내는 비동기 알림이다. 프로세스 제어(wait와 SIGCHLD), 종료 처리, 데몬의 설정 리로드 등 프로세스 관리와 밀접하게 얽혀 있다.

1. 대표 시그널

  • SIGKILL/SIGSTOP을 못 막게 한 이유: 어떤 프로세스든 관리자가 반드시 제어할 수 있어야 하므로

2. 시그널 보내기 — kill(), raise()

#include <signal.h>

kill(pid, SIGTERM);      // 특정 프로세스에게
kill(-pgid, SIGTERM);    // 음수: 프로세스 그룹 전체에게
kill(pid, 0);            // 시그널 0: 실제로 안 보내고 "프로세스 생존 확인"용
raise(SIGABRT);          // 자기 자신에게 (= kill(getpid(), sig))
  • 이름과 달리 kill()은 “죽이는 함수"가 아니라 “시그널 전달 함수"다
  • kill(pid, 0)은 프로세스 존재 확인의 관용 표현 — 성공하면 살아있고, errno == ESRCH면 없는 것

3. signal() vs sigaction()

3-1. signal() — 간단하지만 쓰지 말 것

signal(SIGINT, handler);   // 간단하지만 동작이 구현마다 다름

역사적으로 System V 계열에서는 핸들러가 한 번 실행되면 SIG_DFL로 리셋되는 등(one-shot), 플랫폼마다 의미가 달랐다. 이식성 있는 코드에서는 SIG_IGN/SIG_DFL 설정 정도에만 쓰고, 핸들러 등록은 sigaction()을 쓰는 것이 원칙이다.

3-2. sigaction() — 표준

struct sigaction sa = {0};
sa.sa_handler = handler;
sigemptyset(&sa.sa_mask);        // 핸들러 실행 중 추가로 블록할 시그널 집합
sa.sa_flags = SA_RESTART;        // 시그널로 끊긴 시스템 콜을 자동 재시작
sigaction(SIGINT, &sa, NULL);
주요 플래그의미
SA_RESTART시그널로 중단된 read() 등 느린 시스템 콜을 EINTR 대신 자동 재시작
SA_NOCLDWAITSIGCHLD에 설정 시 자식이 좀비가 되지 않음 (wait 불필요)
SA_SIGINFO핸들러가 siginfo_t로 발신자 PID 등 상세 정보를 받음

4. SIGCHLD와 좀비 회수 패턴

자식 프로세스가 종료되면 부모는 SIGCHLD를 받는다. 이를 이용하면 부모가 블록되지 않고 비동기로 자식을 회수할 수 있다 (Process API 3장의 좀비 문제 해결).

void reap_children(int sig) {
    int saved = errno;                       // errno 보존 (핸들러 규칙)
    while (waitpid(-1, NULL, WNOHANG) > 0)
        ;
    errno = saved;
}

struct sigaction sa = {0};
sa.sa_handler = reap_children;
sa.sa_flags = SA_RESTART | SA_NOCLDSTOP;
sigaction(SIGCHLD, &sa, NULL);

루프를 도는 이유: 시그널은 큐잉되지 않는다(standard signal 기준). 자식 3개가 거의 동시에 죽어도 SIGCHLD는 1번만 전달될 수 있으므로, 핸들러에서 WNOHANG 루프로 그 시점의 종료 자식을 전부 회수해야 한다.

5. 시그널 핸들러 안에서의 제약 — async-signal-safe

시그널 핸들러는 프로그램의 아무 지점에서나 끼어들어 실행된다. 예를 들어 malloc() 실행 도중(내부 lock 보유 상태)에 핸들러가 끼어들어 다시 malloc()을 부르면 데드락이다 — fork의 lock 문제 와 정확히 같은 구조다.

따라서 핸들러 안에서는 async-signal-safe 함수만 호출해야 한다.

안전 (허용)위험 (금지)
write(), _exit(), kill(), waitpid(), sigaction()printf(), malloc()/free(), exit(), 뮤텍스 계열, C++ new/delete

실무 패턴 — 핸들러에서는 플래그만 세운다:

volatile sig_atomic_t got_signal = 0;

void handler(int sig) { got_signal = 1; }   // 이것만 하고 즉시 리턴

int main(void) {
    /* sigaction 등록 후 */
    while (running) {
        if (got_signal) { got_signal = 0; do_real_work(); }
        /* ... 메인 루프 ... */
    }
}
  • volatile sig_atomic_t: 비동기 수정에 대해 읽기/쓰기가 원자적임이 보장되는 유일한 표준 타입
  • 더 나아가면 self-pipe trick이나 리눅스 고유의 signalfd()로 시그널을 이벤트 루프(poll/epoll)에 통합하는 방법도 있다

6. 시그널 블록 — sigprocmask()

크리티컬 섹션 동안 시그널 전달을 잠시 미룰 수 있다.

sigset_t set, old;
sigemptyset(&set);
sigaddset(&set, SIGCHLD);

sigprocmask(SIG_BLOCK, &set, &old);    // SIGCHLD 잠시 보류
/* ... fork 하고 자식 PID를 자료구조에 등록하는 크리티컬 섹션 ... */
sigprocmask(SIG_SETMASK, &old, NULL);  // 원복 — 보류된 시그널이 이때 전달됨
  • 블록은 “버리는 것"이 아니라 “보류(pending)“다 — 해제하면 전달된다
  • 멀티스레드에서는 sigprocmask 대신 pthread_sigmask()를 쓴다 (시그널 마스크는 스레드별 속성)
