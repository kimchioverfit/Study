Linux Process: fork()

✅ fork()란?

fork()는 현재 실행 중인 프로세스(부모)를 복제하여 새로운 프로세스(자식)를 생성하는 시스템 콜이다. 호출 한 번에 반환이 두 번 일어나는 것이 특징이다.

#include <unistd.h>
#include <stdio.h>
#include <sys/wait.h>

int main(void) {
    pid_t pid = fork();

    if (pid < 0) {
        // fork 실패
        perror("fork failed");
    } else if (pid == 0) {
        // 자식 프로세스: pid == 0
        printf("child, pid=%d\n", getpid());
    } else {
        // 부모 프로세스: pid == 자식의 PID
        printf("parent, child pid=%d\n", pid);
        wait(NULL);
    }
    return 0;
}
반환값의미
< 0fork 실패 (자식 생성 안 됨)
== 0자식 프로세스 쪽 리턴값
> 0부모 프로세스 쪽 리턴값 (생성된 자식의 PID)

1. fork()의 동작 원리 — Copy-On-Write (COW)

fork()가 호출되면 커널은 부모의 다음 자원들을 자식에게 복제한다.

복제되는 것비고
주소 공간 (code/data/heap/stack)실제 물리 메모리는 즉시 복사하지 않고 COW로 지연 복사
파일 디스크립터 테이블fd 자체는 복사되지만, 같은 파일 오프셋/커널 파일 객체를 공유
시그널 핸들러 설정복사
환경 변수, 현재 작업 디렉토리복사

반대로 복제되지 않고 새로 부여되는 것:

  • PID (새 프로세스 ID)
  • 부모 PID (PPID = 원래 부모)
  • 리소스 사용량 카운터, 대기 중인 시그널 등

Copy-On-Write란?

fork() 직후에는 부모와 자식이 동일한 물리 페이지를 읽기 전용(read-only)으로 공유한다. 둘 중 하나가 해당 페이지에 쓰기(write) 를 시도하는 순간에만 페이지 폴트가 발생하고, 그때 비로소 커널이 해당 페이지만 실제로 복사해 각자의 것으로 만든다.

  • 장점: 대부분의 fork()는 곧바로 exec()로 이어지므로, 애초에 전체 주소 공간을 복사할 필요가 없다. COW 덕분에 fork()는 프로세스 크기와 무관하게 거의 O(1)에 가까운 비용으로 끝난다.
  • 실제로 복사되는 페이지는 “부모/자식 중 하나가 fork 이후 실제로 수정한 페이지"뿐이다.

2. fork()와 멀티스레드 — 호출한 스레드만 복제된다

2-1. main thread만 살아남는다

멀티스레드 프로세스에서 fork()를 호출하면, 자식 프로세스에는 fork()를 호출한 스레드 딱 하나만 복제된다. 나머지 스레드들은 자식 프로세스에 존재하지 않는다.

// 부모: main thread + worker thread 2개 실행 중
pid_t pid = fork();   // main thread에서 호출
// 자식: main thread 1개만 존재. worker 2개는 자식에 없음

여기서 중요한 점은 다른 스레드들이 “정상 종료"되는 것이 아니라 아무런 정리 과정 없이 그냥 증발한다는 것이다.

  • pthread_cleanup_push()로 등록한 정리 핸들러가 실행되지 않는다
  • 소멸자, unwinding, cancel 처리 전부 없음 — 그 스레드는 자식 입장에서 처음부터 없던 존재가 된다

2-2. 메모리는 전체가 복제된다는 게 함정

스레드는 하나만 복제되지만, 주소 공간(메모리)은 프로세스 전체가 COW로 복제된다. 즉 사라진 스레드들이 만지고 있던 데이터도 “만지다 만 상태 그대로” 자식에게 넘어온다.

  • 어떤 스레드가 연결 리스트를 절반쯤 수정하던 중이었다면, 자식은 반쯤 깨진 연결 리스트를 물려받는다
  • 그 데이터를 고쳐줄 스레드는 자식에 존재하지 않으므로, 그 불일치 상태는 영원히 복구되지 않는다

2-3. lock이 걸린 상태에서 fork() 했을 때의 문제 ⚠️

가장 실전에서 자주 터지는 케이스다. fork() 시점에 다른 스레드가 뮤텍스를 잡고(lock) 있었다면, 자식에서 그 뮤텍스는 “영원히 잠긴 상태"로 남는다.

// [부모 프로세스]
// worker thread:  pthread_mutex_lock(&m);  ← lock 잡은 상태에서
// main thread:    fork();                  ← fork 발생

// [자식 프로세스]
// - worker thread는 존재하지 않음 (증발)
// - 하지만 m은 메모리 복제로 "locked" 상태 그대로 넘어옴
// - m을 풀어줄 소유자가 자식에 없음
pthread_mutex_lock(&m);   // → 영원히 블록 (데드락)
  • 뮤텍스는 그냥 메모리 위의 자료구조이므로 COW로 잠긴 상태 그대로 복사된다
  • 그 lock을 풀 수 있는 유일한 존재(소유 스레드)는 자식에 없다
  • 결과: 자식이 그 뮤텍스를 잡으려는 순간 데드락

malloc 데드락 — 내 코드에 lock이 없어도 당한다

이 문제의 무서운 점은 내가 직접 만든 뮤텍스가 없어도 발생한다는 것이다. 라이브러리 내부 lock 때문이다.

// 부모: worker thread가 malloc() 실행 중 (glibc 힙 내부 lock 보유 상태)
// main thread에서 fork()

// 자식:
char *p = malloc(100);   // glibc 내부 힙 lock을 잡으려다 데드락!
printf("hello\n");       // stdio 내부 lock도 마찬가지로 위험

malloc(), printf(), 로깅 라이브러리 등은 내부적으로 뮤텍스를 사용한다. fork 순간에 어떤 스레드가 그 내부 lock을 잡고 있었는지는 타이밍 운에 달려 있으므로, 이런 버그는 재현이 어렵고 간헐적으로만 터진다.

2-4. 안전 수칙

규칙 1: 멀티스레드 프로그램에서 fork() 후 자식은 exec 전까지 async-signal-safe 함수만 호출한다.

POSIX가 명시하는 공식 규칙이다. async-signal-safe 함수(_exit(), execve(), write(), dup2() 등)는 내부 lock에 의존하지 않으므로 안전하다. 반대로 malloc, printf, exit 등은 금지다.

pid_t pid = fork();
if (pid == 0) {
    // 여기서는 async-signal-safe 함수만!
    dup2(fd, STDOUT_FILENO);   // OK
    execve(path, argv, envp);  // OK
    _exit(127);                // OK (exit()는 금지)
}

규칙 2: 자식에서 계속 실행해야 한다면 pthread_atfork()로 방어한다.

pthread_atfork(prepare, parent, child);
핸들러호출 시점하는 일
preparefork 직전 (부모)프로그램의 모든 lock을 미리 획득 — fork 순간에 잠긴 lock이 없도록 보장
parentfork 직후 (부모)획득했던 lock을 전부 해제
childfork 직후 (자식)lock을 해제하거나, 아예 pthread_mutex_init()으로 재초기화

원리: fork 직전에 모든 lock을 이 스레드가 직접 잡아두면, fork 순간 “다른 스레드가 잡고 있는 lock"이 존재할 수 없게 된다. 자식은 그 lock들을 풀거나 재초기화한 뒤 안전하게 출발한다.

다만 한계도 명확하다:

  • 프로그램이 쓰는 모든 lock(써드파티 라이브러리 내부 lock 포함)을 알고 등록해야 하는데 현실적으로 불가능에 가깝다
  • 그래서 실무 결론은 대부분 “멀티스레드 프로세스에서는 fork()는 fork+exec 용도로만 쓰고, 자식에서 계속 실행하지 마라”, 또는 처음부터 posix_spawn()을 쓰라는 것이다

3. Windows에는 왜 fork()가 없는가

결론부터 말하면, fork()는 UNIX 프로세스 모델의 근본 전제 위에서만 자연스러운 연산이고, Windows NT 커널의 프로세스 모델은 그 전제 자체가 다르기 때문이다.

3-1. UNIX의 “fork + exec” 분리 모델

UNIX 계열은 프로세스 생성을 의도적으로 두 단계로 쪼갠다.

  1. fork() — 현재 프로세스를 그대로 복제해서 “빈 껍데기 프로세스"를 만든다.
  2. exec() — 그 껍데기의 주소 공간을 새 실행 이미지로 통째로 교체한다.

이렇게 나눠 놓으면 fork와 exec 사이에서 자식 프로세스가 자유롭게 자신을 커스터마이징할 수 있다 (예: 표준입출력 리다이렉션, 파일 디스크립터 닫기, 권한 변경, 환경변수 조작 등). 셸이 파이프(|)나 리다이렉션(>)을 구현할 수 있는 것도 이 구조 덕분이다.

3-2. Windows NT의 프로세스 생성 모델

Windows는 애초에 이 두 단계를 분리하지 않는다. CreateProcess() 하나가 “새 프로세스 오브젝트 생성 + 실행 이미지 로드 + 초기 스레드 시작"을 한 번에 처리한다.

CreateProcess(
    "C:\\app.exe",   // 실행할 이미지 경로
    ...,             // 커맨드라인, 보안 속성, 환경 등을 파라미터로 직접 전달
    &si, &pi
);

fork처럼 “현재 프로세스를 복제"하는 중간 단계가 없고, 자식이 어떤 실행 파일을 실행할지, 어떤 핸들을 물려받을지 등을 생성 시점에 파라미터로 명시해야 한다.

3-3. fork가 Windows에 자연스럽게 이식되기 어려운 구조적 이유

이유설명
커널 오브젝트 핸들 테이블 구조 차이NT 커널은 프로세스마다 핸들 테이블(파일, 뮤텍스, 이벤트, 레지스트리 키 등 커널 오브젝트에 대한 참조)을 가지는데, 이 구조가 UNIX의 fd 테이블보다 훨씬 무겁고 커널 전역 오브젝트 매니저와 얽혀 있어 “통째로 복제"하는 비용/의미가 불명확하다
스레드 모델NT는 프로세스 안에 이미 여러 스레드가 떠 있는 것을 기본으로 가정한다(GUI 서브시스템, csrss 등). fork 시 “다른 스레드들은 어떻게 되는가"라는 POSIX에서도 골치 아픈 문제가 Windows 구조에서는 더 심각해진다
DLL / 서브시스템 상태프로세스가 로드한 DLL, Win32 서브시스템(csrss.exe)에 등록된 상태, 레지스트리 핸들 등은 단순 메모리 복제로 재현할 수 없는 프로세스 외부 상태다
주소 공간 레이아웃NT의 메모리 관리자는 UNIX의 fork()가 기대하는 “부모와 동일한 가상주소 레이아웃을 가진 자식"을 값싸게 만들어주는 경로를 처음부터 설계에 넣지 않았다
설계 철학UNIX는 “작은 프로세스를 값싸게 복제"하는 것이 핵심 철학이지만, Windows는 처음부터 “무거운 프로세스 오브젝트를 명시적 파라미터로 생성"하는 철학으로 설계됨

3-4. 실제 사례로 보는 어려움

  • Cygwin: POSIX 호환 레이어에서 fork()를 에뮬레이션하는데, NT 프로세스를 새로 만든 뒤 부모의 메모리를 강제로 복사해 넣는 방식으로 구현한다. 이 과정이 느리고, 부모의 메모리 레이아웃(DLL 로드 주소 등)이 자식과 정확히 일치해야 해서 깨지기 쉽다(“fork() failed” 에러가 Cygwin 사용자들 사이에서 유명한 이유).
  • WSL1 (Windows Subsystem for Linux, 1세대): NT 커널 위에서 Linux 시스템 콜을 직접 구현하려 시도하면서 fork()를 지원하기 위해 “Pico Process"라는 경량 프로세스 개념까지 새로 만들어야 했다. 그럼에도 완전한 호환에는 한계가 있었고, 결국 WSL2는 아예 실제 Linux 커널을 경량 VM 위에서 통째로 돌리는 방식으로 전환했다. 이는 “Windows NT 커널 위에 UNIX의 fork 의미론을 완전히 재현하는 것"이 얼마나 어려운지 보여주는 대표적 사례다.

정리하면, Windows에 fork가 없는 이유는 단순히 “API를 안 만들어서"가 아니라 NT 커널의 프로세스/스레드/커널 오브젝트 모델 자체가 “저비용 전체 복제"라는 연산을 전제하지 않기 때문이다.

4. fork() 대신 clone()을 써야 메모리를 공유할 수 있는 이유

fork()는 좋든 싫든 항상 자식에게 독립된 주소 공간(COW로 분리됨)을 준다. 옵션으로 “메모리를 공유해라"라고 지시할 방법이 fork() 자체에는 없다.

그런데 실제로는 “새로운 실행 흐름은 필요한데, 부모와 메모리는 공유하고 싶다” — 즉 스레드를 만들고 싶은 경우가 매우 흔하다. 이때 쓰는 것이 리눅스 고유의 clone() 시스템 콜이다.

4-1. clone()의 핵심 아이디어

clone()은 “무엇을 공유하고 무엇을 분리할지"를 플래그로 세밀하게 지정할 수 있는, fork()보다 훨씬 저수준/범용적인 프로세스(정확히는 “실행 흐름”) 생성 API다.

int clone(int (*fn)(void *), void *stack, int flags, void *arg, ...);
플래그공유되는 자원
CLONE_VM주소 공간(메모리) 공유 — 이게 없으면 COW로 분리된 주소 공간을 얻음
CLONE_FS파일 시스템 정보 공유 (root, cwd, umask)
CLONE_FILES파일 디스크립터 테이블 공유
CLONE_SIGHAND시그널 핸들러 테이블 공유 (이 경우 CLONE_VM도 필수)
CLONE_THREAD같은 스레드 그룹(TGID)에 속하게 함 — getpid()가 같은 값을 반환
CLONE_VFORK자식이 exec/exit 하기 전까지 부모를 정지시킴 (vfork와 동일한 효과)

4-2. pthread가 바로 이 방식을 쓴다

우리가 흔히 쓰는 pthread_create()는 내부적으로 glibc(NPTL)가 다음과 유사한 플래그 조합으로 clone()을 호출해서 구현된다.

clone(thread_start, stack, 
      CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND |
      CLONE_THREAD | CLONE_SYSVSEM | CLONE_SETTLS |
      CLONE_PARENT_SETTID | CLONE_CHILD_CLEARTID,
      arg);

즉 “스레드"란 리눅스 커널 입장에서는 특별한 존재가 아니라, CLONE_VM(메모리 공유) 등의 플래그를 켜고 clone()으로 만든 실행 흐름일 뿐이다. 커널은 프로세스와 스레드를 구조적으로 구분하지 않고 둘 다 task_struct로 표현하며, 차이는 오직 “clone 시 무엇을 공유했는가"에 있다.

4-3. 왜 fork()는 이 역할을 못 하는가

  • fork()는 역사적으로 “완전히 독립된 자식 프로세스"를 만드는 것이 목적이고 의미론이 고정되어 있다. POSIX 표준상 fork()는 주소 공간을 분리해야 하며, 옵션으로 이를 바꿀 수 없다.
  • 반면 clone()은 리눅스가 “프로세스 생성"과 “스레드 생성"을 하나의 일반화된 시스템 콜로 통합하기 위해 만든 것으로, CLONE_VM 플래그 하나로 원하는 메모리 공유 여부를 스위치처럼 켜고 끌 수 있다.
  • 실제로 리눅스 커널 내부 구현을 보면 fork(), vfork(), pthread 생성이 모두 최종적으로는 커널의 kernel_clone() (예전 이름 do_fork()) 함수 하나로 수렴한다. fork()는 사실상 특정 플래그 조합(SIGCHLD만 설정, CLONE_VM 없음)으로 clone()을 호출하는 것과 동일하다.

즉 “메모리 공유가 필요하면 clone()을 써야 하는 이유"는, clone()이 fork()의 상위 호환(더 일반화된 버전)이며 CLONE_VM 플래그로 정확히 그 니즈(주소 공간 공유)를 표현할 수 있는 유일한 표준 인터페이스이기 때문이다. fork()는 애초에 그 선택지를 제공하지 않는다.

5. vfork()

5-1. vfork()가 등장한 배경

vfork()는 COW가 아직 없던 시절(초기 BSD UNIX)의 최적화 기법이다. COW가 없으면 fork()는 자식 생성 시 부모의 전체 주소 공간을 물리적으로 복사해야 했는데, 대부분의 fork() 뒤에는 곧바로 exec()가 와서 그 복사본을 버리는 경우가 많았다. 이는 명백한 낭비였고, 이를 없애기 위해 vfork()가 도입됐다.

#include <unistd.h>

pid_t pid = vfork();
if (pid == 0) {
    // 자식: 부모와 동일한 주소 공간을 그대로 사용 중
    execve("/bin/ls", argv, envp);   // 반드시 exec 또는 _exit만 호출
    _exit(127);                      // exec 실패 시 반드시 _exit (return/exit 금지)
}
// 부모: 자식이 exec 또는 _exit 할 때까지 여기서 멈춰 있는다

5-2. vfork()의 동작 방식

  • 자식 프로세스는 자신만의 주소 공간을 전혀 갖지 않고, 부모의 주소 공간을 그대로(포인터 수준으로) 사용한다. COW조차 아니고, 그냥 같은 메모리를 보는 것이다.
  • vfork() 호출 후 부모 프로세스는 자식이 exec() 또는 _exit()를 호출할 때까지 완전히 정지(suspend) 된다. 즉 부모와 자식이 동시에 실행되지 않는 것이 보장된다.
  • 자식이 exec()에 성공하면 새 실행 이미지로 교체되면서 비로소 독립된 주소 공간을 갖게 되고, 그제서야 부모가 깨어나 실행을 재개한다.

5-3. vfork()의 위험성 — 왜 fork()보다 훨씬 조심해야 하는가

자식이 부모와 동일한 메모리(스택 포함) 를 공유하기 때문에 다음 규칙을 어기면 매우 위험하다.

금지 사항이유
지역 변수 수정 후 함수에서 return자식의 스택 = 부모의 스택이므로, 자식이 스택 프레임을 건드리면 부모가 나중에 실행을 재개할 때 스택이 이미 오염되어 있어 정의되지 않은 동작 발생
exec/_exit 외의 다른 함수 호출라이브러리 함수가 내부적으로 전역/스택 상태를 바꾸면 부모 쪽 실행 상태를 훼손할 수 있음
일반 exit() 사용glibc의 exit()는 stdio 버퍼 플러시 등 상위 레벨 정리를 수행하는데, 이 과정에서 부모와 공유 중인 버퍼/메모리를 건드릴 수 있어 위험. 반드시 로우레벨 _exit() 사용
전역 변수 변경부모가 그 값을 그대로 이어받아 실행하므로 의도치 않은 부작용 발생

이런 이유로 POSIX 표준 자체가 “vfork 이후 자식은 exec 계열 함수를 호출하거나 _exit()를 호출하는 것 외의 동작을 하면 동작이 정의되지 않는다(undefined behavior)“고 명시하고 있다.

5-4. COW가 있는 지금도 vfork()가 남아있는 이유

리눅스는 이미 fork()에 COW를 적용하고 있어서 이론적으로는 vfork()가 불필요해 보이지만, 여전히 존재하고 사용되는 이유가 있다.

  • COW fork()라도 페이지 테이블 자체는 복사해야 하고(주소 공간이 크면 이 비용도 무시 못함), 이후 exec()가 그 주소 공간을 다시 통째로 버리는 과정에서 추가 오버헤드가 존재한다.
  • vfork()는 페이지 테이블 복사조차 하지 않으므로, “곧바로 exec할 것"이 확실한 상황(예: 셸에서 명령어 실행, posix_spawn() 내부 구현)에서는 fork()보다 더 빠르다.
  • 그래서 glibc의 system(), posix_spawn() 같은 함수들이 내부적으로 vfork() (또는 clone(CLONE_VM | CLONE_VFORK))를 최적화 경로로 사용하는 경우가 있다.
  • 메모리가 제한적인 임베디드 환경에서는 페이지 테이블 복사 비용조차 부담이 될 수 있어 vfork()의 이점이 더 크게 작용한다.
