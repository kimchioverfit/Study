Pthread API

Pthread API

POSIX 스레드(pthread)의 대표 함수 정리. 스레드가 커널 관점에서 clone(CLONE_VM | ...)으로 만들어진 실행 흐름이라는 배경은 Process/Fork 문서 4장 참고.

1. 스레드 생성과 종료

1-1. pthread_create()

#include <pthread.h>

int pthread_create(pthread_t *thread,           // [out] 생성된 스레드 핸들
                   const pthread_attr_t *attr,  // 속성 (NULL = 기본값)
                   void *(*start_routine)(void *), // 스레드가 실행할 함수
                   void *arg);                  // 함수에 넘길 인자
  • 성공 시 0, 실패 시 에러 번호를 직접 반환한다 (errno가 아님 — pthread 계열 공통 규칙)
  • arg는 void* 하나뿐이므로 여러 값을 넘기려면 구조체로 묶어서 포인터를 넘긴다

흔한 실수 — 지역 변수의 주소를 arg로 넘기기:

// ❌ 위험: 루프 변수 i의 주소를 넘김
for (int i = 0; i < N; i++)
    pthread_create(&tid[i], NULL, worker, &i);   // 스레드가 읽는 시점에 i는 이미 바뀜

// ✅ 값 자체를 캐스팅해서 넘기거나, 스레드별 구조체를 힙/배열에 마련
for (long i = 0; i < N; i++)
    pthread_create(&tid[i], NULL, worker, (void *)i);

스레드가 언제 실행될지는 스케줄러 마음이므로, arg가 가리키는 메모리는 스레드가 다 읽을 때까지 유효해야 한다.

1-2. pthread_join() / pthread_detach()

void *ret;
pthread_join(tid, &ret);    // 스레드 종료 대기 + 반환값 수신 + 자원 회수
pthread_detach(tid);        // 회수 예약 — 종료 시 자원이 자동 해제됨
구분joindetach
종료 대기✅ 블록❌ 안 함
반환값 수신✅❌
자원 회수join 시점에스레드 종료 시점에 자동
  • 프로세스의 좀비와 정확히 같은 구조다: join도 detach도 안 한 종료 스레드는 자원(스택 등)을 계속 점유한다 (Process API 3장의 좀비와 비교)
  • 같은 스레드를 두 번 join 하면 미정의 동작
  • pthread_exit(retval) — 스레드 자신을 종료. main thread가 이걸 호출하면 프로세스는 남고 다른 스레드는 계속 돈다 (main에서 return/exit() 하면 전체 종료)

1-3. detach의 함정 — background worker는 detach 하지 말 것 ⚠️

detach를 “스레드를 독립시켜서 알아서 살게 하는 것"으로 오해하기 쉬운데, 실제로는 자원 회수를 자동화할 뿐 수명을 보장해주지 않는다.

함정 1: 프로세스가 끝나면 detached thread도 그 자리에서 끊긴다

int main(void) {
    pthread_t tid;
    pthread_create(&tid, NULL, save_to_file, NULL);  // 파일 저장 worker
    pthread_detach(tid);
    return 0;   // main 리턴 → 프로세스 전체 종료
                // → worker는 파일을 쓰다 만 지점에서 그대로 증발
}
  • main이 리턴하거나 누군가 exit()를 호출하면 프로세스의 모든 스레드가 즉시 종료된다. detach 여부와 무관하다
  • 이때 detached thread는 정리 핸들러도, 소멸자도, 버퍼 플러시도 실행하지 못한다 — fork 시 스레드 증발 과 똑같이 “하다 만 상태"로 끊긴다
  • 쓰던 파일은 깨진 채로, 잡고 있던 외부 자원(소켓, DB 연결)은 정리 없이 남는다

함정 2: 끝나기를 기다릴 방법이 없다

detach 하는 순간 그 스레드의 종료를 감지할 표준 수단(join)이 사라진다. “worker가 일을 다 마쳤는가?“를 확인할 방법이 없으므로, 프로그램 종료 시점에 안전하게 마무리시키는 것이 불가능해진다.

원칙:

  • 프로세스 수명과 얽힌 작업(파일/네트워크/공유 자원을 만지는 background worker)은 detach 금지. 종료 플래그 + join으로 수명을 명시적으로 관리한다
// 안전한 종료 패턴
atomic_bool stop = false;

void *worker(void *arg) {
    while (!atomic_load(&stop)) { /* 작업 */ }
    /* 마무리 (버퍼 플러시, 자원 해제) */
    return NULL;
}

// 종료 시:
atomic_store(&stop, true);
pthread_join(tid, NULL);   // 마무리가 끝났음을 보장받고 나서 종료 진행
  • detach가 정당한 경우는 “언제 끝나도 상관없고, 끝났는지 알 필요도 없고, 프로세스보다 확실히 먼저 끝나는” 일회성 작업 정도로 좁다
  • 같은 이유로 C++의 std::thread::detach()도 안티패턴 취급을 받으며, C++20에서 소멸 시 자동으로 stop 요청 + join을 해주는 std::jthread(+stop_token)가 도입된 배경이 바로 이것이다

1-4. pthread_self() / pthread_equal()

pthread_t me = pthread_self();
if (pthread_equal(t1, t2)) { /* 같은 스레드 */ }
  • pthread_t는 불투명 타입이므로 ==가 아니라 pthread_equal()로 비교하는 것이 이식성 있는 방법
  • pthread_self()는 pthread 라이브러리의 핸들이고, 커널이 보는 TID는 gettid() — 서로 다른 값이다

1-5. pthread_attr — 생성 속성 (std::thread에는 없는 것들)

pthread_attr_t attr;
pthread_attr_init(&attr);

pthread_attr_setstacksize(&attr, 512 * 1024);            // 스택 크기 (기본 ~8MB)
pthread_attr_setdetachstate(&attr, PTHREAD_CREATE_DETACHED);
pthread_attr_setschedpolicy(&attr, SCHED_FIFO);          // 실시간 정책
struct sched_param sp = { .sched_priority = 80 };
pthread_attr_setschedparam(&attr, &sp);
pthread_attr_setinheritsched(&attr, PTHREAD_EXPLICIT_SCHED); // ← 이거 안 하면 위 설정 무시됨!

pthread_create(&tid, &attr, worker, NULL);
pthread_attr_destroy(&attr);
  • 스택 크기: 기본 8MB(가상 메모리)라 스레드 수백 개를 만들면 가상 주소 공간을 크게 소모. 임베디드에서는 줄여서 쓰는 경우가 많다
  • PTHREAD_EXPLICIT_SCHED: 기본값이 “부모 스레드 설정 상속(INHERIT)“이라서, 이 플래그를 명시하지 않으면 policy/priority 설정이 조용히 무시된다 — 자주 당하는 함정
  • SCHED_FIFO/SCHED_RR 실시간 정책은 root 권한 또는 CAP_SYS_NICE가 필요

2. 뮤텍스 — pthread_mutex

2-1. 기본 사용

pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;   // 정적 초기화
// 또는 pthread_mutex_init(&m, &mattr);          // 동적 (속성 지정 가능)

pthread_mutex_lock(&m);      // 블록
pthread_mutex_trylock(&m);   // 못 잡으면 EBUSY 즉시 반환
pthread_mutex_timedlock(&m, &abstime); // 시한부 대기
pthread_mutex_unlock(&m);
pthread_mutex_destroy(&m);

리눅스 구현은 futex 기반이다: 경합이 없으면 유저 공간의 원자 연산만으로 처리되어 시스템 콜이 아예 발생하지 않고, 경합이 생겼을 때만 커널에 들어가 잠든다. “뮤텍스는 무겁다"는 통념과 달리 비경합 lock/unlock은 매우 싸다.

2-2. 뮤텍스 타입

pthread_mutexattr_t ma;
pthread_mutexattr_init(&ma);
pthread_mutexattr_settype(&ma, PTHREAD_MUTEX_ERRORCHECK);
pthread_mutex_init(&m, &ma);
타입재잠금(relock) 시unlock 소유자 검사용도
NORMAL (기본)데드락❌ (미정의 동작)성능 우선, 릴리즈
ERRORCHECKEDEADLK 반환✅ EPERM 반환디버깅
RECURSIVE카운트 증가 (허용)✅재귀 호출 구조. 단, 설계 냄새인 경우가 많음

추가로 알아둘 속성:

  • pthread_mutexattr_setpshared(&ma, PTHREAD_PROCESS_SHARED) — 공유 메모리(shm)에 놓고 프로세스 간 뮤텍스로 사용
  • pthread_mutexattr_setrobust(&ma, PTHREAD_MUTEX_ROBUST) — 소유 프로세스가 죽어도 다음 lock이 EOWNERDEAD로 인지하고 복구 가능. fork 시 lock 문제 처럼 “소유자가 증발하는” 상황의 방어책
  • pthread_mutexattr_setprotocol(&ma, PTHREAD_PRIO_INHERIT) — 우선순위 상속. 실시간 시스템에서 우선순위 역전(priority inversion) 방지. 임베디드 RT에서 중요 — 상세는 동기화 심화 1장

3. 조건 변수 — pthread_cond

“조건이 참이 될 때까지 잠들어 있기"를 구현하는 도구. 뮤텍스와 반드시 세트로 쓴다.

pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  cv = PTHREAD_COND_INITIALIZER;
int ready = 0;

// [소비자]
pthread_mutex_lock(&m);
while (!ready)                    // ← if가 아니라 반드시 while!
    pthread_cond_wait(&cv, &m);   // ① m을 풀고 잠듦 ② 깨어나면 m을 다시 잡고 리턴
pthread_mutex_unlock(&m);

// [생산자]
pthread_mutex_lock(&m);
ready = 1;
pthread_cond_signal(&cv);         // 하나 깨움 (broadcast는 전부)
pthread_mutex_unlock(&m);

while로 감싸야 하는 이유:

  1. spurious wakeup — 시그널 없이도 깨어날 수 있음이 표준에 명시되어 있다
  2. 깨어나서 뮤텍스를 다시 잡기까지의 틈에 다른 스레드가 조건을 도로 거짓으로 만들었을 수 있다

즉 “깨어났다"는 “조건이 참이다"를 보장하지 않으므로, 깨어날 때마다 조건을 재검사해야 한다.

  • pthread_cond_timedwait(&cv, &m, &abstime) — 절대 시각 기준 타임아웃 대기
  • signal은 조건을 바꾼 후 호출해야 하며, 뮤텍스를 잡은 채로 signal 하는 것이 안전한 기본형

5. CPU Affinity와 NUMA

5-1. pthread_setaffinity_np()

특정 스레드를 특정 CPU 코어에 고정(pinning)한다. _np는 non-portable(리눅스 확장)이라는 뜻.

#define _GNU_SOURCE
#include <pthread.h>

cpu_set_t set;
CPU_ZERO(&set);
CPU_SET(2, &set);                                    // 코어 2번만 허용
CPU_SET(3, &set);                                    // 코어 3번도 허용
pthread_setaffinity_np(tid, sizeof(set), &set);

고정하는 이유:

  • 캐시 지역성: 스레드가 코어를 옮겨 다니면 L1/L2 캐시가 매번 식는다(cache warm-up 비용)
  • 실시간성: 인터럽트/다른 작업으로부터 특정 코어를 격리(isolcpus 커널 파라미터와 조합)하고 RT 스레드를 그 코어에 고정 — 임베디드 RT의 정석 패턴
  • NUMA 지역성: 아래 참조

5-2. NUMA (Non-Uniform Memory Access)

멀티 소켓 서버나 일부 고성능 SoC에서는 메모리가 CPU 노드마다 나뉘어 붙어 있고, 어느 메모리에 접근하느냐에 따라 지연시간이 다르다.

┌─ Node 0 ──────────┐      ┌─ Node 1 ──────────┐
│ CPU 0-7           │      │ CPU 8-15          │
│   │ local (빠름)   │ QPI/ │   │ local (빠름)   │
│ Memory 0          │◄────►│ Memory 1          │
└───────────────────┘ 원격  └───────────────────┘
        Node 0의 CPU가 Memory 1을 읽으면 → remote access (1.5~2배 느림)

핵심 개념 — first-touch policy:

리눅스는 malloc() 시점이 아니라 그 페이지를 처음 만지는(touch) 스레드가 실행 중인 노드에 물리 페이지를 할당한다.

// ❌ 흔한 안티패턴: main thread가 혼자 전체 배열을 0으로 초기화
//    → 모든 페이지가 main thread가 있던 노드에 몰림
//    → 다른 노드의 worker들은 전부 remote access

// ✅ 각 worker가 자기가 쓸 영역을 직접 초기화 (first-touch를 분산)
void *worker(void *arg) {
    range_t *r = arg;
    memset(&data[r->start], 0, r->len);   // 내 노드에 페이지가 잡힘
    /* ... 이후 연산도 같은 영역 담당 ... */
}

제어 도구:

도구예시용도
numactl (CLI)numactl --cpunodebind=0 --membind=0 ./app코드 수정 없이 프로세스 전체를 노드에 묶음
libnumanuma_alloc_onnode(size, node), numa_run_on_node(node)코드에서 노드 단위 세밀 제어
numastat, lscpunumastat -p <pid>노드별 메모리 배치/remote 비율 확인

정리: NUMA 최적화의 원칙은 “연산하는 스레드와 그 스레드가 만지는 데이터를 같은 노드에“이며, 이를 위해 ① affinity로 스레드를 고정하고 ② first-touch(또는 libnuma)로 메모리를 그 옆에 놓는다. affinity 없이 NUMA 배치만 하면 스레드가 다른 노드로 옮겨가는 순간 무의미해지므로 둘은 항상 세트다.
