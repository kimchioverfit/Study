Multi Thread Image Pipeline

Multi-thread Image Pipeline — SafeQueue

condition_variable + unique_lock + move 의미론으로 만드는 3단계 이미지 파이프라인.

[Capture 1개] → SafeQueue(q_raw) → [Process 워커 2개] → SafeQueue(q_done) → [Writer 1개]

빌드: g++ -std=c++17 -pthread Multi_Thread_Image_Pipeline.cpp -o pipeline

1. 전체 코드

#include <chrono>
#include <condition_variable>
#include <cstdint>
#include <cstdio>
#include <mutex>
#include <optional>
#include <queue>
#include <thread>
#include <vector>

struct Image {
    int id = -1;
    std::vector<uint8_t> pixels;   // 실제로는 수 MB — 복사하면 안 되는 이유
};

template <typename T>
class SafeQueue {
public:
    explicit SafeQueue(size_t capacity = SIZE_MAX) : cap_(capacity) {}

    // [생산자용] 자리가 날 때까지 대기 후 push. 큐가 닫혔으면 false
    bool push(T v) {                                  // v는 파라미터 = lvalue (→ 2-4)
        std::unique_lock<std::mutex> lk(m_);          // lk는 매 호출 스택에 생성 (→ 2-3)
        not_full_.wait(lk, [&] { return q_.size() < cap_ || closed_; });
        if (closed_) return false;
        q_.push(std::move(v));                        // 버퍼 소유권만 큐로 이동 (→ 2-4)
        lk.unlock();                                  // notify 전에 unlock (→ 2-5)
        not_empty_.notify_one();
        return true;
    }

    // [소비자용] 데이터가 올 때까지 대기. 닫히고 비었으면 nullopt = 종료 신호
    std::optional<T> pop() {
        std::unique_lock<std::mutex> lk(m_);
        not_empty_.wait(lk, [&] { return !q_.empty() || closed_; });   // (→ 2-5)
        if (q_.empty()) return std::nullopt;          // closed && empty → 종료
        T v = std::move(q_.front());                  // front()는 T& = lvalue (→ 2-4)
        q_.pop();
        lk.unlock();
        not_full_.notify_one();                       // 자리 났다고 생산자에게 알림
        return v;
    }

    // [종료용] 닫고, 잠들어 있는 스레드 전원을 깨워 내보낸다
    void close() {
        {
            std::lock_guard<std::mutex> lk(m_);       // 플래그만 바꾸므로 lock_guard (→ 2-2)
            closed_ = true;
        }                                             // ← 블록 끝 = RAII unlock
        not_empty_.notify_all();                      // 대기자 전원이 나가야 하므로 all
        not_full_.notify_all();
    }

private:
    std::queue<T> q_;
    std::mutex m_;                        // 공유되는 잠금 "실체" (→ 2-3)
    std::condition_variable not_empty_;   // 소비자가 기다리는 조건
    std::condition_variable not_full_;    // 생산자가 기다리는 조건 (bounded)
    size_t cap_;
    bool closed_ = false;
};

// ---------------------------------------------------------------- stages
static SafeQueue<Image> q_raw(4);     // bounded: 카메라가 앞서가지 못하게 (→ 2-1)
static SafeQueue<Image> q_done(4);

void capture_stage(int n_frames) {
    for (int i = 0; i < n_frames; ++i) {
        Image img;
        img.id = i;
        img.pixels.assign(640 * 480, static_cast<uint8_t>(i));
        std::printf("[capture] frame %d\n", img.id);
        q_raw.push(std::move(img));               // img는 이후 moved-from 상태 (→ 2-4)
        std::this_thread::sleep_for(std::chrono::milliseconds(5));
    }
}

void process_stage(int worker_id) {
    while (auto img = q_raw.pop()) {              // nullopt(큐 닫힘)이면 루프 종료
        for (auto &px : img->pixels)
            px = static_cast<uint8_t>(255 - px);  // "처리" 흉내: 반전
        std::printf("[process %d] frame %d done\n", worker_id, img->id);
        q_done.push(std::move(*img));
    }
}

void writer_stage() {
    int count = 0;
    while (auto img = q_done.pop()) {
        std::printf("[writer] frame %d saved (%zu bytes)\n", img->id, img->pixels.size());
        ++count;
    }
    std::printf("[writer] total %d frames\n", count);
}

int main() {
    constexpr int kFrames = 20;

    std::thread cap(capture_stage, kFrames);
    std::thread w1(process_stage, 1);
    std::thread w2(process_stage, 2);
    std::thread wr(writer_stage);

    cap.join();          // 1) 생산이 끝날 때까지 대기          (→ 2-6)
    q_raw.close();       // 2) 상류 큐 닫기 → 워커들 drain 후 탈출
    w1.join();
    w2.join();           // 3) 워커 전원 종료 = 하류로 갈 데이터 없음
    q_done.close();      // 4) 하류 큐 닫기 → writer 탈출
    wr.join();

    return 0;
}

2. 설명

2-1. SafeQueue 설계 — cv 2개짜리 bounded queue

  • std::queue는 스레드 안전하지 않으므로, 모든 접근(push/pop/close)을 하나의 mutex m_ 로 감싼다
  • 조건 변수를 2개로 나눈 이유: 기다리는 조건이 두 종류이기 때문. 소비자는 “비어있지 않음”(not_empty_)을, 생산자는 “가득 차지 않음”(not_full_)을 기다린다. cv 하나로도 되지만 push가 생산자까지 깨우는 헛깨움이 생긴다
  • capacity 제한(bounded): 카메라(생산)가 처리(소비)보다 빠르면 큐가 무한정 자란다. 용량을 4로 제한하면 큐가 차는 순간 생산자가 not_full_에서 잠들어 자연스럽게 속도가 맞춰진다(backpressure) — 이미지처럼 항목 하나가 큰 파이프라인에서 필수 설계
  • 조건 변수의 기본 원리(뮤텍스와 세트로 쓰는 이유, while 재검사)는 Pthread API 3장 참고 — 이 파일은 그 C++ 표준 라이브러리 버전이다

2-2. unique_lock vs lock_guard — 둘 다 RAII, 차이는 “중간 조작”

둘 다 RAII lock이다: 생성자에서 lock을 잡고 소멸자에서 unlock하므로, return이든 예외든 어떤 경로로 스코프를 벗어나도 unlock이 보장된다. 수동 m_.lock()/unlock()이었다면 if (closed_) return false; 같은 early return마다 unlock을 챙겨야 했다 (RAII 개념: Rule of Five/Zero 서두).

lock_guardunique_lock
하는 일잡고-풀고가 전부+ 중간 unlock()/재lock(), defer/try/adopt, 이동 가능
크기/비용최소 (포인터 1개 수준)소유 상태 플래그가 추가로 필요
용도크리티컬 섹션 전체를 덮을 때 (기본값)cv 대기, 중간 unlock이 필요할 때

cv.wait()가 unique_lock만 받는 이유: wait는 “잠들 때 unlock → 깨어날 때 재lock"을 cv가 중간에 대신 해야 한다. lock_guard는 그 조작 자체가 불가능한 타입이라 쓸 수 없다.

close()에서 { } 블록으로 lock_guard의 범위를 좁힌 것도 RAII 활용이다 — 블록 끝에서 소멸자가 unlock하므로, notify_all()은 lock 밖에서 실행된다.

2-3. lk는 왜 매 호출마다 생성하는가 — 멤버 변수로 두면 안 되는 이유

push()/pop()의 lk는 호출할 때마다 그 호출의 스택에 새로 생성된다. 낭비처럼 보이지만, 역할을 나눠보면 이 방식만이 옳다.

  • m_ (mutex, 멤버) = 잠금의 실체. 큐 생성 시 한 번 만들어지고 모든 스레드가 공유한다. futex 상태, 대기열 등 커널이 아는 것은 전부 여기 있다
  • lk (unique_lock, 지역 변수) = 그 실체를 “잡았다 놓는 행위"를 감싸는 얇은 핸들. 내부는 mutex* 포인터 + “내가 잠갔나” 플래그가 전부라 생성 비용은 사실상 0이다. 실제 비용은 내부에서 일어나는 m_.lock()(경합 시)이고, 그건 어떤 구조로 짜든 지불한다

멤버 변수로 두면 생기는 문제 1 — 인스턴스 수명 = lock 수명:

class SafeQueue {
    std::mutex m_;
    std::unique_lock<std::mutex> lk_{m_};   // ❌ 생성자에서 즉시 lock
};

unique_lock은 생성 시 lock을 잡으므로, 큐가 만들어지는 순간 잠기고 큐가 파괴될 때까지 풀리지 않는다. 다른 스레드의 첫 push/pop이 영원히 블록된다. (std::defer_lock으로 잠그지 않고 만들어두는 회피는 가능하다 — 하지만 아래 문제가 남는다.)

문제 2 — 회피해도 남는 근본 문제: lock 핸들 자체의 데이터 레이스:

defer_lock으로 바꾸고 매 호출 lk_.lock()/unlock()을 수동으로 한다 해도, 워커 2개가 동시에 pop()에 들어오면 둘 다 같은 lk_ 객체의 내부 상태(소유 플래그)를 동기화 없이 읽고 쓴다. 이것 자체가 데이터 레이스(UB)다 — “lock을 관리하는 객체를 보호할 lock이 또 필요한” 모순. A가 잡은 lock을 B가 자기 것인 줄 알고 unlock하는 사고도 가능하다.

부수적으로:

  • 매 호출 RAII 보장(어떤 리턴 경로든 자동 unlock)이 사라지고 수동 관리로 회귀
  • cv.wait(lk_)가 wait 중에 lk_를 unlock/재lock하는 동안 다른 스레드가 같은 lk_를 조작하면 상태가 꼬임

결론: 공유해도 되는 것은 mutex(실체)뿐이고, lock 핸들은 반드시 각 스레드의 스택에(호출마다) 있어야 한다. 스택은 스레드마다 독립이므로(Memory_Layout 4장) 지역 변수 lk는 공짜로 스레드-로컬이 된다. 비유하면 m_은 문에 달린 자물쇠(하나), lk는 각자 손에 쥐는 열쇠(호출마다)다.

2-4. std::move(v)가 성립하는 이유 — lvalue와의 관계

push(T v)의 파라미터 v는 “이름이 있는 변수"이므로, 호출자가 rvalue를 넘겼더라도 함수 안에서는 lvalue다 (이름으로 여러 번 참조할 수 있는 존재는 전부 lvalue).

  • lvalue를 그냥 q_.push(v) 하면 복사 오버로드(push(const T&))가 선택된다 — 픽셀 버퍼 전체 복사
  • std::move(v)는 “이 lvalue를 rvalue로 취급하라"는 캐스팅일 뿐, 그 자체로는 아무것도 옮기지 않는다. 실제 이동은 그 rvalue를 받은 push(T&&) → Image의 이동 생성자(내부적으로 vector의 포인터 스틸)가 수행한다
  • move는 “여기서부터 v를 다시 쓰지 않겠다"는 약속이다. move 후의 원본은 비어있지만 소멸은 안전한 상태(moved-from) — capture의 img가 그렇다
  • pop()의 std::move(q_.front())도 같은 이유: front()는 T&(lvalue 참조)를 반환하므로 그대로 대입하면 복사 생성이다. 어차피 바로 pop()으로 버릴 원소라 move로 훔쳐온다

이동 생성자가 어떻게 “훔치고 원본을 무해화"하는지는 Rule of Five 4장 참고.

2-5. wait의 predicate와 unlock-후-notify

not_empty_.wait(lk, [&] { return !q_.empty() || closed_; });
// 위는 아래와 동일:
while (!(!q_.empty() || closed_))
    not_empty_.wait(lk);
  • predicate 버전 = while 재검사 내장. spurious wakeup(신호 없이 깨어남)이나, 깨어나서 lock을 재획득하기까지의 틈에 다른 소비자가 먼저 꺼내 간 경우에도 조건을 다시 확인하고 도로 잠든다
  • lk.unlock() 후에 notify_one() 하는 순서: 깨어난 스레드가 wait에서 나오려면 lock을 재획득해야 하는데, notify하는 쪽이 아직 lock을 쥐고 있으면 깨자마자 다시 블록되는 낭비가 생긴다. 먼저 풀고 알리는 것이 정석
  • close()만 notify_all()인 이유: 평상시엔 데이터 1개 = 소비자 1명이면 되지만(one), 종료 시엔 잠들어 있는 전원이 일어나서 nullopt를 받고 나가야 하므로(all)

2-6. 우아한 종료 — 종료 순서가 곧 파이프라인 설계

pop()이 std::optional을 반환하는 것이 종료 프로토콜의 핵심이다: “큐가 닫혔고 비었다"일 때만 nullopt 를 주므로, close 시점에 큐에 남아있던 프레임은 소비자가 마저 꺼내 간다(drain 후 종료 — 데이터 유실 없음).

cap.join();          // 1) 생산 완료 보장
q_raw.close();       // 2) 상류 닫기 → 워커: 남은 것 처리 후 pop()==nullopt로 탈출
w1.join(); w2.join();// 3) 워커 전원 종료 = 이후 q_done에 새 데이터 없음이 보장됨
q_done.close();      // 4) 하류 닫기 → writer 탈출
wr.join();

순서를 어기면(예: 워커 join 전에 q_done.close()) 워커가 닫힌 큐에 push하다 실패해 프레임이 유실된다. 상류부터 하류로, “생산 완료 확정 → 닫기 → 소비자 join"을 단계마다 반복하는 것이 다단계 파이프라인 종료의 일반 패턴이다.

다른 종료 방식으로는 poison pill(종료 표시용 특수 아이템을 큐에 넣기)이 있다 — 소비자 수만큼 넣어야 하는 관리 부담이 있어, close 플래그 방식이 보통 더 깔끔하다.
