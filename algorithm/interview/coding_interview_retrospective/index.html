    Coding Interview Retrospective

    코딩 인터뷰 회고: 문제를 풀기 전에 문제를 고정해야 함

    1. 들어가며

    최근 한 코딩 인터뷰에서 기대했던 만큼의 퍼포먼스를 내지 못했음.

    면접이 끝난 뒤 한동안 꽤 큰 아쉬움과 짜증이 남았음. 단순히 어려운 문제를 못 풀어서라기보다는, 문제를 처음 들었을 때 어느 정도 맞는 방향을 떠올렸음에도 불구하고, 인터뷰 중간에 스스로 그 방향을 버리고 흔들렸다는 점이 가장 아쉬웠음.

    시간이 지나고 다시 생각해보니, 이 경험은 특정 문제를 못 푼 사건이라기보다 불명확한 상황에서 문제를 고정하지 못한 실패에 가까웠음.

    이 글은 그 경험을 정리하고, 다음 인터뷰에서 반복하지 않기 위한 회고임.

    2. 무엇이 어려웠나

    이번 인터뷰에서 가장 어려웠던 부분은 알고리즘 자체보다 문제 조건을 안정적으로 붙잡는 것이었음.

    문제는 구두로 설명되었고, 나는 그 조건을 머릿속으로만 정리한 상태에서 풀이를 시작했음. 처음에는 특정 접근이 가능할 것 같다고 생각했지만, 면접관의 질문을 듣고 내가 문제를 잘못 이해했거나 접근 자체가 틀린 것처럼 느꼈음.

    그 순간부터 문제 풀이보다 다음 생각들이 머릿속을 차지하기 시작했음.

    • 내가 문제를 잘못 이해했나?
    • 내 접근이 완전히 틀린 건가?
    • 지금 brute force부터 다시 가야 하나?
    • 샘플이 내가 이해한 조건과 맞는 건가?

    이 상태에서는 간단한 구현도 쉽게 흔들림. 실제로 나는 이후 더 안전하다고 생각한 단순 접근으로 후퇴했지만, 문제 조건이 머릿속에서 확실히 고정되지 않은 상태였기 때문에 구현에서도 실수가 발생했음.

    결과적으로 제한 시간 동안 충분한 signal을 보여주지 못했음.

    3. 실패의 핵심 원인

    이번 경험을 단순히 “쉬운 문제를 못 풀었다"로 정리하면 부정확함.

    더 정확한 원인은 다음과 같음.

    3.1 문제 statement를 직접 고정하지 않았음

    문제가 구두로만 주어졌다면, 내가 먼저 shared editor에 문제 조건을 내 말로 적고 확인했어야 했음.

    예를 들면 다음과 같은 형태임.

    Given:
- input condition
- target output
- valid answer condition
- edge cases
- return format

    그리고 면접관에게 바로 확인했어야 했음.

    Let me restate the problem in my own words first to make sure I understood it correctly.

    이 과정을 생략한 상태로 바로 풀이에 들어가면, 나중에 면접관의 질문이나 샘플 설명이 조금만 달라져도 문제 정의 전체가 흔들림.

    이번에 내가 겪은 일이 정확히 그랬음.

    3.2 면접관의 질문을 “검증 요청"이 아니라 “부정"으로 받아들였음

    면접관이 내 접근에 대해 질문했을 때, 나는 그것을 “이 접근은 틀렸다"는 신호처럼 받아들였음.

    하지만 기술 인터뷰에서 면접관의 질문은 반드시 부정이 아님. 오히려 다음 중 하나일 수 있음.

    • 내 접근의 근거를 설명해보라는 요청
    • 시간 복잡도를 줄일 수 있는지 묻는 힌트
    • edge case를 확인하려는 질문
    • correctness proof를 요구하는 질문

    즉, 질문을 받았다고 해서 곧바로 접근을 버릴 필요는 없음. 먼저 내가 이해한 문제와 알고리즘의 타당성을 분리해서 확인했어야 했음.

    Let me separate two things:
Are we questioning my understanding of the problem, or the validity of this approach?

    이 한 문장을 말하지 못한 것이 아쉬움.

    3.3 알고리즘 이름보다 invariant를 설명했어야 했음

    처음 떠올린 접근 자체는 완전히 엉뚱한 방향은 아니었음. 하지만 나는 그 접근을 알고리즘 이름이나 직감 수준으로만 설명했고, 왜 그 방식이 안전한지 충분히 말하지 못했음.

    코딩 인터뷰에서는 “무슨 알고리즘인지"보다 다음이 더 중요함.

    • 내가 유지하는 상태가 무엇인지
    • 그 상태가 왜 유효한지
    • 어떤 조건에서 상태를 업데이트하는지
    • 그 업데이트가 왜 정답을 놓치지 않는지

    즉, invariant를 말해야 함.

    앞으로는 특정 알고리즘명을 말하기 전에, 다음 형식으로 설명하려고 함.

    I maintain a candidate state.
At each step, I remove or update only the part that can no longer lead to a valid answer.
This is safe because ...

    이런 식으로 설명하면 면접관이 알고리즘 이름을 어떻게 분류하든, 풀이의 본질을 전달할 수 있음.

    3.4 문제 이해가 흔들리는 상태에서 코딩을 시작했음

    문제 조건이 완전히 고정되지 않은 상태에서 코딩을 시작하면, 구현은 거의 항상 흔들림.

    이번에도 그랬음.

    구현 중에 계속 다음 생각이 들었음.

    • 이 조건을 이렇게 체크하는 게 맞나?
    • 출력은 이게 맞나?
    • 이 샘플에서 왜 이 값이 나오는 거지?
    • 내가 아까 들은 조건과 다른가?

    이 상태에서는 인덱스 실수, 조건문 실수, edge case 누락이 쉽게 발생함.

    이번 인터뷰에서의 구현 실수는 단순한 코딩 실수라기보다, 문제 정의를 안정적으로 고정하지 못한 결과에 가까웠음.

    4. 다음 인터뷰에서 적용할 원칙

    이번 경험을 통해 다음 원칙을 남기기로 했음.

    원칙 1. 구두로 받은 문제는 반드시 직접 적음

    문제가 텍스트로 제공되지 않으면, 내가 직접 shared editor에 적음.

    Let me first write down my understanding of the problem.

    적어야 할 항목은 다음과 같음.

    • input
    • output
    • valid answer condition
    • constraints
    • return format
    • edge cases

    이 작업은 시간 낭비가 아님. 오히려 뒤에서 20분을 잃지 않기 위한 보험임.

    원칙 2. 예시를 직접 만들어 확인함

    문제 조건이 애매하면, 면접관이 준 예시만 따라가지 말고 내가 작은 예시를 하나 만듦.

    For example, would this be a valid answer?

    직접 만든 예시를 통해 조건을 확인하면, 내가 문제를 제대로 이해했는지 빠르게 검증할 수 있음.

    특히 다음 조건들은 반드시 확인함.

    • 기준이 전체 입력인지 부분 구조인지
    • 하나만 만족하면 되는지 모두 만족해야 하는지
    • any valid answer인지, 특정 최적값을 요구하는지
    • index를 반환하는지 value를 반환하는지
    • 답이 없을 때 무엇을 반환하는지

    원칙 3. 면접관의 질문을 받았다고 바로 접근을 버리지 않음

    면접관이 질문을 던졌을 때 바로 “내가 틀렸나 보다"라고 생각하지 않음.

    먼저 이렇게 대응함.

    Good question. Let me explain why I think this condition can be checked efficiently.

    또는:

    Maybe I used the wrong label for the approach. Let me describe the invariant instead.

    질문을 받았을 때 중요한 건 방어적으로 후퇴하는 것이 아니라, 내 접근의 근거를 명확히 설명하는 것임.

    원칙 4. 알고리즘명보다 불변식을 말함

    앞으로는 “이건 two pointers 같습니다”, “이건 BFS 같습니다"처럼 이름만 먼저 말하지 않으려고 함.

    대신 다음 순서로 말함.

    1. 어떤 상태를 유지하는가
    2. 그 상태를 어떻게 업데이트하는가
    3. 그 업데이트가 왜 안전한가
    4. 언제 답을 반환하는가

    알고리즘 이름은 그 다음에 붙여도 됨.

    원칙 5. 샘플이 이상하면 즉시 멈춤

    샘플이나 드라이런이 내가 이해한 조건과 맞지 않는 것처럼 보이면, 그냥 넘어가지 않음.

    This seems inconsistent with my understanding of the condition.
Could we clarify the expected output before I continue?

    이 질문을 하는 것은 공격이 아님. 문제 정의를 고정하기 위한 정상적인 clarification임.

    이 단계를 생략하면 이후 구현과 디버깅이 모두 흔들림.

    5. 이번 경험에서 얻은 결론

    이번 인터뷰는 만족스럽지 않았음. 아쉬움도 컸고, 화도 났음.

    하지만 이번 실패를 단순히 “나는 쉬운 문제도 못 푼다"로 해석하지 않으려고 함.

    더 정확한 해석은 다음과 같음.

    나는 처음에 어느 정도 맞는 방향을 잡았음. 하지만 문제 조건을 직접 고정하지 못했고, 면접관의 질문을 접근에 대한 부정으로 받아들였음. 그 결과 원래 방향을 유지하지 못하고 후퇴했음. 문제 정의가 흔들리는 상태에서 구현하다 보니 실수도 발생했음.

    즉, 이번 실패는 알고리즘 지식 하나의 문제가 아니라, 불명확한 인터뷰 상황에서 문제를 안정화하고 내 접근을 방어하는 루틴의 문제였음.

    이건 고칠 수 있음.

    다음 인터뷰에서는 문제를 듣자마자 먼저 적음. 조건을 확인함. 작은 예시를 만듦. 알고리즘 이름보다 invariant를 설명함. 면접관의 질문을 접근 부정으로 받아들이기 전에, 무엇을 검증하려는 질문인지 분리함.

    이번 경험은 좋지 않았지만, 남길 교훈은 분명함.

    문제를 풀기 전에, 먼저 문제를 고정해야 함.
