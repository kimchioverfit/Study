    Dimension (d_model)

    Dimension — 토큰 하나를 몇 개의 숫자로 표현할까

    결론부터 아주 쉽게: 토큰 하나를 길이 $d$ 인 벡터로 표현하는데, 그 $d$ 가 dimension임. 학습으로 정해지는 값이 아니라 모델 설계자가 직접 정하는 하이퍼파라미터임. 학습되는 건 벡터의 값이지 길이가 아님. 키우면 표현력이 늘지만 공짜가 아니고, 이미지에서는 차원을 키워도 패치 단계에서 이미 잃은 것은 돌아오지 않음.

    1. 무엇을 가리키나

    토큰 하나가 임베딩 을 거치면 숫자 $d$ 개짜리 벡터가 됨. 그 $d$ 임.

    "학교"  →  ID 630  →  [0.23, 0.17, −0.08, …, 0.05]
                       └──────── d개 ────────┘

    문서·논문마다 부르는 이름이 다른데 전부 같은 것임.

    이름쓰는 곳
    $d_{model}$Attention Is All You Need
    Hidden size $D$ViT , BERT
    embedding dim구현 코드
    width스케일링 논문들

    이 값 하나가 모델 전체에 박힘.

    • 임베딩 행렬 이 $(\text{vocab\_size} \times d)$
    • Q/K/V 가중치 가 $(d \times d_k)$
    • FFN 이 $d \to 4d \to d$
    • residual로 더해야 하므로 모든 블록의 입출력 shape가 $d$ 로 고정됨

    그래서 한 번 정하면 중간에 바꿀 수 없음.

    2. 누가 정하나 — 설계자가 정함

    가장 헷갈리는 지점임. 임베딩 문서 에서 본 것처럼 임베딩 행렬 $W$ 의 값은 학습으로 정해지지만, 그 행렬의 크기는 학습 전에 사람이 정함.

    정하는 주체대상
    설계자$d$, 레이어 수 $L$, head 수 $h$, vocab size
    학습$W$ 안의 숫자들, 각 가중치 행렬의 값

    즉 $d$ 는 학습이 찾아주는 값이 아니라 설계 결정임. 모델을 만들기 전에 정해서 구조에 박아 넣는 것이고, 학습이 끝난 뒤에는 사전학습 가중치와 한 몸이라 바꿀 수 없음. 다른 $d$ 를 쓰고 싶으면 처음부터 다시 학습해야 함.

    실제 모델들이 고른 값임.

    모델$d$레이어head파라미터
    Transformer base5126865M
    Transformer big1024616213M
    ViT-Base768121286M
    ViT-Large10242416307M
    ViT-Huge12803216632M

    $d$ 를 정하면 나머지가 따라옴 — head 하나의 차원을 64로 두는 것이 관례라 $h = d/64$ 로 잡고, FFN 내부 차원은 $4d$ 로 둠. 위 표의 숫자들이 실제로 그 관례를 따르고 있음.

    3. 키우면 무엇이 좋아지고 무엇이 나빠지나

    키울 때
    표현력토큰 하나에 담을 수 있는 정보가 늘어남. 스케일링 관점에서 성능이 올라감
    파라미터$d^2$ 에 비례해 늘어남 — 블록 하나에 attention $4d^2$ + FFN $8d^2$. $d$ 를 2배로 하면 파라미터는 4배
    메모리·지연시간같이 늘어남. 추론 비용이 직접 오름
    데이터 요구량커진 용량을 채울 데이터가 없으면 과적합함

    $d$ 를 키우는 것은 “성능을 산다"가 아니라 “연산·메모리·데이터를 성능과 바꾼다” 에 가까움.

    시퀀스 길이 $n$ 과 헷갈리지 말 것. attention 비용은 $O(n^2 \cdot d)$ 이라 길이에는 제곱, 차원에는 선형임. 파라미터 수는 반대로 $d$ 에 제곱으로 늘고 $n$ 과는 무관함.

    4. ViT에서 — 이론과 실제가 갈리는 지점

    이론상으로는 $d$ 가 클수록 좋음. ViT-Base(768) → Large(1024) → Huge(1280)로 갈수록 정확도가 올라가고, 이것이 ViT 논문의 핵심 주장 중 하나임.

    그런데 도메인에 따라 그대로 적용되지 않음. 두 가지 이유가 있음.

    4.1 데이터가 받쳐줘야 함

    ViT는 CNN이 가진 inductive bias(지역성, 2D 구조)가 없어서, 그것을 데이터로 대신 배워야 함. 그래서 ImageNet-1k 정도 규모에서는 큰 ViT가 오히려 같은 크기의 CNN보다 나빴고, JFT-300M 급으로 가야 뒤집혔음. 자세한 내용은 ViT §4 .

    작은 데이터셋을 쓰는 도메인이라면 $d$ 를 키우는 것이 손해일 수 있음.

    4.2 작은 객체는 차원으로 해결되지 않음

    이쪽이 더 중요한 한계임. $d$ 를 아무리 키워도 작은 물체는 여전히 묻힘. 원인이 차원이 아니라 패치 크기와 단일 해상도에 있기 때문임.

    224×224 이미지, 패치 16×16
        ↓
14×14 = 196개 토큰

16픽셀보다 작은 물체  →  패치 한 칸 안에서 배경과 뒤섞임

    패치 임베딩은 $16\times16\times3 = 768$ 개 픽셀값을 $d$ 차원 벡터 하나로 선형 사상함. 차원 숫자만 보면 ViT-Base는 768 → 768 이라 줄어들지도 않지만, 문제는 그 이후 모든 연산이 패치를 한 덩어리로 다룬다는 점임. 패치 안에서 물체가 어디 있었는지, 배경과 어떻게 나뉘는지는 더 이상 구분되지 않음.

    $d$ 를 1280으로 키워도 이 구분은 돌아오지 않음. 이미 뭉쳐진 정보를 넓은 그릇에 담을 뿐임.

    게다가 ViT는 처음부터 끝까지 같은 해상도(14×14 토큰)와 같은 차원을 유지 함. CNN처럼 1/4 → 1/8 → 1/16으로 내려가는 피라미드가 없어서, 작은 물체를 살릴 고해상도 단계 자체가 없음.

    그래서 실제로 효과가 있는 쪽은 차원이 아니라 이것들임.

    방법효과비용
    패치를 작게 (/16 → /14, /8)토큰이 늘어 세밀해짐attention이 $O(n^2)$ 이라 비용 급증
    입력 해상도를 올림같은 패치 크기로도 토큰이 늘어남위와 같음
    다중 스케일 도입 (Swin, FPN 계열)작은 물체에 직접 효과구조가 복잡해짐
    $d$ 를 키움작은 물체에는 거의 도움 안 됨파라미터 $d^2$

    이 저장소의 EoMT 정리에도 같은 관찰이 있음 — plain ViT로 다중 스케일 장치를 걷어냈을 때 instance segmentation 손실이 상대적으로 더 컸고, 작은 물체에는 다중 스케일이 여전히 도움이 되는 것으로 보임.

    정리하면, 위성·의료·결함 검사처럼 작은 객체가 중요한 도메인에서는 $d$ 를 키우는 것보다 패치 크기·입력 해상도·다중 스케일을 먼저 건드리는 것이 맞음. “차원이 깊을수록 좋다"는 일반론이 도메인에 따라 뒤집히는 대표적인 경우임.

    5. 정할 때의 기준

    새로 설계하는 경우가 아니라면 대부분 이미 정해진 값을 물려받음. 사전학습 체크포인트를 쓰는 순간 $d$ 는 고정이고, 선택지는 “어떤 체크포인트를 쓸까"로 바뀜.

    직접 정해야 한다면:

    • $d/h = 64$ 를 맞춤 (head 하나가 64차원)
    • FFN 내부는 $4d$ (SwiGLU를 쓰면 $\tfrac{8}{3}d$)
    • $d$ 는 보통 64의 배수로 둠 — GPU 연산이 그쪽에 최적화돼 있음
    • 데이터 규모를 먼저 보고 정함. 데이터가 적으면 $d$ 를 키우는 것이 손해임
