4.Faster R CNN

Faster R-CNN (2015)

📄 논문: Faster R-CNN: Towards Real-Time Object Detection with Region Proposal Networks — Ren et al., NeurIPS 2015

Region Proposal Network(RPN) 도입으로 region proposal 생성까지 신경망 안에 통합한 모델. Selective Search라는 외부의, CPU 기반, 학습되지 않는 느린 알고리즘을 제거하고, 이미 계산된 conv feature map을 재사용해 proposal을 만든다 — 그 결과 파이프라인 전체가 GPU 위에서 end-to-end로 돌아가는, 처음으로 실시간에 가까운 detector가 됐다. Fast R-CNN 까지 이어진 R-CNN 계열의 마지막 개선 단계이며, 여기서 도입된 RPN + Anchor 개념은 이후 Mask R-CNN 에도 그대로 이어진다.

🔷 1. 이 논문 이전까지 남아있던 문제

R-CNN → Fast R-CNN 을 거치며 “detection 자체"는 크게 빨라졌지만, 파이프라인에는 병목이 하나 남아 있었다.

[Fast R-CNN 파이프라인]

  원본 이미지
     │
     ├──────────────► Selective Search (CPU, 이미지당 ~2초)  ← 병목! 학습 안 되는 고정 알고리즘
     │                       │
     ▼                       ▼
   CNN (GPU, 빠름)      Region Proposals (~2000개)
     │                       │
     └───────► ROI Pooling ◄─┘
                  │
                  ▼
        Classification + BBox Regression
  • Selective Search는 학습되지 않는 고정된 규칙 기반 알고리즘이라, CNN 부분이 아무리 GPU에서 빨라져도 이 부분만은 여전히 CPU에서 이미지당 약 2초씩 걸린다
  • 결과적으로 detection 파이프라인 전체 속도가 “가장 느린 부품"인 Selective Search에 발목 잡힌다 — Fast R-CNN이 아무리 개선돼도 이 병목 자체는 그대로 남아 있었다

🔷 2. 핵심 아이디어 — RPN으로 Selective Search를 대체

Faster R-CNN의 발상은 단순하지만 강력하다.

“이미 CNN이 detection을 위해 feature map을 계산해뒀는데, 그 feature map을 그냥 재활용해서 proposal도 뽑으면 안 되나?”

[Faster R-CNN 파이프라인]

  원본 이미지
     │
     ▼
   CNN (한 번만 통과, GPU)
     │
     ├──────► RPN (같은 feature map 재사용, GPU) ──► Region Proposals
     │                                                    │
     └───────────────► ROI Pooling ◄─────────────────────┘
                  │
                  ▼
        Classification + BBox Regression
  • RPN(Region Proposal Network): proposal 생성을 별도의 외부 CPU 알고리즘이 아니라, detection용으로 이미 계산된 conv feature map 위에서 작은 신경망으로 수행한다
  • Selective Search와 CNN을 나란히(따로) 돌리던 구조에서, feature map 하나를 detection과 proposal 생성이 공유하는 구조로 바뀐 것 — 논문 표현으로는 “region proposal이 거의 공짜(nearly cost-free)가 됐다”
  • 전체가 GPU 위에서 end-to-end로 돌아가면서, Fast R-CNN 대비 훨씬 빨라진다 (§7 참고)

🔷 3. Anchor Box — “후보 박스 모양"을 미리 준비해두는 방법

RPN이 “여기에 물체가 있을 것 같다"를 예측하려면, 먼저 어떤 모양의 박스들을 후보로 놓고 볼지 기준이 필요하다. 이 기준 박스가 Anchor(앵커) box다.

feature map의 각 위치(sliding window 중심)마다:

        ┌───────┐
        │ ┌───┐ │     3가지 스케일(작음/중간/큼)
        │ │┌─┐│ │   ×  3가지 가로세로비(1:1, 1:2, 2:1)
        │ │└─┘│ │   =  9개의 Anchor를 동시에 배치
        └───────┘
  • feature map의 모든 위치마다 미리 정해둔 여러 크기·비율의 anchor를 촘촘히 깔아둔다 (보통 3 scale × 3 ratio = 9개)
  • 예: 800×600 이미지라면 feature map 위 각 위치마다 9개씩, 총 약 20,000개의 anchor가 생긴다
  • RPN이 실제로 학습하는 것은 “이 anchor를 그대로 써라"가 아니라, “이 anchor를 기준으로 물체가 있는지 없는지” + “정확한 박스가 되려면 이 anchor를 얼마나 옮기고 늘려야 하는지” 두 가지다 — 즉 anchor는 정답이 아니라 결과물을 만들어내기 위한 기준점(reference) 역할을 한다

🔷 4. RPN의 구조 — 작은 CNN 하나가 두 가지를 동시에 예측

RPN 자체는 거창한 별도 네트워크가 아니라, feature map 위에서 3×3 conv 하나 + 1×1 conv 두 갈래로 구성된 아주 작은 신경망이다.

              conv feature map
                    │
              3×3 conv (sliding window)
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
  1×1 conv (cls)           1×1 conv (reg)
  → 2k개 출력               → 4k개 출력
  (objectness: 물체 있음/없음)  (anchor 대비 박스 보정값 dx,dy,dw,dh)
출력의미개수(anchor 9개 기준)
cls (classification)이 anchor에 물체가 있는지 없는지(objectness) — 클래스가 무엇인지는 아직 모름anchor당 2개 → 9×2=18
reg (regression)anchor를 실제 물체 박스에 맞게 옮기고 늘리는 보정값 $(dx, dy, dw, dh)$anchor당 4개 → 9×4=36
  • RPN은 “이게 사람이다/자동차다” 같은 클래스 분류는 하지 않는다. 오직 “물체 O/X"만 판단하며, 실제 클래스 분류는 뒤쪽 Fast R-CNN detection head가 담당한다
  • 이 두 브랜치가 같은 conv feature map을 공유하기 때문에, Selective Search처럼 이미지를 별도로 다시 처리할 필요 없이 detection과 proposal이 동시에 계산된다

🔷 5. 학습 — Anchor에 정답을 어떻게 매기나

RPN을 학습시키려면 각 anchor가 “정답(물체 있음)“인지 “오답(배경)“인지 라벨을 매겨야 한다. 기준은 IoU(Intersection over Union).

Anchor 분류조건
Positive (물체 있음)실제 물체 박스와 IoU > 0.7, 또는 그 물체와 IoU가 가장 높은 anchor
Negative (배경)모든 실제 물체 박스와 IoU < 0.3
무시애매한 중간 지대(0.3~0.7) — 학습에서 제외
  • Multi-task loss: Fast R-CNN 과 같은 철학으로, 분류 loss(물체 O/X) + 회귀 loss(박스 보정) 를 한 번에 학습시킨다. 회귀 loss는 positive anchor에서만 계산한다 (배경은 애초에 맞출 박스가 없으므로)
  • 학습 방식: RPN과 detection head가 conv layer(backbone)를 공유해야 하는데, 이 둘을 동시에 학습시키면 서로의 gradient가 얽혀 불안정해질 수 있다. 그래서 원 논문은 4단계 번갈아 학습(alternating training) 을 사용했다 (RPN 학습 → 그 proposal로 detector 학습 → detector의 conv로 RPN 재학습 → detector 미세조정). 이후 구현들에서는 근사 joint training(두 loss를 한 번에 역전파, 일부 gradient는 근사 처리)으로 단순화되어 지금은 이쪽이 표준이다
  • RPN과 detector가 공유하는 conv layer(=backbone)는 처음부터 학습시키지 않고, ImageNet으로 미리 학습된 모델(VGG, ResNet 등)로 초기화한 뒤 fine-tuning만 한다 — backbone을 처음부터 학습하면 시간도 오래 걸리고 데이터도 훨씬 많이 필요하기 때문 (일반적인 전이학습(transfer learning) 관행)

🔷 6. Anchor 20,000개 → 실제로 쓰는 건 수백 개 (NMS)

Anchor를 다 쓰면 이미지 하나에 2만 개나 되므로, 이걸 그대로 detection head에 넘기면 오히려 비효율적이다. 그래서:

  1. RPN이 예측한 objectness 점수로 anchor들을 정렬한다
  2. 상위 N개만 남기고, NMS(Non-Maximum Suppression) 로 서로 많이 겹치는 박스를 제거한다
  3. 학습 시엔 top ~2000개, 테스트(추론) 시엔 top ~300개 정도만 실제 region proposal로 골라 Fast R-CNN 의 ROI Pooling 단계로 전달한다

🔷 7. 결과 — Selective Search 제거의 실질적 효과

모델Region Proposal 방식속도(대략)
R-CNNSelective Search (CPU)~47초/이미지
Fast R-CNNSelective Search (CPU)~2초/이미지 (대부분이 Selective Search 시간)
Faster R-CNNRPN (GPU, feature 공유)~0.2초/이미지 (5fps 이상)
  • Selective Search를 RPN으로 바꾼 것만으로 detection 파이프라인이 처음으로 거의 실시간(near real-time)에 도달했다
  • 정확도(mAP)도 Selective Search 대비 근소하게 향상됐다 — RPN은 학습 가능한 proposal 생성기라서, 고정된 규칙(Selective Search)보다 데이터에 맞는 더 나은 proposal을 만들어내기 때문

🔷 8. 정리 — 한 문장씩

질문답
뭘 없앴나Selective Search (CPU, 학습 안 됨, 느림)
뭘로 대체했나RPN (GPU, 학습됨, feature map 공유)
RPN이 예측하는 것anchor별 “물체 O/X” + “박스 보정값” — 클래스는 예측하지 않음
Anchor란feature map 위 각 위치마다 미리 깔아둔 여러 크기/비율의 기준 박스 (보통 9개)
왜 빨라졌나detection과 proposal 생성이 같은 conv 연산 결과를 재사용하기 때문
어떻게 학습하나IoU 기준으로 anchor에 정답 라벨을 매기고, multi-task loss(분류+회귀)로 학습

참고

  • Anchor의 scale/ratio 하이퍼파라미터는 데이터셋의 물체 크기 분포에 따라 성능에 큰 영향을 준다 — 실전에서 튜닝이 필요한 대표적인 지점
  • 이후 Mask R-CNN 은 이 RPN + Anchor 구조를 그대로 가져오고, ROI Pooling을 ROI Align으로 바꿔 마스크 예측까지 확장한다
