EfficientFormer

EfficientFormer — Vision Transformers at MobileNet Speed (2022)

📄 논문: EfficientFormer: Vision Transformers at MobileNet Speed — Yanyu Li et al. (Snap Inc. & Northeastern University), NeurIPS 2022 · 공식 구현

결론부터 아주 쉽게: “ViT가 모바일에서 느린 진짜 이유를 실제 기기에서 하나씩 측정해서 찾아내고, 그 병목들을 전부 걷어낸 순수 트랜스포머 구조를 만든 논문.” 그 결과 EfficientFormer-L1이 iPhone 12에서 1.6 ms에 ImageNet top-1 79.2% — MobileNetV2 ×1.4와 같은 속도로 4.5%p 더 정확하다. ViT 와 Attention Is All You Need 의 self-attention 개념을 먼저 보고 오면 읽기 수월하다.

🔷 1. 문제의식 — ViT는 왜 모바일에서 느린가

ViT 이후 트랜스포머 기반 비전 모델은 정확도에서 CNN을 앞질렀지만, 실제 기기(on-device)에서는 여전히 CNN이 압도적으로 빠르다.

모델ImageNet top-1iPhone 12 지연시간
MobileNetV2 ×1.071.8%1.3 ms
DeiT-Small (ViT 계열)81.2%11.8 ms

정확도는 9%p 높지만 9배 느리다. 실시간 카메라 필터, AR, 온디바이스 추론 같은 응용에서는 쓸 수 없는 수준.

이 논문이 던지는 핵심 질문

“Can transformers run as fast as MobileNet while obtaining high performance?” (트랜스포머가 MobileNet 속도로 돌면서 높은 성능을 낼 수 있는가?)

그리고 가장 중요한 전제

MACs(연산량)와 파라미터 수는 실제 지연시간(latency)과 잘 맞지 않는다.

기존 경량화 논문들이 “GFLOPs를 줄였다"고 주장해도, 실제 폰에 올리면 안 빨라지는 경우가 허다하다. Reshape, permute, normalization, 활성함수처럼 연산량은 거의 0인데 시간은 오래 걸리는 연산이 많기 때문이다.

그래서 이 논문은 iPhone 12 + CoreML에서 직접 측정한 실측 지연시간을 설계 기준으로 삼는다.

🔷 2. 기존 접근과 무엇이 다른가

당시 모바일용 ViT 접근은 대부분 하이브리드(CNN + Transformer) 였다.

모델방식남은 문제
MobileViTMobileNet 블록 사이에 트랜스포머 블록을 끼워넣음4D(conv) ↔ 3D(attention) 텐서 변환이 반복 → reshape 비용
LeViTCNN stem + attention, attention도 conv로 구현마찬가지로 차원 변환이 잦음
PoolFormer / MetaFormerattention 대신 pooling을 token mixer로 사용전역(global) 정보 모델링 능력 포기

EfficientFormer의 주장은

“attention 자체가 느린 게 아니다. 차원이 계속 바뀌는(reshape) 설계가 느린 것이다.”

그래서 하이브리드 블록을 쓰지 않고, 차원이 일관된(dimension-consistent) 순수 트랜스포머 구조를 설계한다.

🔷 3. On-Device Latency 분석 — 4가지 관찰

논문의 실질적인 핵심. iPhone 12(A14 Bionic, CoreML)에서 연산자 단위로 측정해 얻은 결론들이다.

관찰 1. Patch embedding의 큰 커널 / 큰 stride가 병목이다

ViT는 이미지를 16×16 패치로 자를 때 kernel=16, stride=16 conv 하나를 쓴다. 연산량은 작지만, 모바일 가속기(NPU)는 이런 비표준 큰 커널을 잘 지원하지 못해 CPU로 fallback 되며 크게 느려진다.

✅ 해결: stride 2짜리 3×3 conv 두 개로 대체 (hardware-efficient한 conv stem)

관찰 2. MHSA 자체는 생각보다 비싸지 않다 — reshape가 비싸다

“MHSA does not bring significant overhead on mobiles if the feature dimensions are consistent and Reshape is not required.”

4D 텐서 (B, C, H, W) ↔ 3D 텐서 (B, N, C) 를 왔다갔다 하는 순간 메모리 재배치가 발생하고, 이게 지연시간의 큰 부분을 차지한다.

✅ 해결: 네트워크를 4D 구간과 3D 구간으로 딱 한 번만 나눈다. 앞부분은 계속 4D, 뒷부분은 계속 3D.

관찰 3. CONV-BN이 LN-Linear보다 빠르다

BatchNorm은 추론 시 앞의 conv에 folding(융합) 되어 사라지지만, LayerNorm/GroupNorm은 추론 중에도 통계를 계산해야 한다. 측정 결과 LN 계열이 전체 지연시간의 약 10~20% 를 차지했다.

✅ 해결: 4D 구간은 전부 CONV-BN. LN은 3D 구간에서만 (정확도상 필요한 곳에만) 사용.

관찰 4. 활성함수의 속도는 하드웨어/컴파일러에 의존한다

“GELU는 무겁고 HardSwish는 가볍다"는 통념은 기기마다 다르다. iPhone 12 + CoreML 환경에서는 오히려 GELU가 빠르고 HardSwish가 크게 느리게 측정되었다(특정 설정에서 11.9 ms → 44.5 ms).

✅ 해결: 통념이 아니라 타깃 기기에서 직접 재보고 고른다. (여기서는 GELU 채택)

관찰통념실측 결과설계 반영
1patch embed는 가볍다큰 커널/stride conv는 병목3×3 stride 2 conv stem
2attention이 느림reshape가 느림차원 일관 설계
3LN은 가볍다LN이 10~20% 차지CONV-BN 위주
4HardSwish가 빠름기기마다 다름실측 후 GELU 선택

🔷 4. 아키텍처 — Dimension-Consistent Design

flowchart LR
    I["Input<br/>224×224×3"] --> S["Conv Stem<br/>3×3 s2 ×2"]
    S --> S1["Stage 1<br/>MB4D ×N₁<br/>H/4"]
    S1 --> S2["Stage 2<br/>MB4D ×N₂<br/>H/8"]
    S2 --> S3["Stage 3<br/>MB4D ×N₃<br/>H/16"]
    S3 --> S4["Stage 4<br/>MB4D + MB3D<br/>H/32"]
    S4 --> H["Pool + FC"]

전체는 4개 stage로 구성되고, 각 stage 사이에는 stride 2 conv로 downsampling 한다. 핵심은 네트워크가 4D partition → 3D partition 순서로 딱 한 번만 전환된다는 점이다.

[4D partition]  (B, C, H, W) 유지        [3D partition]  (B, N, C) 유지
   MB4D 블록                                 MB3D 블록
   - Pool token mixer                        - MHSA token mixer
   - CONV-BN FFN                             - LN-Linear FFN
   ─────────────── 여기서 딱 한 번 flatten ────────────────►

MB4D (4D MetaBlock) — 앞쪽 stage

I  = AvgPool3x3(X) + X                  # token mixer (PoolFormer 방식)
Y  = Conv1x1_BN( GeLU( Conv1x1_BN(I) ) ) + I   # FFN을 1×1 conv로 구현
  • token mixer가 attention이 아니라 pooling → 해상도 큰 앞단에서 매우 저렴
  • 모든 연산이 CONV-BN → BN folding으로 추론 시 공짜

MB3D (3D MetaBlock) — 마지막 stage에만

I  = Linear( MHSA( Linear( LN(X) ) ) ) + X
Y  = Linear( GeLU( Linear( LN(I) ) ) ) + I

MHSA(Q,K,V) = Softmax( QKᵀ/√d + b ) · V     # b: 학습되는 attention bias
  • 가장 작은 해상도(H/32)에서만 attention을 쓴다 → self-attention은 토큰 수 $N$ 에 대해 $O(N^2)$ 이므로, $N$ 이 작은 마지막 stage에서만 쓰면 비용이 급감
  • 여기서 전역(global) 문맥을 확보 → 순수 CNN 대비 정확도 우위 유지

왜 이게 “순수 트랜스포머"인가? MobileNet 블록(depthwise separable conv 등)을 전혀 쓰지 않고, MetaFormer의 일반화된 트랜스포머 틀 (token mixer + FFN + residual) 안에서 token mixer만 pooling/attention으로 바꿔 쓰기 때문이다.

🔷 5. Latency-Driven Slimming — 지연시간을 목적함수로 하는 탐색

블록 구성을 손으로 정하지 않고, 실측 지연시간을 기준으로 탐색한다.

5.1 Supernet & MetaPath

각 위치에서 어떤 블록을 쓸지 선택지를 둔 supernet 을 정의한다.

위치선택 가능한 블록
Stage 1~2MB4D, Identity(건너뛰기)
Stage 3~4MB4D, MB3D, Identity

이 선택지 묶음을 MetaPath(MP) 라 부른다.

5.2 Gumbel Softmax 로 중요도 학습

각 후보 블록 $n$ 에 중요도 $\alpha^n_i$ 를 두고, Gumbel softmax 로 샘플링하며 supernet 을 한 번만 학습한다.

$$ \mathcal{X}_{i+1} = \sum_{n} \frac{\exp\!\big((\alpha^n_i + \epsilon^n_i)/\tau\big)}{\sum_{n}\exp\!\big((\alpha^n_i + \epsilon^n_i)/\tau\big)} \cdot MP_{i,n}(\mathcal{X}_i) $$

학습이 끝나면 $\alpha$ 가 곧 “이 블록이 정확도에 얼마나 기여하는가"의 점수가 된다.

5.3 Latency Lookup Table

후보를 매번 기기에 올려 재는 대신, MB4D/MB3D 블록을 채널 폭(16의 배수)별로 미리 측정해 표로 만들어 둔다. → 탐색 중에는 표 조회만으로 지연시간을 계산.

5.4 Action Space (줄이는 방법 3가지)

목표 지연시간에 도달할 때까지, 아래 3가지 동작 중 “1 ms 줄일 때 정확도가 가장 덜 떨어지는(−%/ms 최소)” 것을 반복 선택한다.

  1. 가장 덜 중요한 MetaPath를 Identity로 (깊이 축소)
  2. 앞쪽의 MB3D 블록 제거 (attention 축소)
  3. 가장 덜 중요한 stage의 채널 폭 축소 (너비 축소)

전수 탐색(brute-force) 없이, 정확도-지연시간 트레이드오프가 가장 좋은 방향으로만 깎아 내려가는 방식.

🔷 8. 의의와 한계

의의

항목내용
평가 기준의 전환“FLOPs/params 줄이기” → “실제 기기 지연시간 줄이기”. 이후 경량화 논문들이 실측 latency를 보고하는 흐름을 강화
attention 누명 벗기기느린 건 attention이 아니라 차원 변환(reshape) 임을 실측으로 규명
하이브리드 없이도 된다MobileNet 블록 없이 순수 트랜스포머만으로 모바일 속도 달성
탐색 비용 절감latency LUT + 점진적 slimming으로 값싼 아키텍처 탐색

한계

  • 최적화가 iPhone 12 + CoreML 에 특화됨 → 다른 NPU/컴파일러(예: Android DSP, TensorRT)에서는 결론이 달라질 수 있다 (관찰 4가 스스로 인정하는 부분)
  • 마지막 stage에서만 attention을 쓰므로, 고해상도 단계의 전역 문맥은 여전히 pooling에 의존
  • 파라미터 수 자체는 MobileNet 대비 큼 (L1이 12.3M vs MobileNetV2 3.5M) — 속도는 잡았지만 모델 크기는 아님

이후 흐름

이 마지막 한계를 겨냥한 후속작이 EfficientFormerV2: Rethinking Vision Transformers for MobileNet Size and Speed (ICCV 2023). 제목 그대로 “속도뿐 아니라 크기까지” MobileNet 급으로 맞추는 것을 목표로 한다.

🔷 9. 한 줄 요약

실제 기기에서 재 보니 ViT의 병목은 attention이 아니라 patch embedding·reshape·normalization 이었고, 이를 전부 걷어낸 차원 일관 순수 트랜스포머는 MobileNet 속도로 ViT급 정확도를 낼 수 있다.
