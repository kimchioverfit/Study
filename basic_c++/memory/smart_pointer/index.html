Smart Pointer

Smart Pointer

raw pointer의 수동 delete가 만드는 사고들(누수, double free, 댕글링 )을 소유권을 타입에 새겨서 구조적으로 막는 RAII 도구. “누가 이 메모리의 주인이고, 언제 해제되는가"를 코드가 아니라 타입이 말하게 한다.

2. unique_ptr — 기본 선택지

“이 객체의 주인은 나 하나” 를 타입으로 표현한다. 스코프를 벗어나면 소멸자가 자동으로 delete 한다.

#include <memory>

void f() {
    auto p = std::make_unique<Widget>(42);   // 생성 + 소유 시작
    p->doSomething();
    // return / 예외 / early return — 어떤 경로로 나가든 자동 delete
}

2-1. 복사 금지, 이동만 가능

주인이 하나여야 하므로 복사 생성/대입이 delete 되어 있다. 소유권을 넘기려면 std::move로 명시적으로 이전해야 한다.

auto a = std::make_unique<Widget>();
// auto b = a;              // ❌ 컴파일 에러 — 복사 불가
auto b = std::move(a);      // ✅ 소유권 이전. 이후 a는 nullptr
  • 함수에 넘겨주기: sink(std::move(p)) — 호출 후 내 쪽은 빈손이 된다
  • 함수에서 반환: return std::make_unique<T>(...) — 이동으로 소유권이 호출자에게 전달
  • 빌려주기만 할 때(소유권 이전 없이 읽기/쓰기): use(p.get())처럼 raw pointer나 참조로 전달하는 것이 관례 — “raw pointer = 비소유 관찰자"라는 역할 분담

2-2. 성능 — 사실상 공짜

unique_ptr는 멤버가 포인터 하나뿐이고 가상 함수도 없다 — raw pointer와 크기/속도가 동일하다 (커스텀 deleter가 상태를 가지면 그만큼만 커짐). “스마트 포인터는 느리다"는 걱정은 unique_ptr에는 해당하지 않는다.

2-3. 커스텀 deleter — 메모리가 아닌 자원 감싸기

해제 방법이 delete가 아닌 자원(fd, FILE*, C 라이브러리 핸들)도 감쌀 수 있다 — Rule of Zero 에서 말하는 “얇은 RAII 래퍼"를 클래스 작성 없이 만드는 방법.

// FILE* — 함수 포인터 deleter
std::unique_ptr<FILE, int(*)(FILE*)> fp(fopen("a.txt", "r"), fclose);

// fd — 람다 deleter (int라 포인터가 아니므로 관례상 얇은 래퍼가 더 흔함)
auto closer = [](int *fd) { if (*fd >= 0) close(*fd); delete fd; };

2-4. 배열

auto arr = std::make_unique<int[]>(100);   // delete[]가 자동 선택됨
arr[3] = 7;

단, 동적 배열은 대부분 std::vector가 더 낫다 (크기 추적, 성장, 반복자까지 제공).

3. shared_ptr — 공동 소유가 정말 필요할 때만

“마지막 주인이 나갈 때 해제된다” — 참조 카운트 기반 공동 소유.

auto a = std::make_shared<Widget>();   // count = 1
{
    auto b = a;                        // count = 2 (복사 가능!)
}                                      // b 소멸 → count = 1
// a 소멸 시 count = 0 → 이때 Widget delete

3-1. 동작 원리 — 제어 블록 (control block)

shared_ptr는 내부적으로 포인터 2개다: 객체 포인터 + 제어 블록 포인터. 제어 블록에는 참조 카운트(strong count), weak count, deleter가 들어 있고, 복사본들이 이 블록을 공유하며 카운트를 올리고 내린다.

3-2. 비용 — 공짜가 아니다

비용이유
크기 2배포인터 2개 (객체 + 제어 블록)
복사/소멸마다 원자 연산멀티스레드에서 카운트가 깨지면 안 되므로 fetch_add/fetch_sub — 경합 시 캐시라인 핑퐁까지 (std::atomic 참고)
간접 참조 1회 추가카운트 조작 시 제어 블록 접근

그래서 원칙은 “기본은 unique_ptr, shared_ptr는 소유자가 정말 여럿이어야 하는 설계에서만” 이다. “일단 shared로” 는 소유 관계를 흐리는 안티패턴.

3-3. make_shared를 써야 하는 이유

std::shared_ptr<Widget> p(new Widget);      // 할당 2번 (Widget + 제어 블록 따로)
auto p = std::make_shared<Widget>();        // 할당 1번 (둘을 한 덩어리로)
  • 할당 횟수 절감 + 객체와 제어 블록이 붙어 있어 캐시 지역성도 유리
  • new를 직접 쓰는 방식은 예외 안전 문제도 있었다 (C++17 이전, 인자 평가 순서 틈새로 누수 가능) — make_unique/make_shared가 항상 정답

3-4. 같은 raw pointer로 shared_ptr 두 번 만들기 금지

Widget *raw = new Widget;
std::shared_ptr<Widget> a(raw);
std::shared_ptr<Widget> b(raw);   // ❌ 제어 블록이 2개 생김 → 각자 count 0이 되며 double free

제어 블록은 raw pointer가 아니라 최초의 shared_ptr 생성 시점에 만들어지므로, 이렇게 하면 서로를 모르는 제어 블록 2개가 같은 객체를 두 번 delete 한다.

4. weak_ptr — 순환 참조를 끊는 관찰자

4-1. 문제: 순환 참조 (circular reference)

struct Node {
    std::shared_ptr<Node> next;
    std::shared_ptr<Node> prev;   // ❌ 서로를 shared로 가리키면...
};

auto a = std::make_shared<Node>();   // a: count 1
auto b = std::make_shared<Node>();   // b: count 1
a->next = b;                         // b: count 2
b->prev = a;                         // a: count 2

// a, b 지역 변수 소멸 → 각자 count 1 (서로가 서로를 잡고 있음)
// → count가 영원히 0이 안 됨 → 둘 다 영원히 해제 안 됨 (누수!)

참조 카운트 방식의 구조적 맹점이다 — 서로 잡고 있는 고리는 카운트가 0이 될 수 없다.

4-2. 해법: 고리의 한쪽을 weak_ptr로

struct Node {
    std::shared_ptr<Node> next;   // 소유 방향 (부모→자식)
    std::weak_ptr<Node>   prev;   // ✅ 관찰 방향 (자식→부모) — 카운트를 안 올림
};

weak_ptr는 제어 블록의 weak count만 올리고 strong count는 건드리지 않는다. 객체 수명에 영향을 주지 않는 “관찰자"이므로 고리가 끊긴다.

  • 설계 지침: 소유 관계는 한 방향으로만 (부모→자식은 shared/unique, 자식→부모 역참조·캐시·옵저버 목록은 weak)

4-3. 사용법 — 역참조 전에 lock()

weak_ptr는 직접 역참조할 수 없다. 대상이 이미 죽었을 수 있기 때문이다. lock()으로 “아직 살아있으면 shared_ptr로 승격” 해서 쓴다.

std::weak_ptr<Widget> w = someShared;

if (auto sp = w.lock()) {     // 살아있으면 유효한 shared_ptr (count +1)
    sp->use();                // 이 블록 안에서는 소멸되지 않음이 보장됨
} else {
    // 대상이 이미 소멸됨 — 댕글링이 아니라 "안전하게 실패"
}

raw pointer로 들고 있었다면 댕글링(UB)이 됐을 상황이, weak_ptr에서는 검사 가능한 실패가 된다.
