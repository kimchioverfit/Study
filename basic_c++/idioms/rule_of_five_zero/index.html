Rule of Five Zero

Rule of Three / Five / Zero

클래스가 자원(메모리, fd, 핸들)을 소유할 때 특수 멤버 함수를 어떻게 다뤄야 하는지에 대한 C++의 설계 규칙. 결론부터: 기본은 Rule of Zero, 자원을 직접 만지는 소수의 래퍼 클래스만 Rule of Five.

전제 개념 — RAII (Resource Acquisition Is Initialization) 자원(메모리, 파일, lock, 소켓)의 수명을 객체의 수명에 묶는 C++의 핵심 관용구. 생성자에서 자원을 획득하고, 소멸자에서 해제한다. 스코프를 벗어나는 순간 — 정상 리턴이든, early return이든, 예외가 던져졌든 어떤 경로로든 소멸자는 반드시 호출되므로, 해제를 잊는 것 자체가 불가능해진다 (C의 goto cleanup 패턴을 언어 차원에서 자동화한 것). std::string, vector, unique_ptr/shared_ptr , lock_guard, fstream이 전부 RAII 타입이다. 이 문서의 규칙들은 결국 RAII의 실천법이다 — Rule of Five = RAII 클래스를 직접 올바르게 만드는 법, Rule of Zero = 이미 만들어진 RAII 타입에게 맡기는 법.

1. 배경 — 특수 멤버 함수 6종과 자동 생성

컴파일러는 조건이 맞으면 다음 6개를 자동 생성한다.

class Widget {
    Widget();                            // 기본 생성자
    ~Widget();                           // 소멸자
    Widget(const Widget&);               // 복사 생성자
    Widget& operator=(const Widget&);    // 복사 대입
    Widget(Widget&&);                    // 이동 생성자 (C++11)
    Widget& operator=(Widget&&);         // 이동 대입 (C++11)
};

문제는 하나를 직접 선언하면 다른 것들의 자동 생성이 억제되거나 의미가 달라진다는 것이다.

사용자가 선언하면 →복사 생성/대입이동 생성/대입
소멸자생성됨 (단, deprecated — C++11부터 비권장)생성 안 됨
복사 생성자/대입(나머지) 생성됨생성 안 됨
이동 생성자/대입delete됨(나머지) 생성 안 됨

핵심 함정: 소멸자만 하나 써도 이동이 조용히 사라진다. 컴파일 에러가 아니라 이동해야 할 자리에서 전부 복사로 폴백되므로, 눈치채기 어려운 성능 저하가 된다.

2. 왜 규칙이 필요한가 — 얕은 복사 사고

class Buffer {
    char *data_;
    size_t size_;
public:
    Buffer(size_t n) : data_(new char[n]), size_(n) {}
    ~Buffer() { delete[] data_; }
    // 복사 생성자/대입을 안 썼다면? → 컴파일러가 "포인터 값 복사"로 자동 생성
};

Buffer a(100);
Buffer b = a;      // 얕은 복사: b.data_ == a.data_ (같은 메모리를 둘이 가리킴)
                   // 스코프 종료 시 delete[]가 두 번 실행 → double free, UB

자동 생성되는 복사는 멤버 단위 복사다. raw 포인터 멤버는 “주소값"이 복사될 뿐 가리키는 자원은 복제되지 않는다. 소멸자에서 그 자원을 해제하는 클래스라면 반드시 사고가 난다.

3. Rule of Three (C++98)

“소멸자, 복사 생성자, 복사 대입 — 셋 중 하나라도 직접 정의해야 한다면, 셋 다 정의하라.”

셋 중 하나가 필요하다는 것 자체가 “이 클래스는 멤버 단위 복사로는 안 되는 자원을 소유하고 있다"는 신호이기 때문이다.

class Buffer {
    char *data_;
    size_t size_;
public:
    Buffer(size_t n) : data_(new char[n]), size_(n) {}

    ~Buffer() { delete[] data_; }                        // 1. 소멸자

    Buffer(const Buffer& o)                              // 2. 복사 생성자 (깊은 복사)
        : data_(new char[o.size_]), size_(o.size_) {
        std::memcpy(data_, o.data_, size_);
    }

    Buffer& operator=(const Buffer& o) {                 // 3. 복사 대입
        if (this != &o) {                                // 자기 대입 방어
            char *tmp = new char[o.size_];               // 예외 안전: new 먼저
            std::memcpy(tmp, o.data_, o.size_);
            delete[] data_;
            data_ = tmp;
            size_ = o.size_;
        }
        return *this;
    }
};

4. Rule of Five (C++11)

C++11에서 이동 의미론이 생기면서 둘이 추가됐다: “위의 셋을 정의한다면, 이동 생성자와 이동 대입도 정의하라.”

의무는 아니다 — 안 해도 컴파일되고 동작도 맞다. 하지만 1장의 표대로 이동이 자동 생성되지 않으므로, std::vector<Buffer> 재할당이나 return buf; 같은 자리에서 전부 깊은 복사가 일어난다. “동작은 맞는데 느린” 상태가 되는 것이다.

class Buffer {
    // ... Rule of Three 부분은 위와 동일 ...

    Buffer(Buffer&& o) noexcept                          // 4. 이동 생성자
        : data_(o.data_), size_(o.size_) {
        o.data_ = nullptr;                               // 원본을 "비어있지만 소멸 가능한" 상태로
        o.size_ = 0;
    }

    Buffer& operator=(Buffer&& o) noexcept {             // 5. 이동 대입
        if (this != &o) {
            delete[] data_;
            data_ = o.data_;  size_ = o.size_;
            o.data_ = nullptr;  o.size_ = 0;
        }
        return *this;
    }
};

이동 구현의 요점:

  • 훔치고, 원본을 무해화한다 — 포인터를 가져온 뒤 원본은 nullptr로. 원본의 소멸자가 곧 실행되어도 안전해야 한다 (delete[] nullptr는 no-op)
  • noexcept가 사실상 필수 — std::vector는 재할당 시 이동 생성자가 noexcept일 때만 이동을 쓴다 (move_if_noexcept). 아니면 강한 예외 보장을 위해 복사로 폴백 → noexcept 한 단어 빠졌다고 vector 성장이 전부 깊은 복사가 된다
  • 복사+이동 대입을 하나로 합치는 copy-and-swap 관용구(operator=(Buffer o) 값 전달 + swap)도 있다 — 코드가 줄고 예외 안전이 공짜지만, 대입마다 할당이 일어나 최적 성능은 아니다

5. Rule of Zero — 실무의 기본값

“자원 관리를 스마트 포인터/컨테이너 멤버에게 맡기고, 특수 멤버 함수를 하나도 정의하지 마라.”

class Widget {
    std::string name_;                    // 문자열 자원 → string이 관리
    std::vector<int> data_;               // 동적 배열 → vector가 관리
    std::unique_ptr<Impl> impl_;          // 단독 소유 포인터 → unique_ptr가 관리
public:
    Widget(std::string name) : name_(std::move(name)) {}
    // 소멸자/복사/이동: 아무것도 안 씀
    // → 컴파일러가 "멤버들의 소멸자/복사/이동을 순서대로 호출"하는 올바른 버전을 전부 생성
};
  • 2장의 사고가 원천적으로 불가능하다: 멤버 단위 복사/이동/소멸이 각 멤버의 올바른 의미론으로 수행되므로, 클래스 차원에서 할 일이 없다
  • unique_ptr 멤버가 있으면 복사는 자동으로 delete되고 이동만 남는다 — “복사 금지, 이동 가능"이라는 소유권 정책이 타입 선택만으로 표현된다
  • 소유권별 멤버 선택: 단독 소유 unique_ptr, 공유 shared_ptr, 동적 배열 vector, 문자열 string, C 핸들(fd, FILE*)은 커스텀 deleter를 준 unique_ptr 또는 얇은 RAII 래퍼 — 상세는 Smart_Pointer 참고

Rule of Five가 필요한 곳은 바로 그 “얇은 RAII 래퍼” 한 겹뿐이다. raw 자원을 직접 만지는 클래스(위의 Buffer, fd 래퍼 등)는 Rule of Five로 완전하게 만들고, 나머지 모든 클래스는 그 래퍼를 멤버로 갖는 Rule of Zero로 작성한다 — 자원 관리 코드가 프로젝트에서 한 곳에만 존재하게 되는 구조다.

6. 예외 — 다형성 베이스 클래스

Rule of Zero의 대표적 예외. 다형성으로 쓰이는 베이스는 virtual 소멸자가 필요한데, 소멸자를 선언하는 순간 이동이 억제된다(1장의 표). 그래서 나머지도 = default로 명시해 의도를 드러낸다.

class Base {
public:
    virtual ~Base() = default;                    // virtual 소멸자는 필수인데...

    Base(const Base&) = default;                  // ...선언한 순간 나머지가 영향받으므로
    Base& operator=(const Base&) = default;       //    전부 =default로 복원 명시
    Base(Base&&) = default;
    Base& operator=(Base&&) = default;
protected:
    Base() = default;
};

(다형성 계층에서는 슬라이싱 방지를 위해 복사를 = delete 하고 clone() 가상 함수를 두는 설계도 흔하다.)

7. =default / =delete

Widget(const Widget&) = default;   // "자동 생성 버전을 그대로 원한다"는 명시적 선언
Widget(const Widget&) = delete;    // "이 연산은 금지" — 호출 시 컴파일 에러
  • = default는 문서화 효과 + 1장의 억제 규칙에 걸렸을 때 되살리는 수단
  • = delete는 복사 금지 클래스(뮤텍스 래퍼, 싱글톤 등)의 표준 표현 — C++03 시절 “private 복사 생성자 선언” 트릭의 현대적 대체물
