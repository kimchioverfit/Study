Emplace vs Push back

emplace_back vs push_back

vector에 원소를 추가하는 두 함수의 차이. 결론부터: push_back은 “완성된 객체를 받아서” 넣고, emplace_back은 “생성자 인자를 받아서” 컨테이너 내부 메모리에 직접 생성한다. 차이가 나는 상황은 생각보다 좁고, emplace에만 있는 함정도 있다.

전제 개념: 복사/이동 생성자와 그 자동 생성 규칙은 Rule of Three/Five/Zero 참고.

1. 동작 차이

struct Item {
    Item(int id, std::string name);   // 생성자
};

std::vector<Item> v;

v.push_back(Item(1, "a"));    // ① 임시 Item 생성 → ② vector 내부로 이동(또는 복사) → ③ 임시 소멸
v.emplace_back(1, "a");       // 인자를 그대로 전달받아 vector 내부 메모리에서 곧바로 생성 (1회)
  • push_back(const T&) / push_back(T&&) — T 자체만 받는다. 호출부에서 이미 T가 만들어져 있어야 함
  • emplace_back(Args&&... args) — 아무 인자나 받아서 (perfect forwarding) 내부에서 T(args...)를 호출

즉 emplace_back은 “임시 객체 생성 + 이동 + 소멸” 한 사이클을 절약할 수 있다.

perfect forwarding이란: Args&&... 템플릿 인자로 받은 값을 std::forward로 넘겨, 호출부의 lvalue/rvalue 성질을 그대로 유지한 채 생성자까지 전달하는 기법. 덕분에 emplace_back은 T의 어떤 생성자와도 연결된다.

2. 언제 차이가 나고, 언제 안 나나

차이 없음 — 이미 만들어진 객체를 넣을 때:

Item item(1, "a");
v.push_back(item);              // 복사
v.emplace_back(item);           // 똑같이 복사 (emplace라고 마법처럼 이동되지 않음)

v.push_back(std::move(item));   // 이동
v.emplace_back(std::move(item));// 똑같이 이동

이미 T인 것을 넘기면 emplace_back도 결국 복사/이동 생성자를 호출한다. 성능 동일.

차이 있음 — 생성자 인자를 넘길 때:

v.push_back({2, "b"});     // 임시 생성 → 이동 (이동이 저렴한 타입이면 차이 미미)
v.emplace_back(2, "b");    // 내부에서 직접 생성 — 임시/이동 없음
상황push_backemplace_back
완성된 객체 (lvalue)복사 1회복사 1회 (동일)
완성된 객체 (std::move)이동 1회이동 1회 (동일)
생성자 인자 전달임시 생성 + 이동 1회직접 생성 1회
이동 불가/고비용 타입 + 인자 전달임시 생성 + 복사직접 생성 1회 — 차이 극대화
  • 이동이 싼 타입(string, vector 등 포인터 몇 개 스왑)이면 실측 차이는 거의 없다
  • 이동 생성자가 없거나(레거시 클래스, 소멸자만 선언해서 이동이 사라진 경우 ) 이동이 비싼 타입일 때 emplace의 이득이 커진다

3. emplace_back만 할 수 있는 것

explicit 생성자 호출. push_back은 인자 → T의 암시적 변환이 필요하므로 explicit 생성자로는 컴파일되지 않는다.

std::vector<std::unique_ptr<int>> v;

v.push_back(new int(42));      // ❌ 컴파일 에러 — unique_ptr(T*)는 explicit
v.emplace_back(new int(42));   // ✅ 컴파일됨 — 내부에서 unique_ptr(p) 직접 호출

단, 이게 곧 함정이기도 하다 (4-2 참고).

4. emplace의 함정

4-1. 의도하지 않은 생성자 매칭

emplace는 인자를 “그럴듯한 생성자"에 그냥 연결해버린다. 코드만 봐서는 무엇이 만들어지는지 불분명해진다.

std::vector<std::vector<int>> vv;

vv.push_back({10, 20});    // {10, 20} — 원소 2개짜리 vector (initializer_list)
vv.emplace_back(10, 20);   // vector(10, 20) — "20이 10개" 짜리 vector!

같은 인자처럼 보여도 push_back은 initializer_list 생성, emplace_back은 (count, value) 생성자로 해석된다. emplace를 쓸 때는 어느 생성자에 매칭되는지 항상 의식해야 한다.

4-2. raw pointer + emplace = 예외 시 leak

std::vector<std::unique_ptr<Widget>> v;

v.emplace_back(new Widget());   // ⚠️ 위험
// emplace_back 내부에서 재할당이 일어나다 bad_alloc이 던져지면?
// → new Widget()은 이미 실행됐지만 아직 unique_ptr에 안 들어감 → leak
  • new의 결과가 unique_ptr로 감싸지기 전에 예외가 발생할 틈이 있다
  • 애초에 push_back이 이걸 컴파일 에러로 막아주는 것(explicit)은 보호 장치인데, emplace가 그 장치를 우회한다
  • 올바른 방법: v.push_back(std::make_unique<Widget>()) — 자원이 항상 스마트 포인터 안에서 태어나게 한다 (Smart Pointer 의 make 함수 원칙과 동일)

4-3. 재할당 시엔 어차피 이동/복사가 일어난다

emplace_back은 “새 원소의 생성"만 절약한다. capacity가 부족해 재할당이 일어나면 기존 원소 전체가 새 버퍼로 이동(또는 복사)되는 건 push_back과 똑같다.

  • 이동 생성자가 noexcept가 아니면 vector는 강한 예외 보장을 위해 복사로 폴백한다 — 이동 생성자에 noexcept를 붙여야 하는 실전 이유 (Noexcept 참고)
  • 원소 수를 알면 reserve()가 emplace vs push 선택보다 훨씬 큰 성능 차이를 만든다

5. 정리 — 실전 가이드

상황권장
생성자 인자를 바로 넘길 수 있음emplace_back(args...) — 임시 객체 절약
이미 만들어진 객체를 넣음push_back(x) / push_back(std::move(x)) — emplace와 성능 동일, 의도가 명확
{...} 집합 초기화로 넣고 싶음push_back({...}) — emplace는 initializer_list를 못 받음
unique_ptr 등 자원 소유 타입push_back(std::make_unique<T>(...)) — raw new + emplace 금지
성능이 정말 중요한 루프emplace/push 고민 전에 reserve() 먼저
  • map/set 계열에도 같은 관계가 있다: insert(make_pair(k, v)) vs emplace(k, v), 그리고 map 전용 try_emplace(k, v) (키가 이미 있으면 value 인자의 생성/이동조차 하지 않음)
  • C++17부터 emplace_back은 삽입된 원소의 참조를 반환한다: auto& ref = v.emplace_back(1, "a");
