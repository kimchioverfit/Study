03 Undo Recovery

Git 되돌리기 & 복구

6. 되돌리기 (restore / reset / revert)

명령어되돌리는 대상히스토리
git restore <file>working directory의 수정 취소그대로
git reset --soft <commit>커밋만 취소, 변경은 스테이징에 남김재작성
git reset --mixed <commit>커밋+스테이징 취소, 변경은 working에 남김 (기본값)재작성
git reset --hard <commit>커밋+스테이징+working 전부 삭제재작성 ⚠️
git revert <commit>해당 커밋을 되돌리는 새 커밋 생성보존 (안전)

핵심 구분: reset은 히스토리를 과거로 되감아 지운다(공유된 브랜치에 위험). revert는 “취소하는 커밋"을 새로 쌓으므로 이미 push한 커밋을 안전하게 되돌릴 때 쓴다.

reset –soft / –mixed / –hard 가 건드리는 범위

flowchart TD
    C["대상 커밋으로 HEAD 이동 (셋 다 공통)"]
    C --> S{"어디까지 되돌리나?"}
    S -->|"--soft"| A["Repository만 되감음<br/>Staging·Working 유지"]
    S -->|"--mixed (기본)"| B["Repository + Staging 되감음<br/>Working 유지"]
    S -->|"--hard"| D["Repository + Staging + Working 전부 삭제 ⚠️"]
  • --soft: “커밋만 취소하고 바로 다시 커밋하고 싶다” (메시지 재작성 등)
  • --mixed: “커밋과 add를 취소하고 파일 수정부터 다시” (가장 흔함)
  • --hard: “전부 버리고 그 시점으로 완전 복귀” — 작업 내용이 사라지니 주의

revert — 히스토리를 지우지 않고 되돌리기

gitGraph
   commit id: "A"
   commit id: "B (버그 유입)"
   commit id: "C"
   commit id: "B-취소" type: HIGHLIGHT
  • B를 없던 일로 만들지 않고, B의 변경을 반대로 적용하는 새 커밋을 맨 앞에 쌓는다.
  • 이미 push되어 남들이 받아간 커밋을 되돌릴 때 안전한 유일한 방법.

명령어설명

8. reflog — “사라진 커밋” 되살리기

reset --hard나 잘못된 rebase 로 커밋이 사라진 것처럼 보여도, Git은 HEAD가 거쳐 간 모든 위치를 reflog에 기록해 둔다. 대부분의 “망했다” 상황은 여기서 복구된다.

시나리오: 실수로 git reset --hard로 커밋 3개를 날림

flowchart TD
    A["작업: A-B-C-D-E (HEAD=E)"] --> B["실수로<br/>git reset --hard B"]
    B --> C["git log엔 A-B만 보임<br/>C·D·E가 사라진 듯 😱"]
    C --> D["git reflog 실행"]
    D --> E["출력 예:<br/>e5f1a2 HEAD@{0}: reset: moving to B<br/>a1b2c3 HEAD@{1}: commit: E<br/>...E의 해시(a1b2c3) 확인"]
    E --> F["git reset --hard a1b2c3<br/>(또는 git reset --hard HEAD@{1})"]
    F --> G["A-B-C-D-E 복구 완료 ✅"]
git reflog                      # HEAD가 거쳐 간 이력 확인 (해시 + HEAD@{n})
git reset --hard <잃은 해시>     # 그 시점으로 되돌리기
# 또는 브랜치로 안전하게 살리기
git branch recovered <잃은 해시>

핵심: 커밋은 reset/rebase로 “가리키는 포인터만 바뀔 뿐” 곧바로 삭제되지 않는다. reflog로 해시만 찾으면 되살릴 수 있다. (단, 아주 오래되면 gc로 정리될 수 있으니 발견 즉시 복구할 것.)
