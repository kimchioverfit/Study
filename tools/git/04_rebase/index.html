04 Rebase

Git Rebase 완전 정리

rebase는 이해하기 가장 까다로운 명령이라 문서를 따로 두고 크게 다룬다.

한 줄 정의

rebase = 내 브랜치의 커밋들을 떼어내서, 다른 커밋(보통 최신 main) 위에 “새로 다시 심는” 것.

base(기준점)를 re(다시) 잡는다는 뜻 그대로다. 커밋들의 부모를 갈아끼워 히스토리를 마치 처음부터 최신 위에서 작업한 것처럼 일직선으로 만든다.

merge vs rebase — 무엇이 다른가

feature 브랜치를 main에 반영하는 두 방법을 비교하자. 시작 상태는 이렇다:

gitGraph
   commit id: "A"
   commit id: "B"
   branch feature
   checkout main
   commit id: "C"
   checkout feature
   commit id: "D"
   commit id: "E"

main은 A→B→C로 나아갔고, feature는 B에서 갈라져 D→E를 쌓았다. (feature의 부모는 여전히 B다.)

① Merge 방식 — 두 흐름을 합치는 커밋을 만든다

gitGraph
   commit id: "A"
   commit id: "B"
   branch feature
   checkout main
   commit id: "C"
   checkout feature
   commit id: "D"
   commit id: "E"
   checkout main
   merge feature id: "M"
  • M이라는 병합 커밋(merge commit) 이 생기고, 두 갈래가 그대로 보존된다.
  • 장점: 실제로 언제 갈라지고 합쳐졌는지 이력이 사실 그대로 남는다.
  • 단점: 브랜치가 많아지면 그래프가 복잡한 그물망이 된다.

② Rebase 방식 — feature를 main 끝(C) 위로 옮겨 심는다

gitGraph
   commit id: "A"
   commit id: "B"
   commit id: "C"
   commit id: "D'"
   commit id: "E'"
  • D, E가 C 위에 새 커밋 D’, E’로 다시 만들어진다 (내용은 같지만 부모가 C로 바뀌었으므로 해시가 달라짐 → 그래서 ' 표기).
  • 병합 커밋 없이 히스토리가 일직선이 된다 → git log가 깔끔하다.
  • 이후 main에서 feature를 merge하면 새 커밋 없이 포인터만 앞으로 이동한다 (fast-forward).

흐름 비교 요약

[Merge]                              [Rebase]
main:  A─B─C────M                    main:  A─B─C─D'─E'   (일직선)
            \  /
feature:     D─E                     feature의 D,E는 C 위로 옮겨져 D',E'가 됨
항목MergeRebase
히스토리 모양갈래가 보존됨 (그물망 가능)일직선으로 정리됨
병합 커밋생김 (M)안 생김
커밋 해시유지변경됨 (새로 심음)
사실성실제 이력 그대로이력을 재구성(각색)
충돌 해결한 번에커밋마다 발생 가능

기본 사용법

git switch feature
git rebase main        # feature의 커밋들을 main 최신 위로 옮겨 심음

충돌이 나면 각 커밋마다 멈춘다:

# 충돌 파일 수정 후
git add <해결한 파일>
git rebase --continue  # 다음 커밋 진행
git rebase --abort     # 포기하고 rebase 전 상태로 복구

충돌은 왜 “커밋마다” 나는가 — 진행 과정 시각화

rebase는 옮길 커밋들을 하나씩 순서대로 다시 적용(replay) 한다. 그래서 merge처럼 한 번에 충돌을 만나는 게 아니라, 겹치는 커밋마다 멈출 수 있다.

feature의 D, E를 main(C까지)에 rebase하는 상황을 단계로 보자. D는 C와 충돌하지만 E는 깔끔하다고 가정한다.

flowchart TD
    S["시작: main=A-B-C, feature=B-D-E<br/>git rebase main 실행"]
    S --> D1["① C 위에 D 적용 시도"]
    D1 --> C1{"충돌?"}
    C1 -->|"예 (D vs C가 같은 줄 수정)"| FIX["멈춤 → 파일 수정<br/>git add<br/>git rebase --continue"]
    C1 -->|아니오| OKD
    FIX --> OKD["D' 생성 (C의 자식)"]
    OKD --> D2["② D' 위에 E 적용 시도"]
    D2 --> C2{"충돌?"}
    C2 -->|아니오| OKE["E' 생성 (D'의 자식)"]
    C2 -->|예| FIX2["또 멈춤 → 해결 → --continue"]
    FIX2 --> OKE
    OKE --> DONE["완료: main-A-B-C-D'-E'<br/>(포기하려면 언제든 git rebase --abort)"]
  • 옮길 커밋이 N개면 최악의 경우 N번 멈출 수 있다 — 각 커밋 시점의 변경을 순서대로 재현하기 때문.
  • 매번 --continue로 다음으로 넘기고, 도저히 안 되겠으면 --abort로 rebase 시작 전 상태로 완전히 되돌릴 수 있다 (아직 안전지대).
  • 반대로 merge는 D~E의 최종 결과만 C와 한 번 비교하므로 충돌 해결이 1회다. “충돌이 여러 번 나는 대신 히스토리가 깔끔해진다"가 rebase의 트레이드오프.

git pull --rebase — 원격과 동기화할 때

가장 흔히 rebase를 쓰는 실전 상황이다. 내가 로컬에서 커밋(X)하는 사이 동료가 원격 main에 커밋(C)을 올렸다면, 그냥 git pull은 병합 커밋을 만든다.

시작 상태 — 로컬과 원격이 B에서 갈라짐:

gitGraph
   commit id: "A"
   commit id: "B"
   branch origin/main
   checkout origin/main
   commit id: "C (동료가 올림)"
   checkout main
   commit id: "X (내 로컬 커밋)"

① 그냥 git pull (= fetch + merge) → 병합 커밋 M이 생김:

gitGraph
   commit id: "A"
   commit id: "B"
   branch origin/main
   checkout origin/main
   commit id: "C"
   checkout main
   commit id: "X"
   merge origin/main id: "M"

혼자 당겨받는 것뿐인데 의미 없는 병합 커밋이 남아 히스토리가 지저분해진다. 여러 명이 이러면 “merge bubble"이 잔뜩 생긴다.

② git pull --rebase (= fetch + rebase) → 내 커밋 X를 C 위로 다시 심어 일직선 유지:

gitGraph
   commit id: "A"
   commit id: "B"
   commit id: "C"
   commit id: "X'"
git pull --rebase origin main
# 항상 이렇게 동작하게 하려면:
git config --global pull.rebase true

정리: 당겨받기만 할 때는 --rebase로 일직선 유지가 협업 히스토리를 깔끔하게 만드는 실용 습관이다. 단, 이 역시 아직 push 안 한 내 로컬 커밋(X)만 재작성하므로 아래 황금률에 위배되지 않는다.

Interactive Rebase — 커밋 정리 (-i)

여러 커밋을 합치거나, 순서 바꾸거나, 메시지를 고칠 때 쓴다. 최근 3개를 정리하려면:

git rebase -i HEAD~3

에디터가 열리며 각 커밋 앞의 키워드를 바꿔 편집한다:

키워드동작
pick커밋 그대로 사용
reword커밋 메시지만 수정
edit커밋 내용 수정을 위해 멈춤
squash앞 커밋에 합치기 (메시지도 합침)
fixup앞 커밋에 합치기 (이 커밋 메시지는 버림)
drop커밋 삭제

예: 지저분한 “wip”, “오타 수정” 커밋 5개를 squash로 뭉쳐 의미 있는 커밋 1개로 만들어 PR을 깔끔하게 올릴 수 있다.

⚠️ Rebase 황금률

이미 원격에 push해서 다른 사람과 공유된 브랜치는 rebase하지 마라.

rebase는 커밋 해시를 바꾸므로(=히스토리 재작성), 공유된 브랜치를 rebase하면 다른 사람의 히스토리와 어긋나 git push가 거부된다. 이때 --force로 밀어붙이면 협업자의 커밋이 사라질 수 있다.

  • ✅ 안전: 아직 나만 보고 있는 로컬/개인 브랜치 정리
  • ❌ 위험: main, develop 등 공유 브랜치, 남이 이미 받아간 브랜치
  • 굳이 push된 개인 브랜치를 강제로 올려야 한다면 --force 대신 git push --force-with-lease를 써서 남의 커밋을 덮지 않도록 방어한다.

만약 rebase를 잘못해서 커밋이 꼬였다면 03. reflog 복구 로 되살릴 수 있다.
