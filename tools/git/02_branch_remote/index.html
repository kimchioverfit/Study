    02 Branch Remote

    Git 브랜치 & 원격 저장소

    4. 브랜치 (branch / switch / merge)

    명령어설명
    git branch브랜치 목록
    git branch <name>새 브랜치 생성
    git switch <name>브랜치 이동 (구버전: git checkout <name>)
    git switch -c <name>브랜치 생성 + 이동
    git branch -d <name>브랜치 삭제 (병합된 것만)
    git branch -D <name>브랜치 강제 삭제
    git merge <name>현재 브랜치에 <name>을 병합

    Fast-forward vs 병합 커밋

    gitGraph
   commit id: "A"
   commit id: "B"
   branch feature
   checkout feature
   commit id: "C"
   commit id: "D"
   checkout main
   merge feature id: "M"
    • main이 B 이후 갈라진 적 없다면 merge는 포인터만 앞으로 옮김 (fast-forward, 커밋 안 생김).
    • main도 따로 나아갔다면 위처럼 두 갈래를 잇는 병합 커밋 M 이 생김.
    • 병합 커밋 없이 일직선으로 정리하고 싶다면 merge 대신 04. Rebase 를 씀.

    5. 원격 저장소 (remote / push / pull)

    명령어설명
    git remote -v연결된 원격 저장소 확인
    git remote add origin <url>원격 저장소 등록
    git push origin <branch>로컬 커밋을 원격에 업로드
    git push -u origin <branch>업스트림 지정 후 push (이후엔 git push만)
    git fetch원격 변경을 가져오기만 함 (병합 X)
    git pullfetch + merge (또는 --rebase)

    git pull = git fetch + git merge. 히스토리를 깔끔하게 유지하려면 git pull --rebase를 쓰기도 함 (04. Rebase 참고).

    fetch vs pull

    flowchart LR
    R[("Remote<br/>origin/main")]
    subgraph 로컬
      RT["원격 추적 브랜치<br/>origin/main"]
      LB["내 브랜치<br/>main"]
    end
    R -->|git fetch| RT
    RT -->|merge / rebase| LB
    R -->|"git pull (= fetch + merge)"| LB
    • fetch는 원격 내용을 가져와 원격 추적 브랜치에만 반영함 — 내 작업 브랜치는 건드리지 않아 안전하게 먼저 확인할 수 있음.
    • pull은 그 fetch 결과를 곧바로 내 브랜치에 병합까지 함.
    • 둘 다 원격에서 삭제된 브랜치는 정리해 주지 않음 → 아래 prune 참고.

    prune — 원격에서 사라진 브랜치 흔적 정리

    원격(GitHub)에서 브랜치를 지워도 내 로컬의 원격 추적 브랜치(origin/feature)는 자동으로 사라지지 않음. PR 병합 후 브랜치를 삭제하는 팀에서는 git branch -r에 이미 없는 브랜치가 계속 쌓이게 됨. 이런 “stale(썩은)” 추적 브랜치를 지우는 것이 prune임.

    flowchart LR

    언제 이런 상태가 되나

    1. 동료(또는 내가 GitHub 웹에서)가 feature 브랜치를 PR 병합 후 삭제함.
    2. 내 로컬에서 git fetch를 해도 origin/feature는 남아 있음 — fetch는 새로 생긴 것·바뀐 것만 가져오고, 없어진 것은 지우지 않기 때문임.
    3. git branch -r에 유령 브랜치가 계속 보이고, 자동완성에도 뜨고, git log --all도 지저분해짐.

    명령어

    명령어설명
    git fetch --prune (-p)fetch하면서 원격에 없는 추적 브랜치를 함께 삭제. 가장 많이 씀
    git fetch --prune --prune-tags태그까지 원격 기준으로 정리 (로컬에서만 만든 태그도 지워질 수 있으니 주의)
    git remote prune originfetch 없이 stale 추적 브랜치만 삭제
    git remote prune origin --dry-run무엇이 지워질지 미리 보기만 함
    git remote show originstale (use 'git remote prune' to remove) 표시로 정리 대상 확인
    git config --global fetch.prune true앞으로 모든 fetch/pull에 --prune 자동 적용
    # 1. 뭐가 지워질지 확인
git remote prune origin --dry-run
#  * [would prune] origin/feature-login
#  * [would prune] origin/hotfix-123

# 2. 실제 정리
git fetch --prune
#  - [deleted]  (none)  -> origin/feature-login
#  - [deleted]  (none)  -> origin/hotfix-123

# 3. 매번 치기 귀찮으면 기본값으로
git config --global fetch.prune true

    prune이 지우는 것 / 안 지우는 것

    대상prune 영향
    원격 추적 브랜치 origin/xxx (원격에 없는 것)삭제됨
    내 로컬 브랜치 xxx그대로 남음
    태그기본은 그대로. --prune-tags를 붙일 때만 정리
    커밋 객체그대로 남음 (참조만 지우는 것. 객체 청소는 아래 git gc)

    로컬 브랜치까지 같이 정리하려면 한 단계가 더 필요함. 추적 대상이 사라진 로컬 브랜치는 git branch -vv에서 [origin/xxx: gone]으로 표시되므로 이를 골라 지움:

    git fetch --prune
git branch -vv
#   feature-login  a1b2c3d [origin/feature-login: gone] Add login
#   main           e4f5g6h [origin/main] Update README

# gone 표시된 로컬 브랜치 일괄 삭제 (bash)
git branch -vv | grep ': gone]' | awk '{print $1}' | xargs git branch -d

    -d는 병합된 브랜치만 지우므로 안전함. squash merge를 써서 Git이 “병합됨"을 인식하지 못하면 -d가 거부하는데, 그때는 내용을 확인한 뒤 -D로 강제 삭제함.

    git gc --prune 은 다른 prune임

    이름은 같지만 대상이 완전히 다름.

    명령어대상하는 일
    git fetch --prune / git remote prune참조(ref) — 원격 추적 브랜치원격에 없는 추적 브랜치 이름을 지움
    git gc --prune=<기간> / git prune객체(object) — 커밋·blob·tree어떤 참조에서도 닿을 수 없는(unreachable) 객체를 .git/objects에서 실제 삭제

    git gc --prune=now는 reflog에서도 만료된 unreachable 객체를 즉시 지우므로, 03. reflog 복구 로 되살릴 기회가 사라짐. 평소에는 Git이 자동으로 gc를 돌리므로 직접 칠 일은 거의 없고, 저장소 용량을 급히 줄여야 할 때만 씀. 일상적인 “브랜치 정리"는 항상 git fetch --prune 쪽임.
